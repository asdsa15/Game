## 三、阻断级问题（3 处）

### 🔴 问题 ①｜§2.2 的"对齐断言"按原文写必然失败——仙道前两档根本没有写入点

**方案原文**（§2.2 改法 3）：

> 对齐断言：`S.unlockStage` 的实际推进点与两张表的 `stage` 档位写一条测试断言（**仙道 0~6 / 神道 0~8 全覆盖**），防止两套口径漂移。

**实测**：`S.unlockStage` 在 game.js 中的**全部**写入点如下——

| 行号 | 代码 | 触发时机 |
|---|---|---|
| 75 | `unlockStage: 0` | 初始化 |
| 2118 | `if (nr.idx === 2) S.unlockStage = Math.max(S.unlockStage, 3)` | 破境晋**筑基** |
| 2119 | `if (nr.idx === 3) S.unlockStage = Math.max(S.unlockStage, 4)` | 破境晋**紫府** |
| 2294 | `S.unlockStage = Math.max(S.unlockStage, 5)` | 证位晋**金丹** |
| 2323 | `S.unlockStage = Math.max(S.unlockStage, 6)` | 化**道胎** |
| 2407 | `Math.max(S.unlockStage, Math.min(8, S.pillar + 1))` | 神道**破柱** |
| 5189 | `Math.max(S.unlockStage, 4)` | 紫府第三关渡尽→金丹 |
| 7364 | `S.unlockStage = 0` | 重置 |

对照两张表的语义（`data.js:1611` / `1620`）：

```
UNLOCK_XIAN  stage: 0 创角 → 1 胎息·六轮 → 2 练气·九层 → 3 筑基 → 4 紫府 → 5 金丹 → 6 道胎
UNLOCK_SHEN  stage: 0 创角 → 1 一柱·立庙 → 2 二柱·聚香 → … → 8 八柱·真君
```

**仙道侧**：破境晋**练气**（`nr.idx===1`）时**没有任何写入**。`unlockStage` 从初始的 0 直接被 2118 行推到 3。
→ **stage 1（胎息·六轮）与 stage 2（练气·九层）永远不可达**，两条 phrase 永不触发。

**神道侧**：2407 行在 `S.pillar++`（2396 行）**之后**执行，`pillar` 最小为 1，故 `pillar + 1` 最小为 2。
→ **stage 1（一柱·立庙）永远不可达**。

**合计 16 条 phrase 中，3 条永不触发**（仙道 2 条 + 神道 1 条）。

**另有一处数字错误**：方案 §2.2 写"**17 条** phrase 全部用上"。实测 `UNLOCK_XIAN` 7 条 + `UNLOCK_SHEN` 9 条 = **16 条**，不是 17。

**这不是"漂移"，是结构性的**——两套口径从建立起就没对齐过。方案把"发现死表"当成了"发现漂移"，方向偏了。

**修法**：

1. 在 2118 行前补齐前两档写入：
   ```js
   if (nr.idx === 1) S.unlockStage = Math.max(S.unlockStage, 2);  // 练气
   ```
   并在创角完成时（`finishCreate`，game.js:7311 附近）为仙道置 `unlockStage = 1`（胎息）。
2. 神道侧同理：`pillar` 为 0（一柱·立庙）时应在创角完成置 `unlockStage = 1`。
3. 断言改成**正向可触发性**表述，不要写"全覆盖"这种描述性措辞：
   > 对 `UNLOCK_XIAN` / `UNLOCK_SHEN` 每一档，断言存在至少一条把它置为 `S.unlockStage` 的代码路径，且该路径可被执行。

这样断言一旦红，就是真有档位漏了接线——而不是像现在这样"写出来就是红的"。


### 🔴 问题 ③｜§2.3 淬体：`S.hpMax` 不是计算字段，挂钩点写在了不存在的函数上

方案 §2.3 生效点一：

> `S.hpMax` 计算 × `QUENCH[S.quench].hpMul`

**实测 `S.hpMax` 的全部赋值点只有三处**：

| 行号 | 代码 |
|---|---|
| 43 | `hp: 100, hpMax: 100`（newGame 初始） |
| 4765 | `if (x.name === '力贯千钧') S.hpMax = Math.round(S.hpMax * 1.3)`（技能） |
| 7311 | `S.hpMax = 100 + (S.hpFlatBonus || 0)`（finishCreate） |
| 9348 | `else if (m.id === 'm_hand') { S.hpMax = (S.hpMax || 100) + 20; S.hp = S.hpMax; }` |

**它是存量字段，不存在任何"计算"函数**；且初始值恒为 100——**气血上限不随境界增长**（境界只影响 `monthlyHeal` 的回血比例，game.js:5346）。

因此 "× hpMul" 无处可挂。三条可选路径：

- **(a) 取用侧乘**：改 `injuryLevel`、`monthlyHeal`、`do_cbt` 伤害公式等所有读取点——面大，易漏；
- **(b) 写入侧乘**：在 7311 那行乘，4765 / 9348 两处不动；
- **(c) 引入 `hpMaxOf()` 包装**：读侧全部改走包装函数，语义最干净，但要逐个替换读取点。

**必须一并处理的是存档迁移**（方案 §六 的"缺字段默认值"惯例管不了这个）：

`injuryLevel()`（game.js:5332）按 `S.hp / S.hpMax` 比值分级（<0.15 濒死、<0.35 重伤、<0.65 轻伤）。若淬体倍率抬高 `hpMax` 而不同步抬高 `S.hp`，**老存档的伤势等级会整体漂移**（原本"无伤"变成"轻伤"）。这不是字段缺省问题，是数值口径迁移，需要在 `applyState` 里显式处理。

### 🟡 问题 ⑤｜§四 御兽迁移：`S.yaoshou` 的写入点核实无误，但转换必须在 `applyState` 内做

- `S.yaoshou` 是 boolean，初始化 game.js:113，**唯一写入点 game.js:6014**：`if (hit(55)) { S.yaoshou = true; ... }`（"妖物认亲"奇遇）

- 旧档迁移方向正确 ✅

**但方案漏了一层**：`applyState`（game.js:4323）用 `Object.assign(base, st)` 合并存档。老档的 `st.yaoshou === true` 会**原样覆盖** base 的 `false`，所以：

- `S.beast` 必须在 `applyState` 的合并段内**显式转换**（`st.yaoshou === true && !st.beast` → 生成基础兽），不能靠 `S.beast` 的缺省默认值兜底；
- 转换后应把 `S.yaoshou` 置回 `false`，避免两套状态并存。

方案引用了 game.js:4331 的注释作为"惯例先例"——那正是 `applyState` 合并段内 `dArt` 的处理处，方向完全正确，只是没点出"必须在该段内做转换"。

### 风险 B｜`Math.random → engine.rng()` 的前提不成立

方案 §三排期注记与 §八都提到"60 处裸 `Math.random` 收敛为 `engine.rng()`（半天）"。

实测：**game.js 中 `engine` / `createEngine` / `rng` 零引用**——引擎层根本不存在。game.js 是个 9494 行的单文件全局脚本，只有一层薄封装：

- `rnd(n)`（game.js:17）：`Math.floor(Math.random() * n) + 1`
- `rnd100()`（game.js:18）

`Math.random` 精确 60 处（方案数字 ✅），其中 `rnd` 调用 13 次。

所以"收敛"不是重构，是**从零建引擎**——但方案又明说"createEngine 状态外置等世界层线真正启动时再做全套"。

**批次 2 真正需要的只是"可注入种子的 RNG"**，不需要完整 engine。建议单独抽一个约 30 行的模块：

```js
// 可播种 RNG：批次 2 的破境模拟需要可复现随机数
let _seed = (Date.now() >>> 0);
function seedRnd(s) { _seed = s >>> 0; }
function rnd01() { _seed = (_seed + 0x6D2B79F5) >>> 0; let t = _seed; t = Math.imul(t ^ t >>> 15, t | 1); t ^= t + Math.imul(t ^ t >>> 7, t | 61); return ((t ^ t >>> 14) >>> 0) / 4294967296; }
```

再把 60 处 `Math.random()` 换成 `rnd01()`。这比等后端方案快得多，也不制造"半截 engine"的债务。

### 决策点 ①：淬体是否允许凡体追平先天体质？

**方案建议：允许，但凡体花 3 倍。** —— **同意。**

因此 M2 的真正收益不在"调凡体成本"，而在**顺手把 6 个死体质的加成接上**——这是 M2 范围内最高性价比的工作量（每个体质 1~3 行），比纠结凡体 3 倍成本收益高得多。建议把决策点 ① 扩为：

> ①a 淬体是否允许凡体追平先天体质（允许，凡体 3 倍）
> ①b 是否在 M2 内一并接上 6 个未实现的体质加成（建议接，否则"凡体"仍是唯一有意义的凡人选项）

### 决策点 ②：天劫失败是否掉级？

**方案建议：不掉级，改"重伤 + 修为跌三成 + 三旬锁"三重惩罚，故人关失败追加钩子事件。** —— **同意**，与 v8.0 旬制契合得很好。

一处措辞需要落实：`injuryLevel` 是**按比例计算的纯函数**，没有"拉满"这个状态。建议把"重伤（`injuryLevel` 直接拉满）"写成具体数值：

> 重伤：`S.hp = Math.max(1, Math.round(S.hpMax * 0.10))` —— 落到濒死档（比值 <0.15），回血乘 `healMul 0.35`

### 决策点 ③：首版徒弟上限？

**方案建议：1~2 人（挂 `FOLLOW_LIMIT` 表）。** —— **人数同意，挂表方式改为常量或新建 `DISCIPLE_LIMIT`**（见问题 ⑦）。
