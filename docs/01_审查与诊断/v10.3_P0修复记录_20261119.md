## 一、一句话总结

存档不是「exe 特有问题」，是 v9.0 重构引入的**跨 IIFE 作用域错误**，网页版、手机版、exe 一起中招；
exe 另有两层叠加（打包过旧、导出假成功）。本轮把这三层拆开逐个修掉，并顺手堵住了「买入→卖出」的
无风险套利口与「7 个结局永不触发」的死判定。

## 二、六项 P0

### P0-1 `VER` 跨 IIFE 未定义（存档全端失败）

| 项 | 内容 |
|---|---|
| 根因 | `envelope` / `checkSaveVersion` 在 v9.0 搬进 `rules.js`，但常量 `VER` 留在 `game.js:43`。两个文件是各自独立的 IIFE，作用域链在**定义时**绑定，`rules.js` 里的函数永远看不到 `game.js` 的闭包 |
| 症状 | 存入槽位 → `catch` 吞成「存档失败：VER is not defined」；导出/导入直接抛未捕获异常 |
| 改法 | 存档格式版本归规则层所有：`wxcs3-rules.js` 新增 `var SAVE_VER = '10.2'`，`envelope` / `checkSaveVersion` 改用它，并导出 `RULES.SAVE_VER`；`game.js` 改为 `const VER = RULES.SAVE_VER` |
| 顺带 | 版本号从「两处各写一遍」变成「唯一权威来源」，下次搬函数不会再漏常量 |

### P0-2 exe 导出走 blob，在 file:// 下被拦却报「已导出」

| 项 | 内容 |
|---|---|
| 根因 | `file://` 页面里 `a.download` 不触发下载、**也不抛异常**，`downloadJson` 于是 `return true`，调用方照报「已导出」 |
| 改法 | 新增 `downloadBlocked()`：有桌面桥（`WENDAO_DESKTOP.saveFile`）走系统另存为；判到「`file://` + Electron UA」且没有桥时**明确报错并返回 false**，不再假报成功 |
| 为什么只卡 Electron | 普通浏览器双击 `dist/index.html` 也是 `file://`，但它自带下载管理器，blob 下载照常可用。一刀切拦掉会把「本来能用」变成「报错」，所以判据收到「file:// + UA 含 Electron」这一种组合——这正是旧壳假成功的唯一场景 |
| 覆盖 | `downloadJson`（存档导出/备份）与 `downloadText`（年谱导出）两条通路一起加闸 |

### P0-3 exe 打包过旧（壳与页面都落后于源码）

| 项 | 内容 |
|---|---|
| 现象 | asar 内没有 preload 的 `saveFile`/`openFile`、没有 `ipcMain`、菜单被 `setApplicationMenu(null)` 整条去掉 |
| 处理 | `python mobile/build.py` → `npm run sync` → 重新打包 |
| 产物 | `desktop/app/index.html` 9,456.9 KB；新 exe 在 `desktop/release_v10.3_final/问道长生-win32-x64/` |
| 备注 | `release_m4` 与中途的 `release_v10.3` 两个目录的 `app.asar` 都被某个进程长期占用（EBUSY，非本项目进程、非游戏 exe），无法覆盖也无法删除，故最终另起 `release_v10.3_final`。**这两个目录都是旧包（前者带存档 bug，后者是中途版本），确认无人持锁后请直接删除** |
| 离线打包 | 本机连 electron 官方源会 ETIMEDOUT / ECONNRESET。打包器支持 `electronZipDir`：指向 `%LOCALAPPDATA%\electron\Cache\<hash>\`（内含 `electron-v33.4.11-win32-x64.zip`）即可全程离线 |

asar 实测（二进制检索）：`var SAVE_VER = '10.2'`、`const VER = RULES.SAVE_VER`、
`function downloadBlocked`、`RECOVER_BASE = 0.6`、`wendao:save`、`saveFile:`、
`Menu.setApplicationMenu` 全部命中 → 页面修复与壳能力都进包了。

### P0-4 坊市买入 → 黑市卖出 +45% 无风险套利

| 项 | 内容 |
|---|---|
| 根因 | `SELL_CHANNELS.mul` 的语义是「相对回收基准的系数」，却被直接乘在**零售价**上。市场档 1.00 就是原价收，黑市 1.45 更高 |
| 改法 | 回收价与零售价分离：`sellPriceOf()` 引入 `RECOVER_BASE = 0.6`，零售价先打六折成回收基准，渠道倍率只在此基础上浮动 |
| 结果 | 交宗门 0.42× / 坊市 0.60× / 拍卖 0.756× / 黑市 0.87×（含一成抽成与 0.9 系数）——**最高也低于进货价**，任何渠道都不再生出正套利 |
| 材料 | `do_sellmat` 原写死 `it.price × 0.8` 再乘黑市 1.45（+16%），改为走同一条 `sellPriceOf`；黑市卖材料同样记账业力 +3，与卖丹药一致 |

### P0-5 炼丹面板报价是实际售价的 2.2 倍

| 项 | 内容 |
|---|---|
| 根因 | 同一件成品有三套价：面板读 `matCostOf × 2.2`，结算读 `PILL_EXT.price`，品相再乘 `QUALITY.mul` |
| 改法 | `outPriceOf()` 改为**回产物表取零售价**（丹药→`PILL_EXT`、符→`TALISMANS`、器→`ARTIFACT_EXT`；阵盘表无 `price` 字段，退回材料成本 ×1.6 作估算，面板与结算共用同一支函数） |
| 面板 | 配方卡与制作面板改为「料 X 石 → 中品回收 Y 石/份 ×N（净 …）」，按产出份数算总回收，不再拿单价与整炉料钱相减 |
| 材料面板 | 「卖一份」的报价改为真收价（含渠道），不再是零售价 |

### P0-6 12 个结局实际只有 6 个能到

| 项 | 内容 |
|---|---|
| 根因 | `resolveEnding` 里 `if (S.deathReason) return pickEnd('fall')` 排在所有成就型结局之前，而进结局屏的唯一路径（`finalizeDeath`）**必定写 deathReason**，于是后面全部执行不到 |
| 改法 | 顺序改为「高光结局先判，死因最后兜底」：主动证位 → 登仙/道胎/世尊/真君/果位/名望/魔道 → 寿元 → 失锚 → 横死 |
| 寿元 | 寿元死只可能发生在有寿元的境界（< 道胎），前置判定不会抢走「坐化/逍遥」 |
| 神道 | 判定正则统一为 `/道化\|锚\|枯朽/`，与 `finalizeDeath` 的成就记账一致——庙神失锚不再按「陨落」收束 |
| reinc | 补 `S.reincShown` 标记：在结局屏点「百世书·烧一页重来」即视为这一世以「轮回」结尾，`resolveEnding` 认得它（此前这个结局在判定链里根本没有出口） |

## 五、本轮没做（按方案顺序顺延）

**P1**：`dispatch` 加 phase 白名单（死后仍可破境/加阶）、删 `do_rest` 里的 `S.meditate = true`（静养变 2 倍打坐）、
宗门月课改边际门槛（长老结构性亏损）、寿元死下「最后一搏」给续命或禁用、`maybeTransmitNow` 复用解锁逻辑、
`sync-app.js` / `sync_apk.py` 加「产物不得旧于源码」闸门。

**P2**：日志三处 `esc()`、`applyState` 校验 `body/root`、`achStat` 排除前世、`do_load` 的 cheated 写在新状态、
`lingqiUp` 迁移改 0、死字段清理、7 条死成就。

**数值旁支（本轮新增的待办）**：`docs/03_玩法设计/四艺设计总纲.md` §4.2 提过「成品价提到材料成本 ×2.2」，
但代码只把这条公式用在了**面板报价**上，实际成交价仍是 `PILL_EXT.price`。本轮 P0 只做到「面板不再说谎」，
于是炼丹按真价算多为负毛利——**要把这条设计真正落地，需要一次成品价/材料价的数值批次（P1）**。
