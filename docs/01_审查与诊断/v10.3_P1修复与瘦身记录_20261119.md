## 一、P1 六项

### P1-1 死后仍能操作（状态机没有入口守卫）

| 项 | 内容 |
|---|---|
| 根因 | `dispatch` 开头只 `syncInputs()`，不看 `S.phase`；键盘把 `B` 绑到 `openBreak`，而 `openBreak` / `do_xbreak` 都不检查 phase |
| 后果 | 结算屏开着按 `B` 能真的 `S.xRealm++`，结局成因、年谱、成就被死后的操作污染 |
| 改法 | 新增 `PHASE_FREE_ACT` 白名单 + `phaseAllows(act, phase)`：`dying`/`over` 两态只放行系统面板/存档/年谱/功过格/烧页/投胎/临终四选；其余 `console.warn` 后直接 return |
| 边界 | `create` / `play` / `combat` 一律放行——战斗动作不受影响 |

### P1-2 静养 = 2 倍打坐

| 项 | 内容 |
|---|---|
| 根因 | `do_rest` 的循环里留着 `S.meditate = true`（从 `do_med` 复制过来的副作用），`monthXiuwei()` 见 meditate 就 ×2 |
| 后果 | 同一月：静养 2 倍修为 + 同等回血 + 还滚事件，打坐按钮永久作废 |
| 改法 | 删掉那一行「置真」，只保留循环后的 `S.meditate = false` |

### P1-3 宗门月课按累计门槛收

| 项 | 内容 |
|---|---|
| 根因 | `sectDue()` 用 `ranks[rank].need / 40`，而 `need` 是累计升阶门槛（500/2000/8000/30000） |
| 后果 | 长老月课 750 贡献，而三旬宗门任务满打满算约 144 贡献 → 必然欠课 → 修行 −10% → 连欠三月降阶，升阶变惩罚 |
| 改法 | `SECT.ranks` 每个位阶写死 `due`，与 `pay` 同量纲（1 贡献 ≈ 5 石）：记名 10 / 外门 10 / 内门 12 / 真传 40 / 长老 120；`sectDue()` 优先读 `due`，旧数据退回边际门槛推算 |

### P1-4 寿元死「最后一搏」几乎必死且倒扣寿元

| 项 | 内容 |
|---|---|
| 根因 | 生还后统一 `lifeMax −10`，但寿元死的条件是 `age >= lifeMax` 已成立，下个月 1 号 `age++` 必再触发，而 `dyingUsed` 已置真 → 直接终局 |
| 后果 | 35% 生还其实只买到最多 11 个月，选项等于骗人 |
| 改法 | 死因为「寿元」时改为**续命一年**（`lifeMax += 12`），临终面板文案同步改为「生还三成五 · 续命一年 · 道心 −2」；普通横死仍扣十年 |

### P1-5 `maybeTransmitNow` 清空弹窗不解滚动锁

| 项 | 内容 |
|---|---|
| 根因 | 奇遇让位给传法时只写 `box.innerHTML = ''`，没解 `body.modal-open` |
| 后果 | 38% 概率之后无弹窗，移动端整页滚不动 |
| 改法 | 抽出 `clearModalBody()`（清内容 + 解滚动锁），`closeModal()` 与 `maybeTransmitNow` 共用它；全项目「清弹窗」只剩这一处实现 |

### P1-6 产物新鲜度没有闸门

| 项 | 内容 |
|---|---|
| 根因 | `sync-app.js` 直接 `rmSync` + `copyFileSync`，不比对版本或时间；`sync_apk.py` 的 `check_fresh()` 只盯 game/data/html 三个文件 |
| 改法 | `sync-app.js` 新增 `assertFresh()`：比对 `mobile/dist/index.html` 与全部 `wxcs3-*.js` / 入口 HTML / `mobile.css` 的 mtime，产物更旧就列文件并 exit 1；`sync_apk.py` 改为 `source_files()` 全量扫描（含 15 个 ext、art/scenes、icons） |
| 实测 | 本轮故意不重建直接同步，闸门拦下并列出 `wxcs3-data.js / game.js / rules.js` 三份改动——正是当时改过的文件 |

## 二、代码瘦身

### 2.1 先体检，再动手

一次性脚本（`.tmp/bloat_report.js`，不入库）扫了七类问题：同文件重复定义、只出现一次的顶层函数、无人引用的 ACT、无人使用的规则导出、零引用数据表、空函数体、体量分布。

| 检查项 | 结果 |
|---|---|
| `rules.js` 重复定义 | 3 处（`fmtTime` / `unlockRow` / `shenTongKindMarked` 各定义两次，后一次静默覆盖前一次） |
| 只出现一次的顶层函数 | 9 个 |
| 无人引用的 ACT | 2 个（`do_selldan` / `do_selltal`） |
| 无人使用的规则导出 | 0 个（34 个全在用） |
| 零引用数据表 | 4 张（`XIANJI` / `SHIXIU` / `RENCAI` / `SHOP_CATS`，合计约 20 行） |
| 空函数体 | 3 个（`renderDial` / `closeModalSoon` / `logInfo`） |
| 注释占比 | **11%**（2,243 行注释 / 20,038 行） |

| `wxcs3-game.js` | `tierLabel` / `hasArt` / `achHas` | 一行包装，实际调用点都直接写 `statTier(k).label` / `ownedArts().indexOf` / 直接读 `S.ach` |

> **行数不是本轮的主要收益**，主要收益是「静态可查的死代码归零」：再跑体检脚本，重复定义 0、单次引用函数 0、死 ACT 0。

### 2.3 看过但**故意没动**

| 对象 | 量级 | 为什么不动 |
|---|---|---|
| 零引用数据表（`XIANJI` / `SHIXIU` / `RENCAI` / `SHOP_CATS`） | 约 20 行 | 是**内容**不是代码（释修、魔门人材、仙基档位的设计底稿），已被多处 docs 引用作设计依据；删了省不下多少，却会丢设计资料 |
| 15 个扩展文件的样板头（`EXT` / `EXT_ACT` / `cur` / `ui` / `esc`） | 约 150 行 | 收益可观但要改 15 个文件 + 加载顺序，属于结构性改动，需单独评审 |
| 注释 | 2,243 行（11%） | 这个项目的注释写的是「为什么这么改」，删掉等于把踩过的坑重新埋回去 |
| `game.js` 单文件 9.4k 行代码 | — | 拆文件不减少行数，只降低单文件认知负担；改动面最大，必须先出方案再动手 |

### 2.4 结论

真正的「臃肿」不在死代码（已清完），而在**单文件 11,187 行**与**15 个扩展各带一份样板**。
这两条都属结构性改动，按项目惯例（大改动先出方案、评审后再动）留给下一轮，候选方案见 §四。
