## 一、结论摘要

| 级别 | 问题 | 影响面 |
|---|---|---|
| **P0** | `envelope()` / `checkSaveVersion()` 引用未定义的 `VER`，抛 ReferenceError | **存入槽位、导出存档、导入存档全端 100% 失败** |
| **P0** | exe 页面把导出交给浏览器 blob 下载，file:// 下被拦却回报「已导出」 | exe 导出假成功，硬盘无文件 |
| **P0** | exe 打包于 23:15，早于 preload(23:52)/main(23:57)/页面(00:01) | exe 无 IO 桥、无 IPC、无游戏菜单 |

| **P0** | `resolveEnding` 中 `deathReason` 前置 return，7 个结局永不触发 | 12 个结局实际只有 6 个能到 |
| **P1** | `dispatch` 无 phase 守卫，死后仍可破境/加阶/改状态 | 结局与年谱被污染 |
| **P1** | 静养 `S.meditate=true` 拿到闭关同款 ×2，还多回血多滚事件 | 打坐按钮永久作废 |
| **P1** | 炼丹面板按「材料×2.2」报价，实际按丹药表价回收 | 5 张丹方 4 张负毛利 |

**一句话**：存档不是「exe 特有问题」，是 **v9.0 重构引入的跨 IIFE 作用域错误，网页版、手机版、exe 全部中招**；exe 另有打包过旧、导出假成功两层叠加。

## 二、专项：存档功能失效（完整证据链）

### 2.1 现象

玩家点「存入槽位」，看到 `存档失败：VER is not defined`；点「导出文件」，提示「已导出 xxx.json」，但硬盘上找不到文件。

### 2.2 第一根因（决定性，全端）：`VER` 跨 IIFE 未定义

**定义位置**

`wxcs3-rules.js:106`
```js
function envelope(st) {
  return { format: 'wxcs3-save', version: VER, savedAt: Date.now(), state: st };
}
```
`wxcs3-rules.js:110`
```js
if (o.format === 'wxcs3-save' && v !== VER) return { ok: true, why: '存自 v' + v + '（字段已兜底）' };
```

`VER` 的唯一定义在 `wxcs3-game.js:43`：
```js
const VER = '10.2';
```

**为什么必然失败**

- `wxcs3-rules.js` 是独立 IIFE：`(function (G) { 'use strict'; ... })(window)`（`wxcs3-rules.js:25-28`）
- `wxcs3-game.js` 是另一个独立 IIFE
- JS 函数的作用域链在**定义时**绑定。`rules.js` 里的 `envelope` 永远看不到 `game.js` 闭包里的 `VER`
- `rules.js` 顶部 `'use strict'` 下引用未声明标识符 → 直接 `ReferenceError`

`wxcs3-game.js:20` 只是把函数搬过来，没有把常量带过来：
```js
const buildMeta = RULES.buildMeta, envelope = RULES.envelope;
const checkSaveVersion = RULES.checkSaveVersion;
```

**实测（Node vm 加载 data + rules，不加载 game）**

```
RULES 存在: true | envelope: function
>>> envelope 抛错: ReferenceError - VER is not defined
>>> checkSaveVersion 抛错: ReferenceError - VER is not defined
```

**失败链路**

| 调用 | 位置 | 结果 |
|---|---|---|
| `saveToSlot` → `JSON.stringify(envelope(S))` | `wxcs3-game.js:5865` | 抛错 → `catch` 吞成 toast「存档失败：VER is not defined」（5871），**槽位与自动存档都不写** |
| `do_exp`（导出单槽） | `wxcs3-game.js:5943` | 未捕获异常，按钮无反应 |
| `do_expall`（导出全部） | `wxcs3-game.js:5951` | 未捕获异常 |
| `do_imp`（导入单档） | `wxcs3-game.js:5989` | `checkSaveVersion` 抛错 |

**仍存活的只有自动存档**：`autoSave()`（5797）直接 `JSON.stringify(S)` 写 `wxcs3_save`，不经过 `envelope`。

**真实数据佐证（`%APPDATA%\问道长生\Local Storage\leveldb`）**

```
wxcs3_save      6 次   ← 自动存档在工作
wxcs3.ach       2 次   ← 成就磁盘在工作
wxcs3_slot_*    0 次   ← 槽位从没成功写进去过
wxcs3_slots     0 次   ← 槽位元数据也从未写入
```

**三份产物全部同病**（用 IIFE 边界定位 envelope 与 VER 的归属）：

| 产物 | envelope 所在作用域 | VER 所在作用域 | 同作用域？ |
|---|---|---|---|
| `mobile/dist/index.html` | 8796746–8806526 | 8806717–9293740 | **否** |
| `desktop/app/index.html` | 8797018–8806798 | 8806989–9294012 | **否** |
| exe 内 `app/index.html` | 7892448–7902228 | 7902419–8379112 | **否** |

**引入时间**：`598fdc6 refactor(v9.0#1#2): 扩展分文件机制 + 纯规则层独立`（2026-11-18 16:19）。也就是说，**从这次重构起，之后打的所有包都带这个 bug**，包括 23:15 的 exe。

### 2.3 第二根因（exe 特有）：导出走 blob，在 file:// 下被拦却假报成功

exe 内页面里 `WENDAO_DESKTOP` **出现 0 次**，`downloadJson` 只有一条路（`wxcs3-game.js` 旧版同一写法）：

```js
function downloadJson(filename, obj) {
  try {
    const blob = new Blob([txt], { type: 'application/json;charset=utf-8' });
    const url = URL.createObjectURL(blob);
    const a = document.createElement('a');
    a.href = url; a.download = filename;
    document.body.appendChild(a); a.click();
    ...
    return true;          // ← try 没抛错就返回 true
  } catch (e) { toast('导出失败：' + e.message); return false; }
}
```

`ACT.do_exp`（`wxcs3-game.js:5948`）：
```js
if (downloadJson(nm, envelope(st))) toast('已导出：' + nm);
```

Electron 的 `file://` 页面里，`a.download` 不会触发下载（没有下载管理器目标路径），但**也不会抛异常**。于是：
- `downloadJson` 返回 `true`
- `do_exp` 弹出「已导出」
- 硬盘上什么都没有

这是比「报错」更糟的一类失败：**假成功**。玩家会以为备份好了，直到重装/换机才发现没文件。

### 2.4 第三根因（exe 打包过旧）：壳与页面都落后于源码

| 文件 | mtime | exe 打包时间 |
|---|---|---|
| `desktop/release_m4/.../app.asar` | 11-18 23:15 | — |
| `desktop/preload.js` | 11-18 **23:52** | 晚 37 分钟 |
| `desktop/main.js` | 11-18 **23:57** | 晚 42 分钟 |
| `desktop/app/index.html` | 11-19 **00:01** | 晚 46 分钟 |

**解包 asar 后的实测差异**

| 能力 | exe 内 | 当前源码 |
|---|---|---|
| preload 暴露 `saveFile` / `openFile` | **无**（只有 shell/version/platform） | 有 |
| main 的 `ipcMain` / `registerIpc` / `wendao:save` | **全无** | 有 |
| 游戏菜单（存档·读档 / 年谱） | **`Menu.setApplicationMenu(null)`，整条去掉** | 有 |
| 页面调用 `WENDAO_DESKTOP.saveFile` | **0 次** | 有 |

所以 exe 里即使修好第一根因，导出仍然不可用——**必须重新打包**。

### 2.5 一条重要的排除项：localStorage 本身没问题

用 exe 自带的 smoke 探针连跑两次，探针写入 `__wendao_smoke_ls`：

```
第 1 次启动后：set@1794971053193
第 2 次启动后：set@1794971053193   ← 完全不变
```

第二次**读到了上次写的值**，所以没有重写。→ **localStorage 跨次持久化正常**，「关掉再开进度还在」这件事本身是通的（自动存档在跑）。

### 2.6 修复方案（按依赖顺序）

**第 1 步：修 `VER` 作用域（P0，必做，约 5 行）**

推荐做法——让「存档格式版本」归规则层所有，game.js 引用它，而不是反过来：

```js
// wxcs3-rules.js —— 在 IIFE 内，envelope 之前
var SAVE_VER = '10.2';
function envelope(st) {
  return { format: 'wxcs3-save', version: SAVE_VER, savedAt: Date.now(), state: st };
}
// 文件末尾导出
RULES.SAVE_VER = SAVE_VER;
```
```js
// wxcs3-game.js:43 改为
const VER = RULES.SAVE_VER;
```

理由：`VER` 是存档协议的一部分，属于纯规则；放在 rules 层可被测试直接引用，也避免下次再搬函数时漏常量。

**第 2 步：让导出失败不再假报（P0，约 15 行）**

```js
function downloadJson(filename, obj) {
  const desk = window.WENDAO_DESKTOP;
  if (desk && typeof desk.saveFile === 'function') { /* 走系统对话框，已有分支 */ }
  // 没有桥时，不要在 file:// 下假装成功
  if (location.protocol === 'file:') {
    toast('桌面版导出不可用，请用「游戏 → 存档·读档」菜单，或重新安装最新版本');
    return false;
  }
  /* 浏览器 blob 分支 */
}
```

**第 3 步：重新打包 exe（P0，一条命令）**

```

cd ../desktop && npm run sync       # 同步 app/index.html

```

打包后必须验证三件事（见 2.7）。

**第 4 步：加发布新鲜度闸门（P1）**

`desktop/scripts/sync-app.js` 目前 `rmSync` + `copyFileSync`，**不比对任何版本或时间**。建议：同步前比对 `mobile/dist/index.html` 的 mtime 与根目录 `wxcs3-*.js` 的最大 mtime，产物更旧就 **build 失败并报错**，而不是静默带旧页面打包。

同理 `mobile/sync_apk.py` 的 `check_fresh()` 只盯 3 个文件（game/data/html），漏了 14 个 `ext-*.js`、rules、mobile.css、art、icons。

## 三、阻断级：经济与结局

### 3.1 坊市买入 → 黑市卖出，+45% 无风险套利

**证据**

`wxcs3-data.js:488-493`
```js
{ id: 'market', name: '坊市摆摊', mul: 1.00, ... },
{ id: 'auction',mul: 1.40, ... },
{ id: 'black',  name: '黑市',   mul: 1.45, ... }
```

买入按原价扣（`wxcs3-game.js:3987` / `4193`）：
```js
S.stones -= it.price;
```
卖出按原价 × 渠道倍率（`wxcs3-game.js:10139`）：
```js
return Math.max(1, Math.round(base * (mul||1) * (...) * sellCh().mul * fee));
```

**后果**：`回春丹 50 买 → 黑市 73 卖`；`传音符 90 → 131`。买卖都是 0 旬、0 风险、可无限重复。灵石曲线在开局第一天失去意义，后面所有定价（淬体 107,900、神器、灵脉）全部作废。

**为什么是真问题**：`SELL_CHANNELS.mul` 的语义是「回收折价」，0.70/1.00/1.40/1.45 明显是「相对某基准的系数」，却被直接乘在**零售价**上。市场档 1.00 已经是买 100 卖 100，黑市直接正套利。且 `data.js:490` 写着「每月限件数」，`sellTally()`（`wxcs3-game.js:10723`）只统计不拦截，限制从未实现。

**修复方向**：回收价与零售价分离。买入价 `price`，回收基准 `price * SELL_BASE`（建议 0.55~0.65），渠道倍率只作用于回收基准，且 `max(mul)` 不超过 1.0。或者更简单：`sellPriceOf` 里把 `base` 改成 `base * 0.6` 作为回收基准。

### 3.2 材料回收 0.8 × 原价 × 1.45 = +16%

`wxcs3-game.js:10273-10282`
```js
const price = sellPriceOf(it.price * 0.8, 1);
S.stones += price;
// 没有 S.karma += 3
```

补气草 60 买 → 70 卖，每次 +10，0 旬、0 业力。而同文件 `do_sellitem` 走黑市会加业力（10259）。

### 3.3 炼丹面板报价是实际售价的 2.2 倍以上

**面板**（`wxcs3-game.js:9207`）：
```js
function outPriceOf(recipe, quality) {
  const base = matCostOf(recipe) * 2.2;
```
**实际回收**（`wxcs3-game.js:10227`）：
```js
} else if (kind === 'dan') {
  def = D.PILL_EXT.find(...); base = def.price;
```

| 丹方 | 材料成本 | 面板承诺 | 实际卖价 | 真实毛利 |
|---|---|---|---|---|
| 回春丹 | 200 | 440（净 +240） | 50 | **−150** |
| 聚气丹 | 120 | 264（净 +144） | 40 | **−80** |
| 清心丹 | 230 | 506（净 +276） | 120 | **−110** |
| 生肌续骨丹 | 660 | 1452（净 +792） | 140 | **−520** |
| 玉华灵水 | 370 | 814（净 +444） | 760 | +390 |

玩家照面板买料炼丹，四炉亏三炉半。制符则相反（面板写 110，实际成 3 张 = 330），真实利润是面板的 3 倍。

**根因**：同一个「成品」有三套价格——`matCostOf×2.2`、`PILL_EXT/TALISMANS/ARTIFACT_EXT.price`、`QUALITY.mul`。界面读第一套，结算读第二套。

### 3.4 12 个结局实际只有 6 个能到

`wxcs3-game.js:8934-8968`，精简后：
```js
if (S.endingId) return pickEnd(S.endingId);
if (S.deathReason && /寿元/.test(...)) { ... }        // sit / xiaoyao
if (S.deathReason && /道化|锚/.test(...)) return pickEnd('daohua');
if (S.deathReason) return pickEnd('fall');            // ← 这里拦截了一切
if (isXian() && S.xRealm >= 5) { ... return pickEnd('ascend'); }
if (S.xRealm >= 5) return pickEnd('daotai');
if (S.pillar >= 7 && S.merit >= 300) return pickEnd('shizun');
...
```

**关键**：进入结局屏的路径只有两处——
- `wxcs3-game.js:765` `S.phase='over'; S.deathReason=reason;`（**必写 deathReason**）
- `wxcs3-game.js:6507` `S.phase='over';`（`do_zhenjun` 同时写 `endingId`）

所以只要不是「证真君」主动走的后门，`deathReason` 必然非空 → `return pickEnd('fall')` 先返回 → 后面全部执行不到。

**可达 6 个**：`sit` `xiaoyao` `daohua` `fall`（死亡）+ `zhenjun` `shizun`（主动证位）
**不可达 6 个**：`guowei` `daotai` `ascend` `xianzun` `modao` `reinc`
（`reinc` 连 `pickEnd('reinc')` 调用都没有）

**为什么测试没发现**：`tools/test_reachability.js` 用 `setup({deathReason:null})` 逐个调用 `resolveEnding`，验证的是一个**游戏永远不会产生的状态**。这是假通过。

**修复方向**：把「高光结局」判定提到死因之前——
```js
if (S.endingId) return ...;
// 先判成就型结局（道胎/登仙/果位/名望/业力）
if (isXian() && S.xRealm >= 5 && 四锚全固) return pickEnd('ascend');
if (S.xRealm >= 5) return pickEnd('daotai');
...
// 最后才按死因兜底
if (/寿元/.test(S.deathReason)) ...
if (/道化|锚/.test(...)) ...
return pickEnd('fall');
```
同时补 `reinc` 的判定（`do_legacy` 烧页时写标记），并给 `test_reachability` 加「真实死亡流程」用例：`hp=0 → render → do_die('close')` 之后断言 endingId。

## 四、严重级

### 4.1 死后仍能操作（状态机没有入口守卫）

`dispatch`（`wxcs3-game.js:8718`）开头只做 `syncInputs()`，**不检查 `S.phase`**：
```js
function dispatch(act) {
  if (!act) return;
  syncInputs();
  ...
```

键盘映射（`wxcs3-game.js:6676`）把 `b` 绑到 `act:openBreak`，`openBreak`（2603）与 `do_xbreak`（2854）都不检查 phase。

**后果**：玩家已经死了、结算屏开着，按 `B` 能打开破境面板并真的 `S.xRealm++`（2977）。结局成因、年谱、成就都可能被死后的操作污染。

**修复方向**：`dispatch` 开头加白名单——`S.phase !== 'play'` 时只放行 over/dying 屏自己的动作（`do_burn` / `do_rebor` / `do_die:*` / `act:sys` 等），其余直接 return 并 `console.warn`。

### 4.2 静养 = 2 倍打坐，还多回血多滚事件

`wxcs3-game.js:6747-6760`
```js
ACT.do_rest = (n) => {
  S.xun = 0;
  for (let i = 0; i < n; i++) {
    S.meditate = true;                       // ← 与打坐相反
    if (isXian() || ...) gainXiuwei(monthXiuwei());
    ...
    advanceMonth(1);
  }
  S.meditate = false;
  ...
  maybeEvent();                              // ← 打坐没有
```
`monthXiuwei()`（`wxcs3-game.js:276`）：`if (S.meditate) v *= 2;`

而打坐（`ACT.cultivate`，`wxcs3-game.js:2497`）显式 `S.meditate = false`。

**后果**：同样一个月，静养给 2 倍修为 + 同等回血 + 事件，打坐给 1 倍。玩家一旦发现，打坐按钮永久作废，紫府期从 625 月直接减半。

**为什么是真问题**：`do_rest` 的注释（6754-6755）写的是「静养也是修行：按月给足额，否则与面板上『把时间换成气血与修为』对不上」——作者意图是「与打坐同额」，但 `S.meditate = true` 留在循环里，实际成了 200%。这是复制 `do_med` 时带过来的副作用。

**修复方向**：删掉 `do_rest` 里的 `S.meditate = true`（保留 `S.meditate = false`），或改成 `monthXiuwei()` 内部区分「闭关」与「静养」两种乘数。

### 4.3 宗门月课按累计门槛收，长老结构性亏损

```js
function sectDue() {

  return Math.max(10, Math.round((r.need || 0) / D.FIXED_COST.sectDueNeedDiv));
}
```
`need` 是**累计**升阶门槛（500/2000/8000/30000），`pay` 是月俸（20/60/200/600）。

| 位阶 | 月课（贡献） | 折灵石 ×5 | 月俸 | 净 |
|---|---|---|---|---|
| 真传 | 200 | 1000 | 200 | −80 |
| 长老 | **750** | **3750** | 600 | **−3150** |

**后果**：升到长老后，每月 3 旬全做宗门任务也只有 ~144 贡献，必然欠课 → 修行 −10% → 连欠三月降阶。升阶变成惩罚。

**修复方向**：月课改用「本阶边际门槛」而不是累计门槛，例如 `(need[i] - need[i-1]) / div`；或直接给每个位阶写死 `due` 字段，与 `pay` 同量纲。

### 4.4 临终「最后一搏」在寿元死下几乎必死且倒扣寿元

`wxcs3-game.js:6431`
```js
if (rng() < 0.35) {
  S.phase = 'play'; S.hp = 1;
  S.lifeMax = Math.max(20, (S.lifeMax || 60) - 10);
  ...
}
```
寿元死条件（`wxcs3-game.js:517`）：`if (S.age >= S.lifeMax) die(...)`。

**后果**：寿元死时 `age >= lifeMax` 已成立，复活后 `lifeMax` 再 −10，下个月 1 号 `age++` 必然再次触发，而 `dyingUsed` 已置 true（738），直接 `finalizeDeath`。玩家的 35% 生还其实只买到最多 11 个月。

**修复方向**：`stand` 成功时除了 `hp=1`，必须同时给出「续命」——例如 `S.lifeMax += 12`（换来一年）或 `S.age -= 1`，否则这个选项在寿元死因下没有意义。或者干脆在寿元死因下禁用「最后一搏」，只留传功/托付。

### 4.5 神道失锚死因文案与结局判定不一致

`wxcs3-game.js:686`
```js
die(isXian() ? '道化：...' : '枯朽：像犹在，不复应汝。');
```
判定（`wxcs3-game.js:8944`）只认 `/道化|锚/`，而 `finalizeDeath`（759）的成就记账认 `/道化|锚|枯朽/`。

**后果**：神道失锚而死，功过格点亮「忘了自己」（道化），终局大字却写「陨落」，正文是「血落在土里」——一个庙神死得像被剑捅死。

**修复方向**：判定正则统一为 `/道化|锚|枯朽/`，或让 `die()` 在神道失锚时统一写「道化」。

## 六、系统性根因（比单条 bug 更重要）

### 根因 1：跨文件搬迁只搬函数，不搬依赖常量，且没有契约测试

`VER` 从 game.js 搬进 rules.js 时丢了定义。`saveToSlot` 的 `catch` 又把它降级成一句 toast，所以**从 16:19 到 23:15 打包、到 00:01 重建 dist，七个多小时、多次构建、全部测试通过，没有一个人发现**。

同类：`check_ach.js` 用正则猜「谁写过 tally」，把 `===` 当成赋值；`ARCHIVED` 白名单里 `relic` 早已实现却还挂着。

**结论**：版本常量、字段写入点这类跨文件契约，目前**没有任何单一权威来源或端到端测试守住**。

### 根因 2：时间只有 `advanceXun` 一个名义入口，但「月产」被复制成四条实现

`monthXiuwei` 在打坐（×1）、静养（×2）、闭关（×2）、历练（`8+rk*7`）里各算一遍；`tribLock` 只在 `advanceXun` 里递减，而 `do_med` / `do_rest` 直接 `advanceMonth` 绕过它。

**后果**：天劫失败后闭关 30 年，出来仍提示「余威未散，还需 3 旬」。

### 根因 3：状态机只有渲染层兜底，入口层没有准入

`die()` 只改 `phase` 不负责刷新；`dispatch` 和键盘映射对 `phase` 完全无感；各 `ACT.*` 自己零散补 `if (S.phase !== 'play') return render()`。补漏的地方（破境结算 3061、神道破柱 3341、`do_xbreak`）就成了「死后还能操作」「界面停在旧屏」的缝隙。

### 根因 4：界面数字与结算数字分属两处

`outPriceOf`（材料×2.2）给玩家看，`PILL_EXT.price` 拿来结算；`buildInfo()` 漏 `xianghuo` 键，扩展就显示「香火 undefined」。凡是「面板一套、结算一套」的地方，都会漂移。
