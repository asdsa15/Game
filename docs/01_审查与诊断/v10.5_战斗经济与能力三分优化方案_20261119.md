## 一、结论摘要

本轮排查的重点不是"数值大小"，而是三处**口径断裂**：

1. **上限没有成长来源**：`hpMax/mpMax` 在创角时写死 100，破境只改 `lifeMax`，导致境界、修炼、功法、淬体的成长全部挤在 100 的尺度里。
2. **购买与收入不进账本**：坊市买入、斗法战利品均不写 `ledgerAdd`；宗门月课还存在"贡献扣光 + 全额现金"的重复扣费。
3. **能力三分没有数据边界**：`GONGFA_EXT` 同时装"修炼功法"与"杀伐术法"，`do_setgf` 允许把《烈火掌》当道基；UI 又把 `SKILLS` 叫"神通"，与真正的 `SHENTONG` 混用。

优先级建议：

| 级别 | 先修什么 | 原因 |
|---|---|---|
| P0 | C1/C2/C3 + S1（上限体系与迁移） | 影响所有丹药、耗灵、功法承诺，且越晚改迁移成本越高 |
| P0 | E1/E2/E3（记账与月课） | 纯错误，不涉及平衡，修完即可验证 |
| P0 | A1/A2（role 字段与道基校验） | 语义错误，越晚改旧档分派越复杂 |
| P0 | E5/E6/E7（坊市连续购买/法器唯一/灵脉契） | 需求 5 的核心，改动局部、收益直接 |
| P1 | C4/C5/C6（固定值百分比化/死亡螺旋/位格表） | 平衡调整，需依赖 P0 的上限体系 |
| P1 | A3~A6、N1/N2（文案与神通配置化） | 统一概念，预留后续扩展 |
| P1 | E4/E8/M1/M2（限件/行情/采集文案/四艺毛利） | 经济深度与承诺兑现 |
| P2 | 账本明细、`hpRatio()`、测试补全 | 体验与可维护性 |

**不改的部分**：`dispatch`/`ACT`/扩展钩子、比例伤害框架、淬体/受箓/命格/功法熟练度/态势、存档信封与槽位协议。只做"补洞 + 统一口径 + 表驱动"。

## 二、项目现状梳理

### 2.1 分层与加载顺序

```

```

| 层 | 关键内容 |
|---|---|
| 数据 | `XIAN_REALMS`（六境 power 8→6000、life 120→null）、`PILLARS`（八柱 power 10→8000）、`GONGFA_EXT`、`SKILLS`、`SHENTONG`、`RECIPES`、`SHOP`、`SELL_CHANNELS`、`FIXED_COST` |
| 规则 | `rankBaseXian`、`keMul`、`qualityDef`、`outNameOf`、`envelope`/`SAVE_VER` |
| 表现 | `computePower`、`startCombat`/`do_cbt`/`foeTurn`/`settleCombatWin`、`openShop`/`do_buy`/`do_buyg`、`advanceMonth`/`applyFixedCosts`、`applyState`/`recalc*` |

### 2.2 三条核心数据流

**战斗**

```
startCombat 按玩家战力锚定敌人（常规 0.55~1.55，仇家 1.25~2.0）
  → do_cbt 按 foe.hpMax 比例出伤（attack 0.19×ratio / skill 0.21 / shentong 0.26）
  → foeTurn 按 S.hpMax 比例还手（0.15 × 1/ratio）
  → settleCombatWin 给灵石 / 修为 / 香火
```

**经济**

```
收入：斗法战利品 / 卖货（四渠道 × RECOVER_BASE 0.6）/ 宗门俸禄 / 香火钱 / 任务
支出：坊市与庙市购买 / 淬体 / 破境 / 四艺材料 / 固定开销 / 阵盘与神器维护
```

**属性**

```
hpMax / mpMax 是缓存字段
quench / mpGfMul / lifeGfBonus 记录"已应用的乘区"，靠差额换算
```

### 2.3 已具备的好设计（应保留）

- 伤害按比例结算（`foe.hpMax × 0.19` / `S.hpMax × 0.15`），天然抗数值通胀；
- 胜利结算单一出口 `settleCombatWin`，灼烧/毒/雷不会漏结算；
- 售价与结算同源 `outPriceOf` + `sellPriceOf`，已堵住"坊市买→黑市卖"套利；
- 扩展薄缝/乘区注册表，新增玩法不必改 `game.js`；
- 存档信封、槽位、旧档字段兜底齐全。

## 四、优化方案 · 属性上限与战斗

### 4.1 血量/灵力上限：从"固定 100"改为"境界基数 × 成长乘区"

#### 4.1.1 设计目标

1. 上限随**大境界 / 小阶（神道为柱/位）**成长；
2. 保留淬体、受箓、天赋、残忆、功法等既有乘区；
3. 所有加成改为"字段记录 + 统一重算"，禁止直接改缓存值；
4. 旧档只升不降；
5. 战斗仍按比例结算，不改变"几回合打死"的节奏。

#### 4.1.2 数据表（`wxcs3-data.js`）

```js
/* 境界基数：配合 XIAN_REALMS / PILLARS 使用，便于后续调平衡。
   数值取"每境约 ×1.8~2.0"，与 power 的 ×2.5~4 解耦——
   气血不应跟着战力指数爆炸，否则丹药与固定伤害全部失真。 */
const CAP_BASE = {
  xian: {
    hp: [100, 180, 320, 600, 1200, 2400],   // 胎息→道胎
    mp: [100, 160, 260, 420, 700, 1200]
  },
  shen: {
    hp: [100, 150, 240, 380, 600, 950, 1500, 2400], // 一柱→八柱
    mp: [100, 140, 200, 300, 450, 650, 950, 1400]
  }
};
const CAP_STAGE_STEP = 0.04;   // 每小阶 / 每位 +4%
```

说明：

- 胎息基数仍为 100，保证现有 `test_play.js` 的 100→110→232 断言不需要改；
- 筑基 320 / 紫府 600 / 金丹 1200 / 道胎 2400，与 `lifeMax` 的 400/700/1200/null 同量级，玩家不会出现"寿元 1200、气血 100"的割裂；
- 神道八柱基数单独一套，避免双修/神道借用仙道境界索引。

#### 4.1.3 单一重算出口（`wxcs3-game.js`）

```js
function capLine() {
  if (isShen() && !hasXianLine()) return 'shen';
  return 'xian';
}

function capBase(kind) {
  const line = capLine();
  const arr = D.CAP_BASE[line][kind];
  const idx = line === 'shen' ? (S.pillar || 0) : (S.xRealm || 0);
  const sub = line === 'shen' ? (S.pos || 0) / 4 : (S.xStage || 0);
  return Math.round(arr[clamp(idx, 0, arr.length - 1)] * (1 + D.CAP_STAGE_STEP * sub));
}

/* 气血乘区：淬体 × 受箓 × 永久事件 × 功法 */
function hpMulAll() {
  const X = G.WXCS3_EXT;
  const gf = (X && X.gongfaHpCap) ? clamp(numOr(X.gongfaHpCap(), 0), 0, 0.5) : 0;
  return quenchHpMul()
    * (S.hpLuMul || 1)      // 力贯千钧 1.3
    * (S.hpPermMul || 1)    // 事件/残忆等永久乘区
    * (1 + gf);
}

/* 灵力乘区：功法（吞海功 1.15）× 受箓（重海长鲸 1.5）× 永久 */
function mpMulAll() {
  return gongfaMpCapMul()
    * (S.mpLuMul || 1)
    * (S.mpPermMul || 1);
}

function recalcCaps(keepRatio) {
  const oldHp = Math.max(1, S.hpMax || 100);
  const oldMp = Math.max(1, S.mpMax || 100);
  S.hpMax = Math.max(1, Math.round((capBase('hp') + (S.hpFlatBonus || 0)) * hpMulAll()));
  S.mpMax = Math.max(10, Math.round((capBase('mp') + (S.mpFlatBonus || 0)) * mpMulAll()));
  /* 兼容字段：只供面板/扩展读取，不再参与换算 */
  S.mpGfMul = gongfaMpCapMul();
  S.hpGfMul = hpMulAll() / Math.max(1, quenchHpMul() * (S.hpLuMul || 1) * (S.hpPermMul || 1));
  if (keepRatio) {
    S.hp = clamp(Math.round((S.hp || 0) * S.hpMax / oldHp), 0, S.hpMax);
    S.mp = clamp(Math.round((S.mp || 0) * S.mpMax / oldMp), 0, S.mpMax);
  } else {
    S.hp = Math.min(S.hp || 0, S.hpMax);
    S.mp = Math.min(S.mp || 0, S.mpMax);
  }
}
```

`syncMpCap()` 保留为薄包装：

```js
function syncMpCap() { return recalcCaps(true); }
```

`S.mpGfMul` 仍可保留，但只作"上一次应用的乘区"显示/兼容，不再作为换算基准。

在 `applyState` 末尾、所有字段兜底之后执行：

```js
if (!st.capVer) {
  const baseHp = capBase('hp');
  const baseMp = capBase('mp');
  const qMul = Math.max(1, quenchHpMul());
  /* 旧上限里已含淬体，先除掉再反推 flat，避免二次复利。
     取 max：旧档若已含受箓 ×1.3，这部分被当成 flat 保留，不砍玩家。 */
  S.hpFlatBonus = Math.max(S.hpFlatBonus || 0,
    Math.max(0, Math.round((st.hpMax || 100) / qMul - baseHp)));
  S.mpFlatBonus = Math.max(S.mpFlatBonus || 0,
    Math.max(0, Math.round((st.mpMax || 100) - baseMp)));
  S.capVer = 1;
}
recalcCaps(true);
```

原则：

- 旧玩家上限**只升不降**；
- 新档 `hpFlatBonus/mpFlatBonus` 从 0 起；
- `capVer` 防止重复迁移；
- 迁移后再 `recalcCaps(true)`，保持 `hp/hpMax` 比值，伤势不漂移。

#### 4.1.7 战斗公式是否需要改

**不需要改伤害比例本身**：

- 玩家输出 `foe.hpMax × 0.19`：与玩家上限无关；
- 敌方输出 `S.hpMax × 0.15`：上限涨，敌方绝对伤害涨，但玩家血量同比例涨，节奏不变；

### 4.2 战斗系统：保留比例制，修固定值稀释与死亡螺旋

#### 4.2.1 固定值改为"下限 + 上限百分比"

| 项目 | 现在 | 改为 | 理由 |
|---|---|---|---|
| 回春丹 `hp` | 固定 +50 | `max(50, round(hpMax×0.08))` | 高境界吃低阶丹不应无感 |
| 生肌续骨丹 `hp` | 固定 +160 | `max(160, round(hpMax×0.08))` | 同上 |
| 聚气丹 `mp` | 固定 +40 | `max(40, round(mpMax×0.08))` | 同上 |
| 术法耗灵 | `sk.cost` 20~60 | `max(sk.cost, round(mpMax×0.05))`（0 仍 0） | 防止高境界灵力无限 |
| 神通耗灵 | `sp.cost` 30~45 | `max(sp.cost, round(mpMax×0.08))`（免灵仍 0） | 同上 |
| 百魂幡 | 固定 −5 | `max(5, round(hpMax×0.01))` | 固定 5 在 1200 上限时是噪声 |
| 月回灵 | `5 + xRealm×3` | `max(5 + xRealm×3, round(mpMax×0.06))` | 高境界灵力池大，回得太慢会卡死连续战斗 |

实现建议：

```js
function skillCostOf(sk) {
  if (!sk || !sk.cost) return 0;
  return Math.max(sk.cost, Math.round(S.mpMax * 0.05));
}
function shenTongCostOf(sp) {
  if (!sp || !sp.cost) return 0;
  return Math.max(sp.cost, Math.round(S.mpMax * 0.08));
}
function pillHealOf(it, kind) {
  const base = it.v || (kind === 'mp' ? 40 : 50);
  const pct = 0.08;
  return Math.max(base, Math.round((kind === 'mp' ? S.mpMax : S.hpMax) * pct));
}
```

调用点：

- `do_cbt` 的 `skill` 分支：`S.mp < skillCostOf(sk)`、`S.mp -= skillCostOf(sk)`、面板 `openSkills` 同步；
- `do_cbt` 的 `shentong` 分支：`_cost2 = freeFirst ? 0 : shenTongCostOf(sp)`；
- `applyPill`：`hp`/`mp` 分支；
- `applyAttackArtCost`：`hpCostPct`；
- `advanceMonth` 灵力回复。

#### 4.2.2 死亡螺旋加保底

现状：

- `computePower` 在 `hp/hpMax < 0.33` 时 ×0.4、`<0.66` 时 ×0.7；
- `foeTurn` 的 `ratio = sqrt(computePower/foe.power)`，clamp 0.2~2.5，敌伤 `× (1/ratio)`。

问题：低血 → 战力 0.4 → ratio 0.63 → 敌伤 ×1.58；玩家输出同时下降，形成正反馈死亡。

建议：

1. 低血惩罚从 0.4 提到 **0.55**（仍保留"重伤乏力"的语义，但不至于必死）；
2. `foeTurn` 的 `ratio` clamp 改为 **0.35~2.5**，`1/ratio` 最大约 2.86（原 5）；
3. 战斗面板显示"重伤 · 战力 ×0.55"或"濒死 · 战力 ×0.55"，让玩家知道原因；
4. 可选：给"绝境"一次自动护命（已有 `foeTurn` 的 40% 直接死 / 60% 重伤二分，可保留）。

#### 4.2.3 位格压制统一口径

现状：

- 玩家出手：`gap≥2 → ×0.15`、`gap=1 → ×0.45`、`diff≤-2 → ×1.3`；
- 敌方还手：`gap≥1 → ×1.6`、`gap≤-1 → ×0.35`；
- 玩家用 `gapCut` 后的 gap，敌方用原始 `gap`。

建议建一张表（数值可调）：

```js
const GAP_MUL = {
  up2:  { out: 0.15, inc: 1.60 },  // 低两档打高两档
  up1:  { out: 0.45, inc: 1.60 },
  even: { out: 1.00, inc: 1.00 },
  down1:{ out: 1.30, inc: 0.35 },
  down2:{ out: 1.30, inc: 0.35 }
};
```

- 玩家出手与敌方还手共用同一张表；
- 战斗面板显示"位格差 1 档：伤害 ×0.45 / 受伤 ×1.6"；
- `gongfaGapUp()` 与 `temperPierce` 继续只压 `gap`，不改表。

#### 4.2.4 战利品公式

现状：`loot = 100 + foe.rank × 200`（rank 是位阶序号，最大约 25 → 5100）。

问题：rank 高但实力低的敌人（如被削弱、带伤、越阶生成）会给过高战利品；与"对手强度"脱节。

建议：

```js
const loot = Math.round((60 + c.foe.power * 0.5) * fateMul('loot'));
```

- 胎息散修 power 10 → 65 石；
- 金丹 power 1500 → 810 石；
- 道胎 power 6000 → 3060 石；
- 保留 `S.fame += 5` 与 `noteCombatWin` 的额外声望；
- 同步补 `ledgerAdd('in', '斗法所得', loot)`。

#### 4.2.5 状态可见性

- 灼烧/迟滞/破绽/压势：在敌方面板加小标签（`火 2`、`迟 1`、`破 1`）；
- `burnTickOf` 已是唯一公式，面板与结算同源，不重复定义；
- `burnFresh` 的"点火回合不烧"在标签上写"余焰将起"，避免玩家以为没生效。

#### 4.3.1 记账收口

| 动作 | 现在 | 补记 |

原则：**任何 `S.stones` 变化都必须同时进账本**。这是项目 v10.3 "面板/结算同源"的同一教训——两套账迟早会对不上。

实现建议：在 `do_buy` / `do_buyg` 扣款后统一调用一个 `spendStones(amount, label)`：

```js
function spendStones(n, label) {
  if (!(n > 0)) return true;
  if (S.stones < n) return false;
  S.stones -= n;
  if (S.stones === 0) bump('buyAtZero');
  ledgerAdd('out', label, n);
  return true;
}
```

这样"余额校验 + 扣款 + 记账 + 空囊成就"只有一处，避免各购买分支各写一遍。

#### 4.3.2 宗门月课混合缴纳

现状（`1910-1916`）：

```js
const cash = due * D.FIXED_COST.sectCashPerContrib;
if (S.stones >= cash) {
  S.stones -= cash;
  S.sect.contrib = Math.max(0, (S.sect.contrib || 0) - due);
  ...
}
```

问题：`contrib=90, due=120` 时，贡献扣光，仍按 `120×5=600` 收费。

改为：

```js
const have = Math.max(0, S.sect.contrib || 0);
const gap = Math.max(0, due - have);
const cash = gap * D.FIXED_COST.sectCashPerContrib;
if (S.stones >= cash) {
  S.sect.contrib = Math.max(0, have - due);   // 先扣贡献，再补缺口
  S.stones -= cash;
  ledgerAdd('out', '宗门月课（灵石抵缴）', cash);
  logLine('贡献 ' + have + '，缺口 ' + gap + ' 折 ' + cash + ' 灵石。', '');
  continue;
}
```

边界：

- `have >= due`：`gap=0`、`cash=0`，只扣贡献，不进现金分支；
- `have=0`：`cash=due×5`，与旧行为一致；
- 现金不足：仍走欠账/降阶逻辑。

#### 4.3.6 价格与行情（防套利）

现状：

- 买入价固定（`it.price`）；
- 卖出价 `sellPriceOf = base × 0.6 × 行情 × 品相 × 渠道`；
- 已堵住正套利，但行情只影响卖出，囤货无意义。

建议：

```js
function buyPriceOf(it) {
  const base = it.price || 0;
  const cat = it.cat || 'pill';
  const m = (S.market && S.market.buy && S.market.buy[cat]) || 1;
  let p = Math.round(base * clamp(m, 0.85, 1.25));
  if (S.sect && (S.sect.rank || 0) >= 2) p = Math.round(p * 0.95);
  return Math.max(1, p);
}
```

- `tickMarket` 每月同时维护 `buy.mul` 与 `sell.mul`（可反相或独立小幅波动）；
- 新增护栏：遍历 `D.SHOP`，`buyPriceOf(x) > sellPriceOf(x.price, 1)` 必须恒真；
- 材料纳入 `market.mat`，卖出用 `sellMul().mat`，与丹药/符/器一致。

注意：宗门折扣 0.95 仍应保证 `buy > sell`；若 `sell` 用黑市 0.87，则 `buy` 最低 0.95 > 0.87，安全。

#### 4.3.8 四艺经济定位（M2）

先明确设计定位：

> **"买料→制作→卖"应接近打平或略亏；"采集→制作→卖"应有正毛利。**

当前数据其实符合这个定位（回春丹采集成本 0 → 卖 30 是赚的），问题在于：

1. 采集文案说"占一月"、实际一旬，玩家低估采集效率；
2. 买料流派亏损过大（生肌续骨丹 −576），缺中间档；
3. 宗门收购价 0.70 偏低，四艺缺稳定出口。

建议：

| 调整 | 数值 | 依据 |
|---|---|---|
| 采集/制作文案 | "占一旬"（与实现一致） | 3 旬/月的行动预算；一月可做 3 炉是合理的手作节奏 |
| 中阶配方材料成本 | 下调 15%~25%，或产物表价上调至材料成本 × 1.0 附近 | 买料制作亏损收窄到 −10% 以内，保留"采集更赚"的差异 |
| 宗门收购 | `sect.mul` 0.70 → 0.80，保留两成折贡献 | 给四艺一个稳定、无风险出口 |
| 宗门交付 | 贡献 +20%（90→108 / 120→144 / 600→720 / 400→480） | 与"交成品换贡献"的设计承诺一致 |

依据：星露谷/修仙模拟器的产业链都是"采集免费、买料贵、成品有稳定收购价"，而不是让买料制作稳亏。

### 6.1 现状


| 买入>回收 | `buyPriceOf > sellPriceOf` 恒真 | 延续 v10.3 无套利修复；行情双向波动才有策略 |
| 坊市不关窗 | 局部刷新列表/余额 | 星露谷/太吾商店的连续购买体验；庙市已是此范式 |
| 能力三分 | 神通/术法/修炼功法 + `role` 字段 | 鬼谷八荒（心法/武技/绝技/身法）、太吾绘卷（内功/身法/绝技） |
| 神通配置化 | `SHENTONG_GRANT.fromRealm` | 当前 3 保持现状，后续改 2 即"筑基起赋予" |

参考原则说明（不引用具体未公开数值）：

- **绝对数值成长 + 百分比结算**：成熟修仙游戏普遍让气血/灵力随境界跨数量级成长，同时用比例减伤/百分比伤害避免"数值膨胀后互秒"。
- **能力三分**：修炼类（心法/内功）决定成长与上限，杀伐类（武技/绝技/术法）决定输出，天赋类（神通/先天气运）由道基/出身赋予，三者获取途径与 UI 分开。
- **交易闭环**：买入价高于回收价、行情双向、每月限件、商店不关窗，是防止无风险套利与提升购买体验的常见组合。
- **意图可见**：战斗中的位格差、重伤惩罚、持续状态必须在面板可见，避免"隐性惩罚"。
