## 一、结论与本轮决策

四条抱怨，实测下来全部成立，而且根因不是"样式不好看"，是**三处结构性错配**：

| 抱怨 | 实测根因 | 性质 |
|---|---|---|
| 战斗页上下翻页太难用、左右是空的 | 行动区在页面最底部（`.dockrow` 通栏），而 `.stage-fight` 把最大宽度压到 1020px，宽屏两侧各空 400px+ | 布局错配：把最需要常驻的东西放在了最远的地方 |
| 坊市能批量、四艺不能 | 坊市买完**不关窗**（v10.5 E5），连点即可；采集/炼制每次都 `closeModal()` 并弹收获窗，下次要点回 4~6 下 | 交互错配：同一种"重复劳动"两套成本 |
| 主界面难看、中间选项太占位 | 中栏估算高度 **867px**，可视区只有约 **802px**（1440×900 笔记本）——第一屏放不下，而"近期纪事"在 867px 之后 | 预算错配：把一屏装不下的东西按顺序堆 |
| 日志要放中间、要分类 | 纪事本来就在中栏，但永远在屏外；且 `S.log` 是**唯一一条全局流**，没有类别字段 | 信息错配：位置对，可达性为零 |

顺带查出四个真 bug（第五、六节），其中两个是"点了没反应/跳回顶部"级别：

1. **战斗中键盘全废**：唯一的 `keydown` 监听里有 `if (typing \|\| S.phase !== 'play' \|\| modals.innerHTML) return;`，而战斗中 `S.phase === 'combat'` —— 按钮上印着 1~6，按下去没有任何反应。
2. **每次重绘丢掉栏内滚动位置**：左右栏 `overflow-y:auto` 的 DOM 每次 `render()` 都被 `stage.innerHTML` 整个换掉，滚动位置归零。右栏状态看到一半，点个动作就跳回顶部。
3. **战况混入非战斗条目**：`renderCombat` 取 `S.log.slice(0,4)`，是全局日志；破境、事件、采集也会进来。
4. **战斗动作无上限追加**：`fightRowsHooks` 让本命与灵兽直接 `concat` 进同一个网格，7 基础项 + 最多 5 扩展 = 12 项 = 6 行。v10.7 方案 §4.5 写的"放入固定区域，避免无限制向下追加"，实现时没有落地。

**本轮决策**：
- 战斗页改**三栏**（左敌 / 中我+战况 / 右行动），行动常驻右栏不滚动；
- 主界面中栏改**分页工作区**（行事 / 纪事 / 账目 / 道基），并把插画横幅提到三栏之外，中栏从 867px 压到约 470px；
- 日志加**类别字段 + 筛选**，靠"热点显式标注 + 关键词兜底"覆盖，不逐条改 342 个调用点；
- 采集/炼制/坊市统一成**批量操作**，同一套执行器、同一套中止条件、同一套可复现口径。

**不做的**：不重写战斗引擎、不改任何数值平衡、不做主题皮肤/暗色、不引入前端框架、不动存档结构（只给日志条目加一个向后兼容的 `cat`）。

## 二、现状审查（以 2026-11-21 代码为准）

### 2.1 主界面：中栏 867px，可视区 802px

按 `renderMainCol()` 的渲染顺序逐块估算（1440×900 笔记本，顶栏 58px + stage 上下 padding 40px）：

| 顺序 | 块 | 来源 | 估算高 |
|---|---|---|---|
| 1 | 场景插画 | `renderSceneArt()` → `.sceneart--banner` 190px | 190 |
| 2 | 境界条 | `renderRealmBar()` | ~34 |
| 3 | 气血/灵力/灵石/寿元 | `renderVitals()` 一行四格 | ~44 |
| 4 | 道途目标 | `renderGoalCard()` 单行 | ~40 |
| 5 | 场景句 | `.scene` 一句 | ~54 |
| 6 | 旬数条 | `renderXunBar()` | ~38 |
| 7 | **五项主行动** | `<ul class="opts">`，每项 `.opt` = 11px×2 padding + 27px 键 + 7px×2 margin | **~295** |
| 8 | 自由输入 | `.freebar` | ~44 |
| 9 | 提示句 | `.hint` | ~22 |
| 10 | 道基 / 术法 / 神通 | 三条 `.slotline` | ~84 |
| 11 | 已习功法 | 条件渲染 | ~22 |
| | **合计** | | **~867** |

**结论**：首屏差约 65px 才能看到"自由输入"，差约 400px 才看到纪事与月账。玩家的实际体验是——点完 A/B/C/D/E 就要往下滚，而滚动之后插画与境界条全部离屏。这就是"中间选项太占位置"的量化来源：**选项本身 295px 只占 34%，真正的挤压来自 190px 插画 + 225px 的零碎条块**。

顺带注意：`renderChronCol()` 被拼在 `renderMainCol()` 之后，同一个 `.col-main` 里。所以"日志在中间"这件事**结构上早就是对的**，只是永远在屏外。

### 2.2 战斗页：行动区在 870px 处，而可视区 802px

`renderCombat()` 返回三段：敌方 `.col`、我方 `.col`、`.dockrow`（行动 + 战况）。CSS：

```css
.stage.stage-fight{ grid-template-columns: minmax(0,1fr) minmax(0,1fr); max-width:1020px; }
```

| 项 | 估算 |
|---|---|
| 战斗横幅 `.sceneart--combat` 120px（`grid-column:1/-1`） | 120 |
| 敌方卡（名 / 境界 / 气血 / 战力 / 状态 / 意图 / 相克 / 提示） | 260~300 |
| 我方卡（气血 / 灵力 / 道基 / 术法 / 神通 / 法宝 / 状态） | 200~220 |
| **行动区**：基础 7 项（攻术御息器遁谋）+ 扩展最多 5 项（兽令 3 + 本命 1~2）= 12 项，2 列 6 行 × 52 + 表头 40 | **~350** |
| 战况 4 条 | ~100 |
| **合计** | **~870** |

于是必然发生：**要选招就得往下滚，滚下去敌方卡（含"下回合意图"）就出屏**。而敌人意图正是 v10.7 阶段三刚做出来的东西——做出来了，但看不见。

宽度侧：`max-width:1020px` 在 1920 屏上居中，左右各空 **450px**，且战斗页不再挂载左导航（`stage-fight` 只有三个子元素），那 900px 就是纯白。

### 2.3 批量：坊市 1 击，采集 4 击，炼制 6 击

| 操作 | 首次点击链 | 重复一次 |
|---|---|---|
| 坊市买 1 份材料 | 坊市 → 材料页 → 点条目 | **1 击**（`do_buy` 只 `refreshShop()`，弹窗不关，列表原地刷新，见 v10.5 E5 注释） |
| 采集 1 旬 | 四艺 → 采集 → 选地点 → 关收获窗 | **4 击** |
| 炼制 1 炉 | 四艺 → 配方 → 配方卡 → 选火候 → 关收获窗 | **6 击**（`do_craftgo` 结尾只有 `maybeEvent()+render()`，**不重开配方面板**，直接回主界面） |

这就是用户"为什么坊市能批量、四艺不能"的真相：坊市不是有批量功能，而是**它把"再来一次"的成本压到了 1 击**。四艺要做的是同一件事，不需要发明新概念。

代码位置：`ACT.do_gather` 第 11993 行起（开头 `closeModal()`）；`ACT.do_craftgo` 第 12265 行起（开头 `closeModal()`，结尾 `render()`）。

### 2.4 日志：一条全局流，没有类别

`logLine(txt, cls)` 只写 `{t, txt, cls}`。`game.js` 有 273 处调用，十个扩展另有约 69 处。`cls` 只有 `good / danger / ''` 三个值（颜色），**表达不了"这是战事还是经营"**。

三处消费方各取所需，但都只能按时间截断：

| 消费方 | 取法 | 问题 |
|---|---|---|
| 中栏纪事 | `S.log.slice(0,7)` | 7 条混装，找"上次拍卖什么时候"要翻 |
| 战斗战况 | `S.log.slice(0,4)` | 混入非战斗条目 |
| 年谱面板 | `S.chronicle` 分页 60 条 | 同上，且无筛选 |

### 2.5 全项目通用问题（顺手查到）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| A | 战斗中键盘直选失效 | `keydown` 唯一监听：`if (typing \|\| S.phase !== 'play' \|\| …) return;` | 按钮印着 1~6，按了没反应——"假承诺"，本作最忌讳的一类 |

## 三、目标与非目标

**目标（可验收）**

1. 1440×900 下，战斗页**不滚动**即可同时看到：敌方气血与下回合意图、我方气血与灵力、全部基础行动。
2. 1440×900 下，主界面首屏**不滚动**即可看到主行动与最近 3 条纪事。
3. 炼制 N 炉的点击次数从 `6N` 降到 `3 + 0`（N ≤ 上限内）。
4. 纪事可按类别筛选，任一类别命中率可测。
5. 战斗中数字键 1~9 与按钮一一对应，且"按钮顺序"只有一个真源。

**非目标**

- 不改战斗数值、掉落、成功率、经济曲线（批量必须与逐次等价，见 6.4）。
- 不做第二套布局系统、不引入 CSS 框架、不加暗色主题。
- 不改 `S` 的既有字段语义；只给日志条目新增可选 `cat`（旧档读入为 `undefined`，归"杂记"）。
- 不动移动端底部五项导航（v10.7 刚定）。

## 四、战斗页：左敌 / 中我 / 右行动

### 4.1 目标结构

```text
┌──────────────────── 顶栏 ────────────────────┐
│ ┌──────────┐ ┌──────────────────┐ ┌────────┐ │
│ │  敌方     │ │  战况（本场）      │ │  行动   │ │
│ │ 名 / 境界  │ │  第3回合 你出焚山掌 │ │ 攻 术   │ │
│ │ 气血 ▓▓▓░ │ │  敌灼烧 12        │ │ 御 息   │ │
│ │ 战力 350  │ │  敌蓄力·离火剑     │ │ 器 遁   │ │
│ │ 状态 …    │ │  …（独立滚动）     │ │ 谋      │ │
│ │ ──────── │ │                  │ │ ──────  │ │
│ │ 意图：重击 │ │                  │ │ 外物     │ │
│ │ 可用：雷符 │ │                  │ │ 兽攻 兽护 │ │
│ └──────────┘ │                  │ │ 本命     │ │
│              │ ┌──────────────┐ │ └────────┘ │
│              │ │ 我方 气血/灵力 │ │            │
│              │ └──────────────┘ │            │
└──────────────────────────────────────────────┘
```

> 说明：敌方与我方分居左右两端，中间是被浪费掉的宽度里最该放的东西——**战况**。行动独占右栏，`position:sticky` 常驻，永远不随滚动消失。

### 4.2 栅格与宽度

```css
/* 拟改动：问道长生v6.html */
.stage.stage-fight{
  grid-template-columns: 320px minmax(0,1fr) 368px;
  max-width:1480px;              /* 原 1020 → 吃掉宽屏两侧空白 */
  gap:14px;
  align-items:start;
}
```

- 左 320：敌方卡。340 以下放不下"状态 + 相克 + 意图"三行，会挤成两行换行。
- 中 弹性：我方卡（上）+ 战况（下，`flex:1`，`min-height:140px`，独立滚动）。
- 右 368：行动。2 列 × 每列 176px，够放"攻 / 必中约 37%"两行。

### 4.3 行动区：基础固定 + 扩展分组

问题 D 的解法不是压缩按钮，而是**给扩展项一个属于自己的组**：

| 组 | 内容 | 来源 | 上限 |
|---|---|---|---|
| 基础 | 攻 / 术 / 御 / 息 / 器 / 遁 / 谋 | `renderCombat` 内联 7 项 | 固定 7 |
| 外物 | 令兽攻 / 令兽护 / 令兽显化 / 本命法技 | `fightRowsHooks` | **硬上限 4**，超出折叠为「其余 N 项」 |

- 基础 7 项 2 列 4 行 ≈ 220px；外物最多 4 项 2 行 ≈ 110px；合计 330px + 表头 40 + 战况 140 = 510px < 802 ✓
- `fightRowsHooks` 返回值超过 4 条时，只渲染前 3 条 + 「其余 N 项」一行，点开进侧滑面板。**这是硬约束，写进断言**：`fightRowsHooks` 拼接后总行数 ≤ 11。

### 4.4 单一真源：`combatActionList(c)`

现状：行动项的数组 `o` 在 `renderCombat` 内部就地拼装，键盘完全拿不到。方案是把"有哪些动作、是否可用、按什么顺序"抽成一个纯函数：

```js
/* 拟新增（game.js）：只产出数据，不产出 HTML */
function combatActionList(c) {
  // → [{ id:'attack', key:'1', txt:'攻', tag:{…}, note:'…', act:'do;cbt:attack', dis:false, grp:'base' }, …]
}
```

- `renderCombat` 只负责把数组转成 `<li>`；
- `combatKeyAction(k)` 按 `key` 在数组里找同一条并 `dispatch(act)`；
- 以后加动作只改一个地方，**不会再出现"加了按钮没加键"**。

这一条同时修掉 bug A（战斗键盘失效）：`keydown` 的守卫从 `S.phase !== 'play'` 改成 `['play','combat'].indexOf(S.phase) < 0`，并按阶段分派到 `mainKeyAction` 或 `combatKeyAction`。

### 4.5 战况：本场日志，不再借全局

修 bug C 的零成本做法（不改 342 个 `logLine` 调用）：给日志条目加自增序号，战斗开始时记下起点。

```js
/* logLine 内两行 */
S.logSeq = (S.logSeq || 0) + 1;
S.log.unshift({ t: timeLine(), txt, cls: cls || '', seq: S.logSeq, cat: cat || guessCat(txt, cls) });

/* startCombat 内一行 */
c.logFrom = S.logSeq;

/* renderCombat 取战况 */
const fl = (S.log || []).filter(l => l.seq > (c.logFrom || 0)).slice(0, 6).reverse();
```

- 战况显示改为 **6 条**并独立滚动（右/中栏底部），可点「本场全部」看完整场次。
- 旧档 `seq` 为 `undefined` → `undefined > n` 为 false → 老条目自然不进战况，符合预期。

### 4.6 响应式三档

| 宽度 | 布局 | 行动区位置 |
|---|---|---|
| ≥1200px | 320 / 1fr / 368 三栏 | 右栏 sticky，可见即用 |
| 880~1199px | 左敌 + 中我（两栏，撤掉中栏战况，战况折叠进"战况"按钮） | **底部 sticky 行动条**，2 列最多 6 项 + 「更多」 |
| <880px | 单列：敌 → 我 → 战况 | **底部固定行动条**（两行高，`position:fixed`），上滑展开全屏行动面板 |

窄屏要点：

- 战斗页目前不渲染 `.navmob`（`render()` 在 combat 分支直接 return），所以底部空间是干净的，不会和五项导航打架——**这一点必须在实施时保持**，否则行动条会被导航压住。
- `.stage-fight` 在窄屏要给 `padding-bottom` 预留行动条高度（约 132px），否则战况最后一条被遮住。

### 4.7 验收

- 1440×900、1280×800、390×844 三个尺寸截图，均满足：敌方气血、敌方意图、我方气血、全部基础行动在首屏内。
- `combatActionList` 存在且 `renderCombat` 与 `combatKeyAction` 都读它（断言：改数组顺序后键盘与按钮顺序同步）。
- 战斗中按 1~9 与点击对应按钮产生**完全相同**的 `dispatch` 参数（断言遍历全部动作）。
- `fightRowsHooks` 合计行数 ≤ 11（断言）。

## 五、主界面：中栏分页工作区 + 中栏固定

### 5.1 高度预算：把 867 拆成 470

| 处理 | 省下 | 做法 |
|---|---|---|
| 插画横幅移出中栏 → 三栏之上通栏 | **190 → 0**（中栏内） | `render()` 里 banner 提到 `<div class="col-main">` 之外，`grid-column:1/-1`，高度 190 → **132** |
| 气血/灵力/灵石/寿元 叠到横幅底边 | **44** | `.vitals` 绝对定位于 banner 下沿，半透明纸底 |
| 道基 / 术法 / 神通三行 + 已习 → 移入「道基」页 | **106** | 本来就是状态，不是行动 |
| 五项主行动改紧凑网格 | **295 → 190** | `.opt` padding 11→8，键 27→22，margin 7→4；五项改 2 列（末项通栏）→ 3 行 |
| 提示句并入自由输入行右侧小字 | **22** | 同一行 |
| **中栏合计** | **867 → 约 470** | 一屏余 330px 给纪事薄条 |

> 关键取舍：**横幅不删，改成通栏**。删掉会丢这个项目最花力气的插画层（33 张 JPEG），而通栏之后三栏都变宽了，实际观感是"画变大了、中栏变清爽了"。

### 5.2 分页工作区

```text
中栏 = ┌ Tab 条（sticky）：行事 │ 纪事 │ 账目 │ 道基 ─────────┐
       │                                                  │
       │ 内容区（固定高度，内部滚动）                        │
       │                                                  │
       └──────────────────────────────────────────────────┘
       底部薄条：最近 3 条纪事 · 分类 chips · 展开 ›
```

| Tab | 内容 | 说明 |
|---|---|---|
| **行事** | 场景句 + 旬条 + 主行动（2 列）+ 自由输入 | 默认页，v10.7 的现状减去横幅/道基/提示 |
| **纪事** | 6~8 条 + 分类 chips + 「全部 ›」 | 原 `renderChronCol` 的纪事部分 |
| **账目** | `renderLedger()` 本月收支 + 明细入口 | 原挤在纪事面板底部 |
| **道基** | 道基 / 术法 / 神通 / 已习功法 / 上限说明 | 原中栏底部三行 |

- Tab 状态存内存（`let _mainTab = 'act'`），**不写档**——读档后回到"行事"，与 `SG_OPEN` 同一惯例。
- Tab 条 `position:sticky; top:0` 在栏内吸顶（注意 4.5 提到的老坑：`.stage>*` 的 `position:relative` 会把 sticky 压成 relative，新规则必须写在它**之后**）。

### 5.3 "中栏固定"怎么做

用户的原话是"如果中间是一页这种，那左右上下滑动时中间可以固定"。落到实现，指的是**中栏不要跟着页面一起滚**。两个层次：

**A. 低风险版（建议先做）**
不给中栏固定高度，只做 5.1 的高度压缩 + 5.2 的分页。中栏 470px 一屏放得下，页面几乎不用滚，"固定"问题自然消失。

**B. 应用外壳版（可选，P2）**
三栏都 `position:sticky; top:58px; height:calc(100dvh - 72px)`，各自内部滚动，页面本身不滚：

```css
.stage>.col-main{
  position:sticky; top:58px;
  height:calc(100dvh - 72px);
  display:flex; flex-direction:column;
}
.stage>.col-main>.tabbar{flex:0 0 auto}
.stage>.col-main>.tabbody{flex:1 1 auto; overflow-y:auto; overscroll-behavior:contain}
@supports not (height:100dvh){ .stage>.col-main{height:calc(100vh - 72px)} }
```

- 好处：切 Tab、翻纪事，左右栏与页头纹丝不动，这就是用户想要的"固定"。
- 风险：三栏独立滚动会让"滚到哪一栏都看不清全貌"（v10.7 方案 §4.3 明确否过一次）。所以放在 P2，且**只在 ≥1200px 生效**，中栏内容短于容器时 `height:auto` 退回文档流。
- 必须先修 bug B（滚动位置保持），否则 sticky + 内部滚动 + 每次重绘归零，体验比现在更差。

### 5.4 验收

- 1440×900 首屏可见：五个主行动、自由输入、至少 3 条纪事。
- 390×844 首屏可见：横幅、气血/灵力、五个主行动（不含纪事）。
- 切 Tab 后左右栏位置不动（B 版验收）。
- 中栏内容 < 容器时可正常回落，不出现大片空白。

## 六、批量操作：一套执行器，三处接入

### 6.1 共同口径（先定死，再写代码）

| 口径 | 规定 |
|---|---|
| 时间 | 每单位占 1 旬，沿用 `advanceXun(1)`；不新造时间单位 |
| 随机 | **每单位独立掷骰**，禁止"一次掷骰 ×N"；同 seed 下批量 N 与手动 N 次结果必须逐条相同 |
| 中止 | `S.phase !== 'play'` / `modalBusy()` / `S.pendingEnc` / 资源不足 / 死亡 —— 任一命中即停，并如实报「第 k 次中止，原因…」 |
| 汇总 | 只弹**一次**结果窗，列清每次的成败与总账；不逐次弹窗 |
| 上限 | 采集 ≤ 本月剩余旬数（含跨月则 ≤ 3）；炼制 ≤ min(材料可做数, 12)；坊市 ≤ 可负担数 |
| 记忆 | 上次选的批量数存 `S.batchN`（与存档兼容，缺省 1） |

### 6.2 执行器

```js
/* 拟新增（game.js）：唯一的批量跑法 */
function runBatch(n, step, opts) {
  // step(i) → { ok:bool, msg:string, stop:false }
  // 返回 { done, stopped, why, results:[] }
}
```

- `ACT.cultivate`（打坐到月末）与 `ACT.do_med`（闭关 N 年）**已有各自的循环**，本轮不强行合并（它们的"单位"是整月，语义不同），但要把中止条件补齐到同一套（现在 `do_med` 有 `lifeMax*0.9` 与 `collapse` 两条，`cultivate` 没有）。
- 新接入的三处统一走 `runBatch`。

### 6.3 三处接入

**① 坊市：数量段控（最省事、收益最大）**

```text
坊市 · 灵石 12,400        [买 1] [买 5] [买 10] [买满]
─────────────────────────────────────────────
补气草   黄阶 · 60 石 · 已有 3      → 点一下买 5 份
```

- 段控放在 `.shop-tools` 里，与"搜索 / 价格排序"同一行；
- 点击条目按当前档位买；余额不足**自动降到可买数**并提示「已买到上限 3 份」；
- 记 1 笔账（不是 N 笔），label 写「补气草 ×5」；
- 法器、功法、术法、灵脉契**强制 ×1**（购买唯一性，v10.5 P0·E6 的约束不能破）。

**② 采集：一次 N 旬**

```text
采集 · 占一旬        [1 旬] [2 旬] [坐满本月]
────────────────────────────────
溪畔   灵草 · 2~4 份 · 可能出 补气草/蓝幽草
```

- `do;gather:<spot>:<n>`；n 缺省 1（旧链接全部继续有效）；
- 每旬独立掷材料数量与稀有判定，材料累加；
- 只有**一次** `maybeEvent()`（与 `ACT.cultivate` 一致：批量只掷一次外界事件），并在结果文案里写明「期间外界之事，一并略过」；
- 结果窗底部给「再来一旬」，不用退回四艺。

**③ 炼制：一次 N 炉**

```text
制作 · 回春丹            [1 炉] [3 炉] [5 炉] [做满]
────────────────────────────────
文火慢炼  87% · 品相不变
武火猛攻  62% · 上品/极品翻倍 · 炸炉更狠
稳守中火  72% · 不赚不亏
```

- `do;craftgo:<id>:<mode>:<n>`；火候一次选定，作用于全部 N 炉；
- 每炉独立扣料、独立判成败、独立结算炸炉（气血/道心/残料回收）——**不许把炸炉惩罚只算一次**；
- 材料在第 k 炉不足时停下，报「第 k 炉料尽」；
- 结果窗：成败各几炉、产出清单（按品相汇总）、总料钱与总净利，底部「再来 3 炉」。

### 6.4 可复现验收（这是本方案最硬的一条）

```js
// 同 seed 下：
setSeed(20261121); 三次手动采集; 记录 sequence A
setSeed(20261121); 一次批量采集(3); 记录 sequence B
assert deepEqual(A, B)
```

炼制同理（`n=5`，含一次人为触发炸炉的 seed）。**批量不许改变期望值，只许减少点击。** 若这条断言过不了，批量就是"偷偷改数值"，一律退回。

### 6.5 验收

- 炼制 5 炉：点击 4 次（四艺→配方→卡→火候段控）以内完成，含结果窗。
- 采集 3 旬：点击 3 次以内。
- 上面 6.4 的两条 deepEqual 断言。
- 中止路径三个都要有测试：料尽、炸炉致死（hp=1 时武火）、途中进战斗（`S.phase` 变化）。

## 十二、待你拍板的两处（已定，见落地记录）

1. **横幅要不要提为通栏**（5.1）。提了中栏才降到 470；不提就要把 190 压到 100 并接受画面变小。我建议提。
   → **已按建议实施**（P1）：通栏 132px，气血叠底。
2. **"中间固定"做到哪一档**（5.3）。A 版（压缩+分页，页面照常滚）风险低；B 版（三栏各自滚动，页面不滚）就是你说的"固定"，但要先修滚动保持，且只在 ≥1200 生效。我建议先 A 后 B。
   → **A 已随 P1 落地，B 随 P2 落地**：`max-height` 而非 `height`，内容短于一屏时自动回落文档流。
