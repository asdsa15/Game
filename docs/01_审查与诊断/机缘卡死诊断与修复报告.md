# 机缘弹窗卡死 · 诊断与修复报告

日期：2026-11-08
对象：`wxcs3-game.js`（3,417 行）／`wxcs3-data.js`（65,639 字节）
现象：**弹出「机缘」面板后，三个选项全部点不动，且没有关闭按钮，只能刷新页面**
状态：**已修复并重建产物**（dist 与 D:\wendao-apk 均已更新，versionCode 624）

---

## 一、结论（一句话）

新加的奇遇系统把选项动作写成了 `enc:<事件>:<选择>`，而点击分发器 `dispatch()` **只认 `do;`、`act:` 等 13 种前缀，没有 `enc:`**；再加上弹窗是"无关闭按钮"模式、分发器末尾又没有兜底提示——三者叠加，就成了**点了完全没反应、也退不出去**的死锁。

不是卡顿，不是性能问题，是**一次纯粹的路由缺失**。

---

## 二、现象与复现

### 2.1 你看到的

```
推进一月 → 弹出「机缘 · 崖边老者」
         → 三个选项（上前问路 / 绕道而行 / 递上半块饼）
         → 点任何一个：没有反应，没有提示
         → 找关闭按钮：没有（这个弹窗是故意不给关闭的）
         → 只能 F5 刷新
```

### 2.2 精确复现路径（代码级）

| 步 | 发生什么 | 位置 |
|---|---|---|
| 1 | 每次行动推进一月，`maybeEvent()` 先掷奇遇 | 3117 |
| 2 | `tryEncounter(false)`：`rnd100() > 18` 才放弃 → **18% 概率触发** | 2618 |
| 3 | 命中后 `openEncounter(e)` → `openModal(title, body, true)` | 2639 |
| 4 | 第三个参数 `true` = **不渲染关闭按钮** | 2584 |
| 5 | 玩家点选项，`data-act="enc:oldman:ask"` → `dispatch()` | — |
| 6 | `dispatch` 里 13 个 `startsWith` 全不匹配，函数直接返回 | 2601~2660 |
| 7 | 弹窗还在，选项无效，无关闭按钮 → **死锁** | — |

18% 的触发率意味着：**平均每 5~6 次行动就会撞上一次**。你说"刚弹出机缘就卡死"，正是这个概率下的必然结果。

## 三、根因：三处叠加，缺一不会死锁

| # | 位置 | 事实 | 单独存在时的后果 |
|---|---|---|---|
| **①** | `wxcs3-data.js` 第 352 行起 | 全部 30 个奇遇选项写成 `act: 'enc:oldman:ask'`，**没有 `do;` 前缀** | 点击无反应 |
| **②** | `wxcs3-game.js` `dispatch()` | 只处理 `act:` / `do;` / `modal:` / `cv:` / `gender:` / `fx:` / `origin:` / `path:` / `root:` / `el:` / `body:` / `tal:` / `st:` 共 13 种，**没有 `enc:`** | 点击无反应 |
| **③** | `dispatch()` 末尾 | **没有 else 兜底**，不认识的动作静默丢弃，连 toast 都没有 | 玩家无从判断点没点上 |
| **④** | `openEncounter()` | `openModal(..., true)` 第三参数为真 → 不渲染关闭按钮 | 无法退出 |

**为什么说"缺一不会死锁"**：

- 如果只有 ①②：玩家点了没反应，但还能点右上角关闭、或按遮罩关闭 → 只是迷惑，不是死锁
- 如果 ③ 有兜底：至少会弹「无此指令」提示，玩家知道是 bug 而不是自己没点上
- 如果 ④ 给了关闭按钮：玩家能退出，损失一步而已

**三者同时成立，才变成"只能刷新"的死局。**

## 五、影响面（含一处你没察觉的二次伤害）

### 5.1 直接损失

- **12 个奇遇 × 平均 3 个选项 = 30 个选项全部失效**
- 触发率 18%/次行动 → 平均 5~6 步就撞一次

### 5.2 二次伤害：卡死过的存档会让奇遇**永久不再出现**

这一点比死锁本身更麻烦，必须单独说：

```js
// 2631  打开奇遇时打标记
S.pendingEnc = e.id;

// 3119  掷奇遇前检查
if (S.phase === 'play' && !S.pendingEnc && tryEncounter(false)) return;
```

`pendingEnc` 只在 `do_enc()` 开头被清空（2648）。但因为死锁，`do_enc` **永远执行不到**。

于是：

1. 弹窗卡死 → 600ms 后自动存档触发 → `pendingEnc: 'oldman'` 被写进 localStorage
2. 你刷新页面 → 从存档恢复 → `pendingEnc` 还是 `'oldman'`
3. 此后每次 `maybeEvent()` 里 `!S.pendingEnc` 恒为 `false` → **奇遇再也不会触发**

**换句话说：卡死一次并刷新，奇遇系统就对你永久关闭了。** 这解释了为什么有些人"更新后玩了几步就再没见过机缘"。

## 六、修复（3 处，已应用）

### 6.1 给 `dispatch` 加 `enc:` 分支

```js
function dispatch(act) {
  if (!act) return;
  syncInputs();
  // 奇遇／机缘：data.js 里写作 enc:<事件id>:<选项>，没有 do; 前缀
  if (act.startsWith('enc:')) {
    const p = act.split(':');
    if (ACT.do_enc) ACT.do_enc(p[1], p[2]);
    return;
  }
  if (act.startsWith('act:')) { ... }
```

`enc:oldman:ask` → `p = ['enc','oldman','ask']` → `ACT.do_enc('oldman','ask')`，
与原有的 `do;enc:oldman:ask` 路径完全等价（`do_enc` 内部本就按 `id:sub` 拆分）。

### 6.2 给 `dispatch` 末尾加兜底

```js
  if (act === 'create-start') { finishCreate(); return; }
  // 兜底：没有任何分支接住这个 act 时，至少给个提示，
  // 避免"点了完全没反应 + 弹窗又无关闭按钮"的静默卡死。
  toast('此选项暂不可用：' + act);
}
```

以后任何新模块忘记接前缀，玩家会看到明确的提示，而不是面对一个装死的界面。

### 6.3 载入存档时清空残留标记

```js
out.anchors = Object.assign({ wu: 1, ren: 1, shi: 1, yi: 1 }, st.anchors || {});
out.anchorMiss = Object.assign({ wu: 0, ren: 0, shi: 0, yi: 0 }, st.anchorMiss || {});
// 奇遇卡死过的存档会残留 pendingEnc，不清掉的话 maybeEvent 里
// `!S.pendingEnc` 恒为假，奇遇系统此后永久不再触发。
out.pendingEnc = null;
```

这条修的是**已经被卡过的老存档**——不加的话，你即使换了新代码，旧存档依然不会出奇遇。

## 八、防呆：把这类问题变成可扫描的

我加了一个脚本 `check_actions.py`（项目根目录）：

```bash
python check_actions.py
```

它做的事：

1. 从 `dispatch()` 源码里抓出所有 `startsWith('...')` 前缀
2. 从 `data.js` 里抓出所有 `act: '...'`
3. 比对，列出"没有对应分发分支"的动作

修复后的输出：

```
dispatch 支持的前缀：act:, body:, cv:, do;, el:, enc:, fx:, gender:, modal:, origin:, path:, root:, st:, tal:
data.js 中可点击动作：30 个

✔ 全部动作都有对应的分发分支
```

如果把这 3 处修复回退，它会报：

```
✘ 以下前缀没有对应的 dispatch 分支（点击会静默失败）：
   enc:  ×30
```

**以后每次给 data.js 加新事件、新选项，跑一次这个脚本，就不会再出现"点了没反应"。**

## 九、为什么这类问题特别难发现

值得记一笔，因为它不是孤例：

1. **代码本身完全合法**——`act: 'enc:x:y'` 是个正常字符串，语法检查、ESLint、人工通读都不会报错
2. **数据与逻辑分居两个文件**——data.js 定义"点什么"，game.js 定义"点了怎么办"，两者靠**字符串约定**连接，没有任何编译期校验
3. **失败是静默的**——`dispatch` 里没有 else，不认识的 act 连日志都不打
4. **弹窗是无出口设计**——强制选择本身是好的交互，但它把"小概率静默失败"放大成了"必然死锁"
5. **测试路径依赖随机数**——18% 概率，自动测试要跑很多次才触发

这和上一次"对战卡死"（`foeTurn` 返回 false 却没 render）是同一类病：**状态机漏了一条出口**。

## 十、附带发现（不影响运行，但值得知道）

### 10.1 奇遇触发率偏高

`tryEncounter` 的阈值是 18%，即**每次行动有近五分之一概率遇到奇遇**。12 个事件轮着出，玩 30 步可能撞 5 次。

这个密度在前期会稀释主线节奏。建议降到 **8%~10%**（数值在 2618 行 `rnd100() > 18`）。要不要改由你定——这不影响正确性。

### 10.2 `noClose` 弹窗缺少"逃生阀"

`openModal(title, body, true)` 的设计是"必须选一个"，逻辑上没错。但配上前面的静默失败就是死锁。

现在加了兜底 toast，最坏情况是"点了弹提示但退不出去"。更稳的做法是给这类弹窗加一个「暂不理会」的兜底项，代价是玩家可以绕过奇遇。

**我倾向于保持现状**：只要选项都能正常工作，强制选择是好的；兜底 toast 已经够用来定位问题。
