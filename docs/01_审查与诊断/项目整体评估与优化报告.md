## 二、五个结构性问题

这一节是本报告的核心。**它们都不是 bug，但每一条都会让后面所有工作打折。**

### 2.1 【最紧急】产物与源码静默分叉

```
源码      21:11  ← 有四艺
dist      19:27  ← 没有四艺（差 1 小时 44 分）
apk       17:41  ← 没有四艺（差 3 小时 30 分）
```

验证方式（直接查功能符号，不靠时间戳）：

| 符号 | 源码 | dist | apk |
|---|---|---|---|
| `ACT.openCraft` | 2 | **0** | **0** |
| `RECIPES` | 6 | **0** | **0** |
| `craftRateOf` | 3 | **0** | **0** |
| `ledgerAdd` | 8 | **0** | **0** |
| `tickMarket` | 2 | **0** | **0** |

**为什么这条最紧急**：你现在双击 `dist/index.html` 或打开手机上的 APK，看到的都是一个**没有四艺的世界**。你可能已经在用"能玩"来判断四艺做得对不对——但你玩的那个版本根本没有四艺。

而且这个偏差**没有任何提示**。构建脚本 `build.py` 不比对源文件时间，`sync_apk.py` 只负责复制。只要你不主动跑，它们就一直是旧的。

**修法（10 分钟，一次性）**：

```python
# mobile/build.py 开头
import os, sys
SRC = ['../wxcs3-game.js', '../wxcs3-data.js', '../问道长生v6.html']
for f in SRC:
    if os.path.getmtime(f) > os.path.getmtime('dist/index.html'):
        print(f'⚠ {f} 比 dist 新，产物已过期'); sys.exit(1)
```

再到 `build.py` 末尾打印源码与产物的 md5 前 8 位，一眼能比。

```

```

**5,473 行代码、8 个设定版本、多次 AI 改写、一次"机缘卡死"事故——全程没有一次提交。**

现有的保护只有：

### 2.3 两份"真相"，已经分叉

项目有两套描述同一个游戏的东西：

| | 设定集 `v6 · 仙道为主.md` | 代码 `v6.3` |
|---|---|---|
| 用途 | 给 AI 当引擎说明书 / 人类读设定 | 真在跑的游戏 |
| 规模 | 2,659 行 / 177 KB | 7,126 行 |
| 仙道六境 / 神道八柱 / 玄鉴道统 / 魔门果位 / 两界 / 锚 | ✅ | ✅ |
| **四艺** | ❌ 0 次 | ✅ 208 配方 |
| **品相 / 熟练度** | ❌ 0 次 | ✅ 五档 / 九级 |
| **行情 / 收支账本** | ❌ 0 次 | ✅ |
| **阵盘** | ❌ 0 次 | ✅ 4 种 |
| **成就** | ❌ 0 次 | ❌ 只有方案 |
| **恩义/钩子** | ❌ 只有 2 处"钩子"字样 | ❌ 只有方案 |

也就是说：**设定集停留在"四艺之前"。**

这带来一个具体的坏处：如果你拿设定集去问 AI"这个游戏四艺怎么玩"，它会告诉你"没有四艺"——因为设定集里真的没有。

**三条路，必须选一条**：

| 方案 | 做法 | 代价 | 适合 |
|---|---|---|---|
| **A. 代码为准，设定集降级为"世界观资料"** | 删掉设定集里所有"你能做什么"的规则段，只留世界/人物/术语 | 低 | 推荐 |
| B. 设定集为准，代码补文档 | 每次改代码同步改 md | 高，会持续腐化 | 不推荐 |
| C. 双轨 | 设定集给 AI 跑文字版，代码是电脑版 | 中，但两份都要维护 | 想两条腿走才选 |

我推荐 **A**。理由：设定集最大的价值不是"规则"，是那 177 KB 里的**世界、术语、人物、门派、道统谱、九十六庙**——这些东西代码里没有，而规则代码里全有。**让设定集做它擅长的事。**

### 2.4 165 MB 小说在项目里

`小说参考/` 10 本 txt 共 165 MB，占项目体积 **97.6%**。

它不影响运行，但影响三件事：

1. 任何备份/同步/压缩都会变慢 100 倍
2. `git init` 之后如果没 ignore，会把 165 MB 塞进仓库
3. 目录 `du -sh` 的结果会让人误判项目规模

而且这 10 本里 `《火星引力作品集》` 54 MB 是**作品合集**，与项目无关（之前审查时已确认跳过）。

**修法**：移到 `D:\参考小说\`（项目外），或用 `.gitignore` 排除 + 目录移到 `../小说参考`。

### 2.5 底部指令坞会无限膨胀

截图里底部是 **10 个按钮**（功法/洞府/坊市/舆图/情缘/历练/法宝/宗门/家族/乾坤袋）。

代码里 `dockItems()` 有 **16 个 `list.push`**，条件满足时最多 **14 个**：再加「四艺」「洞天」「锚」「化道胎」。

但**每加一个新系统，就是加一个按钮**：四艺加进去了，成就要加，恩义要加，释修要加……

在一加 Ace 2（412 px）上，10 个按钮已经占三行；14 个会占**四到五行**，也就是**屏幕下半部分全是按钮**。

这是设计债，不是实现问题。**真正的问题是：所有系统都平等地放在同一层。**

**修法**：分两层。

```
主层（5~6 个，常驻）：修炼 · 历练 · 坊市 · 人物 · 身家 · 系统
      ↓ 点「身家」展开
次层：功法 法宝 乾坤袋 洞府 四艺 · 宗门 家族 锚
```

判断标准很简单：**一个月里你会点超过 3 次的，放主层；其余进次层。**

按这个标准，「乾坤袋」和「舆图」一个月点不到 1 次，但它们现在和「修炼」占同样大的位置。

## 五、体验层评估（基于真实截图）

### 5.1 做得好的地方（真的不错）

我看的是 `_shots/_v63_主界面.png`（1,050 px 宽）。三件事值得说：

**① 中间栏的境界条已经修好了**

之前我提过"境界字太小"。现在中栏顶部是：

```
筑基·中期                       修为 186 / 300
────────────────────────────────────────────
已至此功法所能到的尽头（紫府三关）
```

**17 px 加粗 + 进度条 + 一句"你为什么卡在这"**。这是全屏信息层级最清楚的一处，而且顺手把 `DAOGONG_CAP` 这个抽象规则翻译成了人话。

**② 选项的语义标签很克制**

```
A 打坐采气（推进一月）      〔平和〕 +18 修为
B 闭关快进                  〔平和〕 岁月流逝
C 打坐疗伤                  〔风险〕 轻伤：回 42
```

〔平和〕〔风险〕〔机缘〕是**三个词**，不是十种颜色。这是对的——标签多了等于没有标签。

**③ 状态右栏没有废话**

道号/年龄/境界/战力/主修/道统/神通池/道途印 + 三条进度条。**没有一栏是"为了好看"。**

### 5.2 三个具体问题

**① 中栏下方大片空白**

选项区（A~D）到底部「道基」之间，有约 **140 px 的空白**。在 1080p 屏上这是页面最有价值的位置。

**建议**：把「最近一次结算明细」放这里（`+18 修为 = 基数 10 × 灵气 1.3 × 资质 1.2 × 功阶 1.7 × 状态 0.9`）。

玩家现在只知道"+18"，不知道为什么是 18。**把公式变成可读的一行，比任何数值平衡都有效。**

**② 左栏「天时·纪事」太轻**

只有所在地/时节/道途 + 事件流，字号约 11 px。但它是**唯一记录"发生过什么"的地方**。

**建议**：至少把"道途"（问道飞升）这一行加粗——那是玩家的长期目标，现在和一个地名同样大小。

**③ 底部 10 个按钮，视觉权重完全相同**

「修炼」和「乾坤袋」占一样的格子。而按点击频率，前者是后者的 50 倍。

见 2.5，建议分两层。

### 5.3 移动端

`mobile.css` 138 行补丁都在产物里（`stage-fight` / `safe-area` 等 28 处命中），412 px 下双栏可读。**这块是好的**，只需要随 2.1 一起重建。

| 动作自检 | `check_actions.py` | **这是整个项目最值钱的一个文件** |
| 数据/逻辑分离 | data 79 表 / game 逻辑 | 结构清晰 |

`check_actions.py` 值得单独夸一句：它从 `dispatch` 抓前缀、和 `data.js` 的 `act` 列表比对，直接列出"点了没反应"的动作。**这个思路比任何单元测试都适合这个项目**（因为 bug 都是"接线没接上"，不是"算法算错了"）。

### 6.2 三个风险

**① 没有全局错误兜底**

```js
2760:  r.onerror = function () { toast('读取文件失败'); };
```

这是**FileReader** 的错误处理，不是 `window.onerror`。

意味着：任何一个 render 函数抛异常 → 整个界面冻结，**没有任何提示**。

这正是「机缘卡死」和「对战卡死」两次事故的共同表现。那两次都是靠人肉发现、人肉定位的。

**修法（10 行，收益极高）**：

```js
window.onerror = function (msg, url, line) {
  try {
    var d = document.createElement('div');
    d.style.cssText = 'position:fixed;left:12px;bottom:64px;z-index:99999;' +
      'background:#FBEDE9;border-left:4px solid #C05F55;padding:10px 14px;' +
      'font:12px/1.7 monospace;max-width:70%;white-space:pre-wrap';
    d.textContent = '引擎出错：' + msg + '\n位置：第 ' + line + ' 行\n' +
      '（把这一行发给开发者，或点「系统 → 导出存档」保住进度）';
    document.body.appendChild(d);
    setTimeout(function(){ d.remove(); }, 20000);
  } catch (e) {}
  return false;
};
```

**它不会修 bug，但会让 bug 从"卡死"变成"有话说"。** 对一个玩 300 回合的游戏，这值 10 个小时的排查时间。

**② 版本号三处不一致**

| 位置 | 值 |
|---|---|
| 页面标题 | v6.2 |
| 目录名 | 03_v6.2_仙道为主 |
| 存档 `envelope.version` | `'6.2'` |
| **实际功能** | **v6.3+（四艺）** |

存档版本号尤其重要——`checkSaveVersion` 靠它判断兼容性。如果将来真的升到 6.3、加了不兼容字段，**版本号还是 6.2 会导致旧档被误判为兼容，然后崩**。

**修法**：在 `game.js` 顶部定义一个常量，全项目只读它。

```js
const VER = '6.3';
// 标题、envelope、导出文件名、关于面板全部引用 VER
```

**③ 单文件 5,473 行**

现在还能维护（有 `check_actions.py` 兜底），但已经出现"改一个数值要跨三个系统读代码"：

改战斗数值要看 `computePower`(433) → `positionRank`(478) → `keMul` → `artBonus` → `resonResult` → `foeTurn`(4359) → `do_cbt`(4401)。

**建议（不是现在做）**：按域拆 5 个文件，`window` 挂载，不引入打包器：

```
js/core.js       状态 / 存档 / 时间 / 日志   ~800 行
js/cultivate.js  修炼 / 破境 / 功法 / 神通   ~900 行
js/combat.js     战斗 / 招式 / 敌人          ~700 行
js/world.js      奇遇 / NPC / 宗门家族 / 四艺 ~1,600 行
js/ui.js         渲染 / 面板                ~1,500 行
```

`build.py` 只需多内联几个 `<script>`。**这是唯一能阻止它变成 8,000 行的办法。**

## 八、如果只做三件事

假设时间只够做三件，我选这三个：

### ① `git init`（5 分钟）

不是因为它"规范"，是因为**这个项目已经在裸奔**。三份重复文件、一个时间戳备份、8 个设定版本——这套东西的风险不在今天，在"下次误覆盖"。

### ② 重建产物 + 接卖出渠道（半天）

**这两件事必须一起做。** 只重建，四艺能玩但赚不到钱；只接渠道，玩家玩的是没有四艺的版本。

做完之后，你第一次能真的回答一个问题：**"这游戏的钱能转起来吗？"**

而这个答案会决定后面所有设计——如果转不起来，做成就和恩义都是在沙上盖楼。

### ③ 加全局错误兜底（10 分钟）

这个项目已经被"静默失败"坑了四次：

| 事故 | 表现 |
|---|---|
| `foeTurn` 返回 false 不 render | 战斗卡死 |
| `dispatch` 不认 `enc:` | 机缘卡死，且永久不再触发 |
| `S.ownedGongfa` 无兜底 | 旧档一买功法就冻结 |
| `'火' === 'fire'` | 加成永不生效，无人发现 |

**四次里有三次是"玩家先发现，开发者后知道"。** 加 10 行 `window.onerror`，让下一次失败至少会自己说话。

## 九、几句不太好听但该说的

**① 这个项目的瓶颈已经不是"功能不够"，是"接线不牢"。**

79 张数据表里 11 张零引用，7 个系统半成品，1 个做完的玩不到——**这些都不是设计问题，是最后一米没走完。**

再加 3 个新系统（成就、恩义、释修）会让它看起来更丰富，也会让"没接上的东西"从 7 项变成 10 项。

**建议：下一轮不要新开系统，先把现有的接上。**

**② 设定集和代码必须有一个降级。**

现在两份都是"部分真相"。人类读设定集会以为没有四艺，AI 读设定集会给出错误规则，开发者读代码会以为设定集还有效。

三份都错一点，比一份错全部更难维护。

**③ 这个项目最值钱的资产不是代码，也不是设定。**

是 `docs/01_审查与诊断/` 那 5 份、共 106 KB 的事故记录——`foeTurn` 为什么卡死、`enc:` 前缀为什么漏、`ownedGongfa` 为什么会崩档。

**这些东西下次重写时能省一半时间**，而代码和设定都会被重写。

建议给 `docs/01_` 加一个 `00_事故模式总结.md`，把四次的共同形态抽出来：

> **改了枚举值，没改所有比较点。**
> **记录存在，结算不存在。**
> **状态机漏一条出口，且失败是静默的。**
