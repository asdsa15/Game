# Electron 打包后的两个问题：更新方不方便、源码看不看得到

> 日期：2026-11-18
> 性质：**方案稿，未修改任何代码。**
> 前置：本文接《桌面端打包方案对比_20261118.md》。载体事实不变——`mobile/dist/index.html` 764KB 单文件、4 个内联 script、0 外部 JS、0 fetch。

---

## 一、两个问题的答案，先摆出来

| 问题 | 答案 | 一句话理由 |
|---|---|---|
| **后续更新方便吗？** | **方便，而且比 pywebview 更成熟。** 但"方便"分两种场景，代价不同 | electron-updater 是现成的，差分更新能省掉壳的 150MB；分发给别人则要过签名和 SmartScreen |
| **查看源码方便吗？** | **非常方便。任何拿到安装包的人，一条命令就能拿到你的全部源码。** | asar 是打包格式，不是加密格式。官方工具 `npx @electron/asar extract` 直接解开 |

第二点不是"可能会有风险"，是**确定会发生**。所以真正的问题不是"能不能防住"，而是"你需不需要防"。下面分开讲。

---

## 二、源码可见性：asar 到底是什么

### 2.1 官方自己的措辞

Electron 文档在介绍 ASAR 时说，打包可以"缓解 Windows 上长路径名的问题、加速 require，**并隐藏你的源代码以避免能够轻易查看**" [ref_web_9cbf7f157677e225e071d346]。

注意 "**cursory inspection**"（随手翻看）这个词。官方没有说"保护"，也没有说"加密"。ASAR 的定位是**打包**，类似 tar：文件按顺序拼接，前面加一个索引。

社区实践说得更直接：

> ASAR 代表 Atom Shell Archive Format。Electron 的术语表把它描述为一种简单的、类似 tar 的格式，把文件拼接成单个文件。**它不保护源码。** 这个格式里没有压缩，也没有加密。官方打包器 `@electron/asar` 用一条命令就能解开：
> `npx @electron/asar extract app.asar out`
> 这就是为什么 asar 是随手可解的。[ref_web_0d854c0231676deab1596614]

### 2.2 对本项目意味着什么（具体到文件）

如果按标准方式打包，`app.asar` 里会有：

| 文件 | 体量（实测） | 解包后玩家能看到什么 |
|---|---|---|
| `wxcs3-game.js` | 9666 行 / 413KB | 全部规则：境界公式、突破概率、战斗判定、恩义、四艺、市场系数 |
| `wxcs3-data.js` | 3215 行 / 162KB | **全部 108 个成就、38 条事件、25 处奇遇、12 个 NPC 人设与台词、7 类诗词库**（以上五项均已实测计数） |
| `index.html` | 764KB | 全部 CSS、界面结构、文本渲染逻辑 |

也就是说：**解包 = 把整个游戏的策划案 + 文案库 + 数值表原文交出去。** 这比"代码被抄"严重——代码抄了要重写，文案和数值抄了直接能用。

### 2.3 防护手段的真实分级（别被标题骗了）

我把常见手段按"实际挡住谁"排序，用的是可核实的效果描述：

| 级别 | 手段 | 挡住谁 | 挡不住谁 | 对本项目值不值 |
|---|---|---|---|---|
| **L0** | 什么都不做（asar） | 完全不懂电脑的人 | 会搜一下的人 | — |
| **L1** | **asar 完整性校验**（`EnableEmbeddedAsarIntegrityValidation` + `OnlyLoadAppFromAsar`） | **改包的人**（改了就启动失败） | **读包的人**（解包照读） | 值得开，但解决的不是"看源码" |
| **L2** | 压缩/去注释（minify） | 瞥一眼的人 | 格式化器几秒还原布局 | 顺手做，不指望它 |
| **L3** | 混淆（标识符重命名、字符串编码、控制流平坦化） | 随手搜索替换的人 | 免费 deobfuscator 多数能还原 | 让代码变丑，但 108 条成就文本仍然明文 |
| **L4** | 字节码（bytenode）/ V8 快照 | 直接读源码的人 | 有反编译器；**字符串常量常存活** | 对本项目无效——文案是字符串 |
| **L5** | VM 保护（JSVMP） | 需要先读懂解释器的人 | 有成本、有性能损失 | 过度设计 |
| **真解** | 关键逻辑放服务端 | 所有人 | 需要联网 | 对应上一轮 S1/S2 |

关于 L1 要说清楚边界：ASAR 完整性从 **Electron 39 起转为稳定功能**，运行时按构建时哈希校验 `app.asar`，哈希缺失或不匹配则强制终止 [ref_web_53ba5395f8cb83a41ce75c91]。而两个 fuse 的细节是：

- `EnableEmbeddedAsarIntegrityValidation`：**macOS 从 Electron 16 起支持，Windows 从 Electron 30 起支持**，**且默认关闭**；
- `OnlyLoadAppFromAsar`：默认情况下 Electron 会依次找 `app.asar` → 松散的 `app` 文件夹 → `default_app.asar`；开启后不再回退到松散文件夹。**两个 fuse 必须一起开**，否则有人可以在 asar 旁边丢一个 `app` 文件夹绕过校验；
- 这两个 fuse **不隐藏源码**；官方文档未列出 Linux 支持 asar 完整性校验 [ref_web_0d854c0231676deab1596614]。

一句话：**L1 防"改"，L2~L5 只是提高门槛，都防不住"看"。**

### 2.4 所以对本项目的结论

看你的目的：

| 你的目的 | 源码可见是问题吗 | 该做什么 |
|---|---|---|
| **自己玩 / 发给几个朋友** | **完全不是问题，甚至是优点** | 什么都别做。玩家能看数值、能改文案、能做 mod——对单机文字游戏这是加分项 |
| **想收点钱 / 认真发行** | 是问题，但 Electron 解决不了 | 别在客户端加壳硬扛；把"能收费的部分"放服务端（云存档、论道、世界简报），客户端本来就该是"能读的壳" |

我倾向第一种。理由：这个项目的护城河不是代码复杂度（规则都是可读的 JS），而是**文案、数值手感和世界观**——这些恰好也是最容易被"看一眼就懂"的东西。而真要防，唯一有效的办法是让它**必须在服务端跑**，那正是上一轮后端方案里的 S1/S2。

## 三、更新：分三种场景，代价完全不同

### 3.1 场景 A：只更新自己的机器（最可能）

```
改 wxcs3-game.js → python mobile/build.py 重建 dist
→ npx electron-builder --dir（不出安装包，直接出目录）
→ 覆盖运行
```

代价：**每次要重新打一次 150MB 的包**，但这是本地操作，几十秒到两三分钟，不需要联网、不需要签名。

**结论：完全无痛。** 甚至可以不打包——开发期直接 `npx electron .` 指向源码目录，改完刷新就行。

### 3.2 场景 B：发给朋友更新（有摩擦，但可控）

如果不想做自动更新，最土但最有效的办法：**把游戏本体和壳分开。**

因为本项目是单文件 HTML，可以做这个取舍：

| 做法 | 更新成本 | 玩家能否看到/改游戏 | 适用 |
|---|---|---|---|
| **把 `index.html` 打包进 asar** | 每次要重发安装包 | 需要解包才能看 | 想要"像个整体软件" |
| **把 `index.html` 放 `extraResources`（asar 外）** | **替换一个 764KB 文件即可** | 直接可见可改 | 想省事 + 允许 mod |

第二种是我对这个项目的推荐：**壳（150MB）装一次，之后所有版本更新只是替换一个 764KB 的 HTML。** 玩家甚至自己就能更新——你把新 HTML 发给他，他丢进目录覆盖就完事，不用重装、不用签名、不用管 SmartScreen。

代价写在明面上：**玩家能直接打开这个 HTML 看到全部源码。** 但结合第二节的结论，这本来也防不住。

### 3.3 场景 C：真正的自动更新（electron-updater）

### 3.3.1 它怎么工作

electron-builder 打包时生成三个文件 [ref_web_78c5ba2921f9961b0f3af83a]：

| 文件 | 作用 |
|---|---|
| `latest.yml` | 版本号、文件哈希、块大小等元数据 |
| `xxx-setup.exe` | 新版本二进制 |
| `xxx-setup.exe.blockmap` | **每个文件块的 SHA512 哈希** |

客户端通过 `autoUpdater.checkForUpdates()` 读 `latest.yml` 比对版本，然后拿 blockmap 和本地文件逐块比对哈希，**只下载变化的块** [ref_web_78c5ba2921f9961b0f3af83a]。

分发端不需要专门服务，一个静态目录就够：

```yaml
publish:
  provider: generic
  url: https://updates.example.com/releases
```
nginx、S3、任意静态托管都行 [ref_web_7984d494eaf5b8dc5a1e35e1]。

### 3.3.2 对本项目的差分收益（这是 Electron 最实在的优点）

正常发版只改游戏逻辑，**Chromium + Node 那 150MB 逐字节不变**，所以差分后真正下载的只是 `app.asar` 变化的部分。对一次"改了几百行 JS"的版本，这个量级远小于全量 [ref_web_7984d494eaf5b8dc5a1e35e1]。

但要认清一个例外：**升 Electron 大版本（换 Chromium）时壳会变，差分接近全量。** 所以策略是——壳的版本尽量稳，游戏频繁发。

### 3.3.3 三条必须遵守的规则

来自一份两年生产环境的实践总结 [ref_web_7984d494eaf5b8dc5a1e35e1]：

1. **服务器上永远不要删旧版本**，至少保留最近两个。发坏的版本，重发旧 `latest.yml` 就能回滚。
2. **不要关闭安装包校验。** electron-updater 会自动验签名和哈希，关了等于给篡改开门。
3. **严格三段式 semver。** `1.0.10` 比 `1.0.9` 新，但 `1.0.9.5` 这种四段版本会让比较逻辑混乱。

另外 electron-updater 7.x 有个安全收紧值得知道：**凭证头只发给与 feed 同源的下载**。如果 `latest.yml` 里的文件 URL 指向另一个域名，那个下载不会带认证头——要么把文件放在 feed 同源，要么用预签名 URL [ref_web_b322cb6382580bb5f070076b]。

### 3.4 更新这件事的真正门槛：签名，不是代码

这是我要重点说的——**electron-updater 的代码量很小（十几行），麻烦全在签名。**

未签名的 Windows 安装包，用户会看到：

> Windows protected your PC — Microsoft Defender SmartScreen prevented an unrecognized app from starting.

对非技术用户，这个界面直接劝退。而现实更难看：

- 即使买了 **OV 证书**，**前几千次安装仍可能弹警告**，直到微软的声誉引擎认识你的发布者；
- **EV 证书**能立刻获得声誉，但贵、需要硬件令牌；
- 时间戳服务器比多数人想的更重要——不打时间戳，证书过期后签名就失效了 [ref_web_7984d494eaf5b8dc5a1e35e1]。

macOS 更严：必须 sign → notarize → staple 三步，且签名后**不能再改 bundle**。

**所以对这个项目的判断很直接：**

> 如果只是自己玩 + 发给几个朋友，**不要做自动更新，也不要买证书**。让朋友手动替换那个 764KB 的 HTML（场景 B），摩擦远小于"配一条签名+更新管线"。

自动更新只在一种情况下值得：**你有一批不认识你的用户**，且希望他们永远用最新版。那才需要花钱买证书、搭更新服务器。

## 四、两个被忽略的交汇点

这两个点不在"更新/源码"的问题里，但用 Electron 就一定会撞上，且直接影响前面两轮讨论的结论。

### 4.1 origin 与存档：Electron 也需要显式处理

上一轮说过：**localStorage 按 origin 隔离，`file://` 下行为未定义** [ref_web_18b661ec5e2300187fb1985b]。

Electron 里如果直接用 `win.loadFile('index.html')`，走的是 `file://`——**同样落入"未定义"区间**，且 origin 绑定的是 `app.asar` 里的那个路径。

**但 Electron 在这件事上比 pywebview 强一档**：它可以注册自定义协议，把 origin 钉成一个稳定、且被当作安全上下文的 scheme。这是 Electron 相对 pywebview 的一个真实优势（pywebview 只能靠"起本地 HTTP 服务 + 固定端口"绕）。

对本项目的要求不变：**先确认 origin 稳定，再谈打包。** 迁移老存档的问题依旧存在（见上一轮的 6.1 节，含 `wxcs3.ach` 成就磁盘那一块）。

### 4.2 DevTools 与"防作弊"是同一个人

Electron 就是 Chromium——玩家按 `Ctrl+Shift+I` 就能开 DevTools，然后：

- 直接在 Console 里改 `localStorage` 的存档；
- 直接改 DOM 里的数值看效果；
- 直接 Reproduction 你的战斗判定。

这一点**和上一轮后端方案的结论完全一致**：B 形态下"前端权威 = 不防作弊"，想防只能等 S6 后端权威数值。

所以有一个反直觉的建议：**别在生产包里关 DevTools。** 关掉只是阻止玩家"顺手看看"，但对一个单机文字游戏，能自己调试、自己改数值的玩家往往是核心玩家。关了它，你损失的是社区，不是安全。

## 五、给你的决策表

| 你的情况 | 更新方案 | 源码处理 | 签名 | 总成本 |
|---|---|---|---|---|
| **只自己玩**（最可能） | `--dir` 打包，覆盖运行；或直接 `npx electron .` | 不管 | 不需要 | **≈0** |
| **发朋友，不做更新管线** | HTML 放 asar 外，**换文件即更新** | 不管（本来也防不住） | 不需要 | **低** |
| **发给不认识的人，要自动更新** | electron-updater + generic 静态目录 + 差分 | 开 L1 完整性 fuse；别指望 L2~L5 | **OV/EV 证书，必须** | **中高（钱 + 管线）** |
| **想真正保护核心逻辑** | 同上一行 | **只能放服务端**（S1/S2） | 必须 | 高 |

## 六、一句话总结

**Electron 的更新是"工程问题"，源码可见是"定位问题"。**

- 更新：**自己更新零成本；发给朋友只需换一个 764KB 的 HTML；只有面向陌生用户做自动更新时，才需要为证书和管线付钱。** 差分更新确实好用，收益来自"壳不变、只换游戏"。
- 源码：**asar 不是锁，是打包。** 一条 `npx @electron/asar extract` 就能把 108 个成就、38 条事件、12 个 NPC 全部台词和数值表原文拿走。ASAR 完整性 fuse 防的是"改"，不是"看"。
- 结论：**如果你是给自己和朋友做，这两件事都不是问题，别为它们增加复杂度。** 如果你要商业化，那 Electron 帮不了你——真正有效的保护在服务端，而那条路上一轮已经画过了。
