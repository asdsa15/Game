## 一、一句话结论

**本项目只需要装 2 个必装包 + 1 个建议包。** 不需要 `electron-forge`、不需要 `electron-icon-builder`、不需要 `electron-store`。
主进程只做一件事——用自定义协议 `app://` 加载 `mobile/dist/index.html`——因此主进程**零第三方运行时依赖**也可以跑起来。

| 级别 | 数量 | 包 |
|---|---|---|
| 必装 | 2 | `electron`、`electron-builder` |
| 建议 | 1 | `electron-log` |
| 可选（有前提） | 2 | `electron-updater`、`electron-store` |
| **明确不要装** | 4 | `electron-forge`、`electron-icon-builder`、`builder-util`/`app-builder-lib`、`electron-devtools-installer` |

## 二、安装清单

### 2.1 必装（2 个）

| 包 | 版本 | 装到 | 作用 | 注意 |
|---|---|---|---|---|
| `electron` | **45.3.4** | `devDependencies` | 壳运行时（Chromium + Node） | postinstall 会从 GitHub 拉 **80~150MB** 二进制；**必须先配镜像**（§3） |
| `electron-builder` | **26.18.0** | `devDependencies` | 打包器，产出 Windows NSIS 安装包 | 首次打包还会拉 `winCodeSign` / `nsis` 工具包，同样走镜像 |

> `electron` 放 devDependencies 是标准做法：`electron-builder` 会把 Electron 二进制直接打进安装包，运行时不需要 `node_modules/electron`。

### 2.2 建议装（1 个）

| 包 | 版本 | 装到 | 作用 |
|---|---|---|---|
| `electron-log` | **5.4.4** | `dependencies` | 主进程/渲染进程日志落盘到 `%APPDATA%/问道长生/logs/`。打包后渲染进程 `console` 很难捞，出了白屏只能靠它 |

### 2.3 可选（各有前提，别无脑装）

| 包 | 版本 | 装到 | 前提与说明 |
|---|---|---|---|
| `electron-updater` | **6.8.11** | `dependencies` | **要自动更新才装。** 需要配套：① electron-builder 配 `publish`（GitHub Releases 或自建静态服务器）；② 把安装包和 `latest*.yml` 一起传上去。`electron-updater` 与 `electron-builder` 是同一 monorepo 的两个独立包，版本号体系不同（6.x vs 26.x），属正常 |
| `electron-store` | **12.0.0** | `dependencies` | **只存"应用设置"**（窗口尺寸、上次位置），**不存游戏存档**。⚠️ v12 是**纯 ESM**（`"type": "module"`，无 CJS 导出），CJS 主进程里 `require('electron-store')` 会报错；要用只能 `await import('electron-store')`，或锁 `electron-store@8.x` |

> **游戏存档不要用 electron-store。** 存档在渲染进程的 `localStorage`（`wxcs3_save` / `wxcs3_slots` / `wxcs3_slot_0~4` / `wxcs3.ach`），两个存储系统并存会让"存档到底在哪"变得不可查。electron-store 只放窗口尺寸这类无关存档的东西。

### 2.4 明确不要装（及原因）

| 包 | 原因 |
|---|---|
| `electron-forge` (5.2.4) | 与 `electron-builder` 二选一。两个都装只会互相抢 `postinstall` 钩子和构建产物目录 |
| `electron-icon-builder` | **不需要。** electron-builder 26 自带 `icon-tool.js` + `resvg.wasm`，放一张 `build/icon.png` 或 `build/icon.svg` 就能自动转出 `.ico` / `.icns` / Linux 全套尺寸（见 §4） |
| `builder-util` / `app-builder-lib` | `electron-builder` 的传递依赖，手动装没有意义 |
| `electron-devtools-installer` | 可选，但本项目是单文件原生 JS 应用，不装 React DevTools 等扩展，这一个用不上 |

### 2.5 安装命令

```bash
# 1) 先配镜像（§3），再装，否则 electron 的二进制会卡到超时
# 2) 必装
npm i -D electron@45.3.4 electron-builder@26.18.0
# 3) 建议
npm i electron-log@5.4.4
# 4) 可选（二选一或都不选）
```

## 三、国内镜像（装之前必须做）

`electron` 的二进制默认从 GitHub Releases 下载，`electron-builder` 首次打包还要拉 `winCodeSign` / `nsis`。
不配镜像，这两步各能卡 15 分钟以上并最终 `ETIMEDOUT`。

在项目根建 `.npmrc`：

```ini
registry=https://registry.npmmirror.com/
electron_mirror=https://npmmirror.com/mirrors/electron/
electron_builder_binaries_mirror=https://npmmirror.com/mirrors/electron-builder-binaries/
```

校验（应分别回显上面三个地址）：

```bash
npm config get registry
npm config get electron_mirror
npm config get electron_builder_binaries_mirror
```

**如果用环境变量而不是 `.npmrc`**，变量名是大写形式：`ELECTRON_MIRROR` / `ELECTRON_BUILDER_BINARIES_MIRROR`。
两种写法只选一种，`.npmrc` 对 CI 更可复现。

> 注：electron-builder **v26** 里，配置文件中的对应键名是 `electronDownload`（`mirror` / `mirrorOptions`）；
> **v27 改名为 `electronGet`**。本项目锁 26.x，所以用 `electronDownload`。这是 §8.1 那个陷阱的具体表现。

## 五、origin：Electron 方案的头号风险（照做，别跳）

### 5.1 为什么 `loadFile()` 不行

**Electron 的 `file://` 是 null origin（不透明源）。** 这和浏览器里"file:// 下 localStorage 行为未定义"是同一个坑，只是换了个壳。

Electron 官方文档在 `protocol.registerSchemesAsPrivileged` 一节写得很直白：

> By default web storage apis (localStorage, sessionStorage, webSQL, indexedDB, cookies) are **disabled for non standard schemes**.
> So in general if you want to register a custom protocol to replace the `http` protocol, you have to register it as a **standard** scheme.

—— 也就是说，自定义协议若不声明为 standard，**localStorage 直接不可用**，游戏的 4 个存档键全部失效。

### 5.2 正确做法：注册 `app://` 协议

```js
// main.js —— 骨架，示意，尚未实施
const { app, BrowserWindow, protocol, net } = require('electron');
const path = require('node:path');
const { pathToFileURL } = require('node:url');

// ⚠️ 必须在 app ready 之前调用，且整个进程只能调用一次
protocol.registerSchemesAsPrivileged([
  {
    scheme: 'app',
    privileges: {
      standard: true,        // ← 关键①：开启 localStorage 等 web storage API + 相对路径解析
      secure: true,          // ← 关键②：安全上下文
      supportFetchAPI: true, // ← 关键③：让 fetch 能用
      corsEnabled: true,
    },
  },
]);

const DIST = path.join(__dirname, 'mobile', 'dist');

function createWindow() {
  const win = new BrowserWindow({
    width: 520, height: 900,        // 沿用《桌面端打包方案对比》§6.2 的结论
    minWidth: 390, minHeight: 640,
    backgroundColor: '#FAF6EE',       // 宣纸底，避免白屏闪一下
    webPreferences: {
      contextIsolation: true,
      nodeIntegration: false,
    },
  });
  win.loadURL('app://bundle/index.html');
}

app.whenReady().then(() => {
  protocol.handle('app', (req) => {
    const { host, pathname } = new URL(req.url);
    if (host !== 'bundle') return new Response('not found', { status: 404 });

    // 目录穿越防护
    const target = path.resolve(DIST, '.' + decodeURIComponent(pathname));
    const rel = path.relative(DIST, target);
    if (rel.startsWith('..') || path.isAbsolute(rel)) {
      return new Response('forbidden', { status: 403 });
    }
    return net.fetch(pathToFileURL(target).toString());
  });

  createWindow();
  app.on('activate', () => {
    if (BrowserWindow.getAllWindows().length === 0) createWindow();
  });
});

app.on('window-all-closed', () => {
  if (process.platform !== 'darwin') app.quit();
});
```

### 5.3 这个方案顺带解决四件事

| 问题 | 为什么被解决 |
|---|---|
| **localStorage 不可用** | `standard: true` 才开启 web storage API |
| **dist 里的相对路径失效** | `standard: true` 才能解析相对 URL。`mobile/dist/index.html` 有 3 处 `href="./icons/..."`（`apple-touch-icon.png` / `icon-192.png` / `manifest.webmanifest`），非 standard scheme 下 `file` 协议那种"相对路径不认"的老问题会直接让图标挂掉 |
| **Service Worker 缓存陈旧** | `mobile/build.py` 注入的 SW 注册守卫是 `protocol === 'https:' \|\| hostname 是 localhost/127.0.0.1`。`app://bundle` 两个条件都不满足 → **SW 不注册**，彻底避开"装了新版还停在旧版"的坑 |
| **origin 每次启动都变** | `app://bundle` 是固定 origin，跨版本、跨安装路径、跨机器都一致 —— 这正是《桌面端打包方案对比》§二 约束二要求的东西 |

### 5.4 关于 asar 的一个坑

上例的 `net.fetch(file://...)` 在 `asar: true` 时读的是 asar 虚拟文件系统。Electron 对 `file:` 协议和 `fs.*` 都做了 asar 补丁，但 `net.fetch` 走的是 Chromium 网络栈，**这条路径的 asar 兼容性需要在实施时实测**。

对本项目的建议：**`asar: false`**。整个应用就 `index.html` + 4 个图标 + `manifest` + `sw.js` 共约 800KB，asar 压缩带来的好处（隐藏源码、缩短路径）在这里毫无价值，而"解包成真实目录"能让上面的 handler 逻辑最简单、最不容易出错。

若坚持 `asar: true`，改用 `fs.readFile`（fs 是 asar-aware）或 `protocol.registerSource`（官方文档明确说它支持从 asar 流式读取，但标记为 Experimental）。

## 六、存档迁移（承接既有结论，必做）

Electron 壳的 origin 与现有 `file:///C:/.../问道长生v6.html` 不同，**老存档一个都读不到**。既有文档已定方案，此处只列与 Electron 相关的落点：

1. **必须先给导出包补字段。** `game.js:4775` 的 `do_expall` 只打 `slots`，**不含 `wxcs3.ach`（跨局成就磁盘）**。
   改动是两行：
   ```js
   // 导出包加一项
   ach: achDisk()
   // 导入时若存在 ach，则合并
   achDiskSave(合并(oldDisk, o.ach))
   ```
   不补这个，"角色回来了、前世的功过格没了"，且 `unlockedMemories()`（前世记忆）随之失效。

2. **新壳首次启动主动提示一次**："如你此前在浏览器里玩过，请先在旧版导出全槽位备份，再在此处导入。"

3. **这条改动不依赖 Electron。** 换电脑、清浏览器缓存、手机→电脑，都靠它。建议在动桌面端之前先做掉。

## 八、版本陷阱（三个，都是会咬人的）

### 8.1 electron-builder 27 是 next，不是稳定版

`www.electron.build` 根路径现在指向 **v27（next，未发布）** 的文档。v27 的变更很大：

- 全量改用 **原生 ESM**，最低 Node **22.12.0**
- 配置键改名：`win.signtoolOptions` → `win.sign`、`electronDownload` → `electronGet`、`snap` → `snapcraft`、ASAR 选项归入 `asar`、原生模块选项归入 `nativeModules`
- `--publish` 不再隐式触发
- 有迁移命令：`electron-builder migrate-schema`（可先 `--dry-run` 预览）

**本项目锁 26.18.0**，读文档时把 URL 里的 `/v26/` 带上：
`https://www.electron.build/v26/docs/configuration/`、`https://www.electron.build/v26/docs/features/icons-and-images/`。

### 8.2 electron-store v12 是纯 ESM

见 §2.3。CJS 主进程里 `require()` 会抛 `ERR_REQUIRE_ESM`。要么用动态 `import()`，要么锁 `electron-store@8.x`，要么——像本项目建议的那样——**不用它**。

### 8.3 Electron 44 移除了 32 位构建

Electron 44 起不再提供 Windows ia32 与 Linux armv7l 的预编译二进制；需要这两个架构就得停在 Electron ≤ 43.x（v43 系列维护到 2027 年 1 月 EOL）。

本项目只要 Windows x64，**不受影响**。但 electron-builder 文档也提示：v26 对 32 位架构的要求是 `electronVersion <= 43.x`，用 45 时 electron-builder 会对 32 位请求**直接报配置错误**（不是警告）。
