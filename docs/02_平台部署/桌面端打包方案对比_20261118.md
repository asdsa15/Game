# 桌面端打包方案对比 · pywebview 是否合适

> 日期：2026-11-18
> 性质：**方案稿，未修改任何代码。**
> 前提事实（已实测）：`mobile/dist/index.html` 是 **615,627 字符的单文件**，4 个内联 `<script>`、**0 个外部 JS**、**0 处 fetch/XHR**；图标走相对路径 `./icons/`；已有 `manifest.webmanifest` 与 `sw.js`（且 `sw.js` 注册处有协议守卫，只在 https/localhost 生效）。

---

## 一、先说结论

**pywebview + PyInstaller 能做出来，但对这个项目不是最优，而且有一个会让玩家存档消失的陷阱。**

三句话：

1. **技术上可行**：单文件 HTML 直接 `--add-data` 塞进去就行，764KB 对打包体积几乎无影响（壳本身才是体积主体）。
2. **有一个必须避开的坑**：pywebview 的 `private_mode` **默认开启**、默认加载方式会起**随机端口**的本地服务——两个默认值叠加，结果是**关掉程序存档就没了，或者重启后读不到**。必须显式改配置，这不是"注意一下"，是"不改就废"。
3. **架构上不顺**：上一轮后端方案定的是 **Node**（Hono/Express）。pywebview 是 **Python**。等于在 JS 前端之外再引入一个 Python 运行时，将来本地后端要么跟着用 Python（推翻上轮选型），要么三个运行时并存（JS + Python + Node）。**Electron 是唯一能让"壳"和"后端"同语言的选项。**

如果只想要"图标 + 双击即玩 + 存档别丢"，其实有比 pywebview 更轻、更省事的路（见第四节方案 B / C）。

## 二、为什么这个项目对打包有特殊约束

普通网页应用打包，关心的是体积和启动速度。这个项目不一样，它有两条硬约束，**任何方案必须先过这两关**：

### 约束一：存档全在 localStorage，origin 一换就全丢

实测存档相关的 `localStorage` 调用点共 **14 处**，涉及 4 个键：

| 键 | 内容 |
|---|---|
| `wxcs3_save` | 自动存档 |
| `wxcs3_slots` | 槽位元数据 |
| `wxcs3_slot_0` ~ `wxcs3_slot_4` | 5 个手动槽位 |
| `wxcs3.ach` | 成就磁盘（跨角色。注意实际键名是带点的 `wxcs3.ach`，不是下划线，L9298） |

**localStorage 是按 origin 隔离的。** 现在的 origin 是 `file:///C:/.../问道长生v6.html`。换成桌面壳后，origin 会变成别的——**老玩家的存档一个都读不到**。

这不是理论风险，微软文档写得很明确：file URL 加载的文档"**origin 与其文件路径唯一绑定**"，不同路径的文档不共享存储数据 [ref_web_4d0c8c57307c44a9f9d731a3]。MDN 更进一步：**file: URL 下 localStorage 的行为是"未定义"的**，各浏览器不一致，规范不保证，浏览器随时可以改 [ref_web_18b661ec5e2300187fb1985b]。

其中 `wxcs3.ach` 尤其要注意：代码里明确写了「跨局独立存储键 ACH_KEY，**不跟存档走**——这是整个设计的地基」。

具体会丢什么、不会丢什么，实测判定函数是这样写的：

```js
// L9353
function achHas(id) { return !!(S.ach && S.ach[id]) || !!achDisk()[id]; }
```

也就是「本局成就（在存档里）」与「跨局成就磁盘（在 localStorage 里）」取并集。所以：

| | 换 origin 后 |
|---|---|
| **当前这一局的成就**（`S.ach`） | ✅ 随存档导入带回 |
| **前几世累计的成就**（只在磁盘里） | ❌ **丢**。`achDisk()` 会返回 `{}`，`unlockedMemories()`（前世记忆）随之失效 |

也就是说，迁移不只是"搬存档"，**还得单独把 `wxcs3.ach` 这个键搬过去**。而现在 `do_expall` 打出的备份包里只有 `slots`，**不含 `ach`**；`do_imp` 里也搜不到 `ACH_KEY`。这是迁移方案里必须补的一块（第六节）。

### 约束二：不能因为打包方式引入"每次启动 origin 都变"

这一条是约束一的推论，但杀伤力更大。两种常见做法都会踩：

- **PyInstaller `--onefile`**：每次运行解压到**新的临时目录**（`sys._MEIPASS`）→ 若用 file:// 加载，路径每次都变 → origin 每次都变 → **每次启动都是空存档**。
- **pywebview 默认加载**：传相对路径时，pywebview **自动起一个内置 HTTP 服务**（"对于相对路径，会自动启动HTTP服务器且无法禁用"）[ref_web_fe70e9b9fe415f3b9b2bc6e0]，而端口**默认随机** [ref_web_29db7da2b5e0bf7f673853ef]。→ origin 是 `http://127.0.0.1:<随机端口>`，**每次重启端口不同** → 同样读不到旧档。

**所以对这个项目，"用什么壳"其实是第二位的；"origin 能不能钉死"才是第一位的。**

好消息是：钉死 origin 的办法很简单，pywebview 支持固定端口（`http_port`），并且在非 private 模式下默认用 `DEFAULT_HTTP_PORT = 42001` [ref_web_3e84d56a70a3bc47529724c9]。但**必须显式配置**，不能靠默认值。

### 还有一个隐性约束：private_mode 默认不持久

pywebview 的官方 API 里，`private_mode` **默认值为 `True`**：

> `private_mode` - Control whether cookies and other persistant objects are stored between session. **By default, private mode is on and nothing is stored between sessions.** [ref_web_6fe7a94736b12af59d94b029]

另一份 API 参考写得同样直接：`private_mode bool True — Disable persistent cookies and storage` [ref_web_29db7da2b5e0bf7f673853ef]。

也就是说：**装完一跑，玩一小时，关掉，再打开——存档没了。** 而 `storage_path` 默认是 `%APPDATA%\pywebview`，配合 `private_mode=False` 才能落盘。

这三条加起来，就是"pywebview 方案能用但必须改三个默认值"的完整理由。**这三个默认值一个都不能漏。**

## 三、pywebview + PyInstaller 具体怎么改才对

如果最终选这条路，最小正确配置是这样（示意，非最终代码）：

```python
import webview, sys, os

def app_path(p):
    base = getattr(sys, "_MEIPASS", os.path.dirname(os.path.abspath(__file__)))
    return os.path.join(base, p)

if __name__ == "__main__":
    webview.settings["ALLOW_FILE_URLS"] = False   # 不依赖 file://，避免 origin 漂移
    webview.create_window(
        "问道长生",
        app_path("dist/index.html"),   # 相对/本地路径
        width=520, height=900,
        min_size=(390, 640),
    )
    webview.start(
        http_server=True,
        http_port=42001,               # ← 关键：钉死端口，锁死 origin
        private_mode=False,            # ← 关键：允许持久化
        storage_path=os.path.join(
            os.environ["APPDATA"], "问道长生"),  # ← 关键：存档目录落到用户目录
        debug=False,
    )
```

打包（`--onedir` 优先，理由见下）：

```bash
pyinstaller --noconfirm --clean --onedir --noconsole \
  --name 问道长生 \
  --add-data "mobile/dist;dist" \
  --hidden-import webview.platforms.winforms \
  --hidden-import webview.platforms.edgechromium \
  --exclude-module tkinter --exclude-module unittest \
  --exclude-module pydoc --exclude-module doctest \
  --icon assets/app.ico \
  launcher.py
```

几个参数的取舍说明：

| 选择 | 理由 |
|---|---|
| **`--onedir` 而非 `--onefile`** | onefile 每次解压到新临时目录，不但启动慢，还**直接威胁存档 origin**；且 Windows Defender 对单文件 exe 误报率明显更高 [ref_web_c4c3c6f75b13843eb12335fd] |
| **不用 UPX** | UPX 压缩后误报率上升，对一个要发给朋友的小游戏不值得 [ref_web_77888950f59f6a3c91ff79e7] |
| **显式两个 hidden-import** | pywebview 的 WinForms / EdgeChromium 后端是动态加载的，不写会"打包成功但运行白屏" [ref_web_9a8dc65fa7274a530de1428c] |
| **`--exclude-module` 排除四项** | 这是把体积从 24MB 压到 19MB 的主要手段（官方实测）[ref_web_eb4e69f0c1844a885940fbd4] |

期望体积：**约 15~25MB**（onedir）。对比：onefile 精简后可到 11MB [ref_web_a4f38ca2ba9a2201217bda00]，但带来上面的代价。

## 四、七个方案横向对比

评估维度按本项目重要性排序——**origin 稳定性排第一，不是体积**。

| # | 方案 | 体积 | 冷启动 | **origin 能否钉死** | 引入新运行时 | 与 Node 后端同源 | 跨平台 | 分发摩擦 | 上手成本 |
|---|---|---|---|---|---|---|---|---|---|
| **A** | 现状：双击 HTML | 0（单个 764KB 文件） | 极快 | ❌ **file:// 未定义** | 无 | — | ✅ | 零 | 无 |
| **B** | 本地服务器 + 浏览器（bat/启动器） | ≈0 | 快 | ✅ **可钉 127.0.0.1:8000** | 无（有 Python/Node 即可） | ✅ 同端口 | ✅ | 低（杀软不拦 bat） | **极低** |
| **C** | PWA 安装（Edge/Chrome"安装为应用"） | ≈0 | 快 | ✅ localhost/https | 无 | — | ⚠️ 桌面为主 | 零 | 零（已具备） |
| **D** | **pywebview + PyInstaller** | 15~25MB | 中 | ✅（需改 3 个默认值） | **Python** | ❌ 不同语言 | ✅ | **中高（误报）** | 低 |
| **E** | Electron + electron-builder | **150~300MB** | 慢 | ✅ | Node（**已有**） | ✅ **完全同源** | ✅ | 中 | 中 |
| **F** | Tauri | **3~10MB** | **极快** | ✅ | **Rust** | ⚠️ 壳/后分离 | ✅ | 低 | **高（要 Rust 工具链）** |
| **G** | C# WinForms/WPF + WebView2 | ≈10MB | 快 | ✅ | **.NET** | ❌ | ❌ 仅 Windows | 低 | 中 |

### 逐个说清区别

**A · 现状（双击 HTML）**
零成本，但正好踩在约束一上：**file:// 下 localStorage 是未定义行为** [ref_web_18b661ec5e2300187fb1985b]。玩家现在能用，是因为 Edge/Chrome 恰好给每个 file URL 分配了独立存储区——**但这不是承诺**，清缓存、换浏览器、挪文件位置都可能丢档。**这其实是当前最大的隐患，比"要不要打包"更值得先处理。**

**B · 本地服务器 + 浏览器**
`python -m http.server 8000` 或一个 20 行的 Node 静态服务，origin 固定 `http://127.0.0.1:8000`，存档立刻变可靠。**不需要任何打包。** 缺点：不像"软件"（有个黑窗口/要先双击两个文件）、需要机器上有 Python 或 Node。

但它是**唯一同时满足"零体积 + origin 可靠 + 与后端同端口同源"的方案**——因为它本来就是个服务器，将来 S1 云存档 / S2 论道代理直接挂同一个端口，前端连 CORS 都不用处理。这一点其他方案都做不到或要额外绕。

**C · PWA 安装**
项目已经有 `manifest.webmanifest` + `sw.js` + 图标，Edge/Chrome 打开后地址栏直接有"安装"按钮，装完是独立窗口 + 开始菜单图标。**零额外工作、零体积、origin 是 localhost 或托管域名（可靠）。**
`sw.js` 里已有协议守卫（只在 https/localhost 注册），说明这条路当初就考虑过。
限制：装的是"网站快捷方式"，不打包成 exe，**发不了给没有源码的人**。

**D · pywebview + PyInstaller**
优点：**上手最快**、代码量最少（20 行）、体积中等、Python 若已有环境则依赖最轻；`js_api` 可以把 Python 函数直接暴露给 JS，天然能当一个本地后端。
缺点三条：① 三个默认值不改就丢档（第二节）；② 引入 Python 运行时，与 Node 后端选型冲突；③ PyInstaller 打包的 exe **被杀软误报的概率明显高于其他方案**，尤其 onefile [ref_web_77888950f59f6a3c91ff79e7]。

**E · Electron**
优点：**唯一让壳与后端同语言**的方案——上一轮定的 Hono/Express 后端可以直接跑在主进程里，前后端一致、类型可共享、调试链路最短；生态最成熟，白屏/图标/自动更新都有一堆现成答案。
缺点：**体积失控**。一个 764KB 的游戏配 150MB+ 的壳，性价比很差 [ref_web_77888950f59f6a3c91ff79e7]。对一个单机文字游戏，这个代价很难说服自己。

**F · Tauri**
优点：**体积最小（3~10MB）、启动最快**、用系统 WebView 所以内存也低。是目前"轻量桌面壳"的最优解。
缺点：**要 Rust 工具链**。如果没有 Rust 经验，卡在编译环境上的时间大概率超过省下来的所有收益——这是搜索到的一手经验里的原话建议："如果团队里没人碰过 Rust，不要为了'小'去折腾 Tauri" [ref_web_77888950f59f6a3c91ff79e7]。

**G · C# + WebView2**
优点：体积小、启动快、Windows 原生、无需任何解释器。
缺点：**只有 Windows**、引入 .NET 栈、和现有 JS 工程完全脱节。对一个可能还想上 Mac/Linux 的项目，等于锁死平台。

## 五、针对本项目的推荐

分三种意图，答案不同——**先确认你要的是哪一个**：

### 意图 1：只是想让存档别丢、像个软件 → 选 **B + C 组合**

```
第一步（今天就能做，0 成本）：加一个 起步.bat 或 起步.command
    → python -m http.server 8000 --directory mobile/dist
    → 自动打开 http://127.0.0.1:8000
第二步（可选）：让玩家用 Edge「安装为应用」，得到独立窗口 + 图标
```
- 存档 origin 从"未定义的 file://"变成"确定的 http://127.0.0.1:8000"，**隐患当场消除**
- 零体积、零误报、零新运行时
- **这一步的收益比打包成 exe 大得多**，而且它是后面所有方案的前置条件（谁来当壳都得先解决 origin）

### 意图 2：想做出能发给别人的 exe → 选 **D（pywebview）**，但要接受三条代价

适合：主要自己玩 + 偶尔发给朋友、机器上本来就有 Python、不打算让后端和壳同语言。
必须做：第二节那三个配置 + `--onedir` + 存档迁移（第六节）。

### 意图 3：想让桌面端和后端方案长在一起 → 选 **E（Electron）** 或 **F（Tauri）**

- 愿意吃 150MB 换"全栈同语言、调试最短" → **Electron**
- 愿意学 Rust 换 5MB 和秒开 → **Tauri**

**不推荐把 pywebview 当作"后端化"的一部分**：上一轮方案选 Node 是有理由的（`wxcs3-game.js` 本身是 JS，S0 解耦后前后端共用一份规则）。用 Python 做壳再做后端，等于把这份红利扔掉。

## 六、无论选哪个，有两件事必须一起做

### 6.1 存档迁移（不做就是"更新即清档"）

老玩家存档在 `file:///C:/.../问道长生v6.html` 的 origin 下，新壳读不到。**必须在切换版本前提供迁移通道。**

好消息：项目已经具备大部分零件——`ACT.do_imp`（导入）、`ACT.do_exp`（单槽导出）、`ACT.do_expall`（全槽位备份，格式 `wxcs3-all`）、`downloadJson`、`chooseFile` 都在。

但**现有导出包不够用**。实测 `do_expall` 打出的包里只有 `slots`：

```js
// L4775
if (downloadJson(nm, { format: 'wxcs3-all', version: VER, exportedAt: Date.now(), slots })) ...
```

它**不含** `wxcs3.ach`（跨局成就磁盘），也不含 `wxcs3_save`（自动存档）。所以只靠现有按钮迁移，会出现"角色回来了、前世的功过格没了"。

**建议在动桌面端之前，先给导出/导入补一个字段**（几行改动，但必须做）：

```
导出包加一项：ach: achDisk()
导入时若存在 ach，则 achDiskSave(合并(oldDisk, o.ach))
```

这个改动同时可以让它**脱离桌面端独立成立**——以后玩家换电脑、清浏览器缓存、从手机换到电脑，都靠它。**它的价值不依赖于最终选哪个打包方案。**

迁移流程（三步）：

```
旧环境（浏览器双击 HTML）
  → 存档面板 → 全槽位备份 → 得到 问道长生v6.2_全槽位备份_xxx.json
新环境（桌面壳）
  → 存档面板 → 导入 → 选这个 json
```

**建议在新壳首次启动时主动弹一次提示**："如你此前在浏览器里玩过，请先在旧版导出全槽位备份，再在此处导入。" 这句话值一整个存档。

### 6.2 图标与窗口比例

`manifest` 里写的是 `"orientation": "portrait"`、设计按手机竖屏。桌面窗口默认 800×600 会挤压布局。建议初始 `520×900`、`min_size=(390, 640)`，并把窗口做成可缩放——实测截图目录里有 390/412/500 三种宽度的验收图，说明布局已验证过窄屏，桌面壳不该给它一个宽而扁的窗口。

## 七、一句话总结

**pywebview 能跑，但它不是"更省事"，而是"把三个默认值改成正确值之后才省事"——而这三个值恰好就是存档的生死线。**
对这个项目，真正的优先级是：

```
先钉死 origin（B/C，0 成本，今天可做）
    ↓
再看要不要 exe（D 够用 / E 同源 / F 最轻）
    ↓
最后才是壳的细节（图标、窗口比例、误报）
```

如果只做一件事，做第一件。**它不增加一行打包代码，却把"某天玩家存档突然没了"这个隐患提前拆掉。**

---

*方案完。未修改任何代码。*
