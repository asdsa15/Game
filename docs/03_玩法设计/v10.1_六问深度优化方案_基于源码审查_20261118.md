# 问题 1 · 灵根的差别体现在哪？

## 现状（证据）

数据表 `wxcs3-data.js:207-213`：

```js
heaven: { name:'天灵根', load:2.0, mul:2.0, els:1, ... }
earth:  { name:'地灵根', load:1.6, mul:1.6, els:2, ... }
true_:  { name:'真灵根', load:1.3, mul:1.3, els:3, ... }
pseudo: { name:'伪灵根', load:1.0, mul:1.0, els:4, ... }
mutate: { name:'变异灵根', load:1.8, mul:1.8, els:1, ... }
```

`load` 和 `mul` 五行数值**逐行完全相同**——两个语义不同的字段，其中之一显然是复制出来的。`els` 是死字段：全代码无一处读 `ROOTS[x].els`，实际逻辑在 `game.js:2047` 另写了一份硬编码 `needEls()`。

灵根真正产生差别的地方，全局只有三处：

1. **月修为倍率** `game.js:255,259`：`v = r.base*qi*qual*root*gf*zt` —— `root` 是 1.0~2.0 的连续值，这是唯一真实的差别。
2. **神道香火上限** `game.js:301-304`：`load>=1.5 ? 2.5 : 2` —— 天/地/变异全压成 ×2.5，真/伪全压成 ×2，**五种灵根在这里只有两种表现**。且这是"上限"，不是创角文案说的"香火速度"——真正的香火公式 `monthXianghuo()`（280-300）里根本没有 root。
3. **开仙基 +1 特判** `game.js:2930-2933`：只照顾天灵根。

战斗里灵根资质完全缺席：`computePower()`（`846-878`）返回 `base*stMul*sd*am*bodyDef().pow`，无 root；`do_cbt` 伤害（`7940` 附近）唯一的灵根贡献是 `keMul(mainEl(), foe.el)`，而 `mainEl()`（`6106`）= `S.rootEls[0]` —— **创角让你选 2~4 个五行属性（2181），游戏只认第一个，其余都是状态栏里的彩色装饰**。

创角文案（`2119`）说"灵根决定修为/香火速度与法术威力"：修为属实；香火是上限不是速度；"法术威力"只来自 rootEls[0] 的五行克制（×0.85~1.3），与天/地/真/伪资质无关。

## 诊断

- 选地灵根和变异灵根：修为差 20%，香火上限相同，战斗/突破/结局零差别。
- 伪灵根的"四/五系杂而不精"是纯设定：选 4 个属性只有 1 个生效，"杂而不精"的代价没有，"多系"的收益也没有。
- 项目自己知道这类问题长什么样：`BODIES` 注释（`data.js:840-843`）承认"其余六种体质的 eff 全是死文案"，然后 v8.1 给每种体质补了落点（`mul/pow/fire/ice/keFloor/quenchMul`）。**灵根从没做过同类修复。**

## 优化方向（只给方向）

1. **给资质一个战斗出口**：按天/地/真/伪/变异给 `computePower` 一个 `rootPow` 因子，或让五行克制的强度随资质缩放。让"万中无一"在打架时也有感觉，而不是只在打坐时。
2. **让多系真多系**：把 `rootEls[1..n]` 做成副属性参与共鸣/五行流转，或让系数决定可兼修的功法五行数。这样"伪灵根四系"从装饰变成一种有取舍的 build（系多则宽、专精度低）。删掉硬编码 `needEls`，直接读 `ROOTS[x].els`，消除双份数据。
3. **把塌陷的 2 档还原成多档**：`load>=1.5?2.5:2` 改成按资质分档的真实上限序列，让地/变异不再挤同一档。
4. **修正创角文案**：要么把文案改成实际行为，要么按上面 1~3 补实现，二选一，不能长期挂着不实说明。

# 问题 2 · 功法的差别（个体不同给出差异）

## 现状（证据）

45 本功法（`data.js:236-285`）在代码里被压成 5 个字段（`data.js:837`）：

```js
const GONGFA = GONGFA_EXT.map(x => ({ id:x.id, name:x.name, tier:x.tier, el:x.el, eff:x.eff }));
```

连 `price` 都丢了，结构上就不可能承载独特机制。`GONGFA_TIERS`（829-835）只有 `name/mul/color`，**没有题诗或描述字段**——真正的诗在 `VERSES`（2298+）按 realm 索引，与功法零关联。

个体差异只有两个半：
- `tier` → 月修为倍率（1.0/1.3/1.7/2.2/3.0）+ 境界上限卡点（`DAOGONG_CAP` 520-526）；
- `el` → 招式共鸣倍率（0.85~1.5，`resonResult` 6843-6856）；
- 半个：45 本里**只有 2 本**的 eff 落地——`game.js:6338-6339` 长春功回血 ×1.25、续脉决 ×1.3。而续脉决判定用的是 `ownedGongfa.indexOf`，**只要拥有就生效，不需要装配**，与"装配改变体验"矛盾。

**最硬的物证**：施法分支 `game.js:8019-8025`（实测行号，注意上一版方案引用的位置已漂移）：

```js
} else if (sub === 'cast') {
  if (S.mp < 30) { toast('灵力不足（需 30）'); render(); return; }
  S.mp -= 30;
  const g = getGongfa();
  dmg = Math.round(c.foe.hpMax * Math.max(0.08, 0.22*ratio) * mult * keK * (1 + artBonus('atk')));
  note = `施展《${g.name}》`;
}
```

`g` **只用于 note 字符串，伤害公式里没有任何功法字段**。花 75000 灵石买《百炼成仙道法》和用入门《聚气诀》点"施展"，伤害完全一样，只是弹窗书名不同。

eff 空头支票举例（`data.js` 原文 → 代码实现）：

| 行 | 功法 | eff 承诺 | 实现 |
|---|---|---|---|
| 238 | 御风术 | 遁速 +5% | 无 |
| 241 | 龟息延年诀 | 寿元 +10 | 无 |
| 242 | 金光咒 | 减伤一成 | 无 |
| 251 | 梅花易 | 机缘 +6，窥因果 | 无 |
| 254 | 紫霄雷法 | 需雷灵根 | **零 gating，任意灵根可用** |
| 256 | 天河剑诀 | 伤害 +50% | 无 |
| 265 | 补天真经 | 寿元上限 +80 | 无 |

`tools/test_text.js:94-118` 的文账一致校验只覆盖 `EVENTS.eff`，**没有一条检查 `GONGFA.eff`**——所以这些空头支票在 478 项全绿下照样存活。

另有一个命名空间错位：`resonResult`（6843-6856）里功法 el 用 `metal`、招式 kind 用 `sword`（`data.js:502`），全 `SKILLS` 没有 `kind:'metal'`。**所有剑系功法永远触发不了 ×1.20 同源共鸣**，只能靠相生吃 ×1.10。注释（`6841`）承认这类问题修过一次（"火" vs `fire`），没修干净。

## 诊断

换功法的可感知差异只有三条：修为速度、境界卡点、共鸣字样/倍率。法宝、体质、神通、符箓、灵兽各有独立机制，**唯独功法本体没有**。43 本功法的 `eff` 是纯展示。

## 优化方向（只给方向）

1. **数据化 eff，复刻体质的修复路径**：参照 `BODIES`（`data.js:844-853`）给每种体质补落点的做法，给 `GONGFA_EXT` 加结构化 `effect` 字段（如 `{swordMul:0.4, dmg:0.5, life:10, needEl:'thunder'}`），由一个统一函数结算。优先落地已经写死数值的那批（玄元剑经 +40%、天河剑诀 +50%、龟息延年诀寿元 +10、梅花易机缘 +6、紫霄雷法雷灵根 gating）。
2. **让施法真的施"法"**：把功法的 tier、el、专属 effect 接进 `cast` 的伤害公式（当前只读 `g.name`）。这是最高杠杆的一处——切换功法在最常用的输出手段上立刻有手感。
3. **统一 el 与 kind 命名空间**：给招式补 `el` 字段或在 `resonResult` 加 kind→el 映射，修好剑修体系的共鸣断链。
4. **把功法文本做成体系**：为 `GONGFA_TIERS` 或功法本体补题诗/描述并挂到功法详情，让"文本层"与"数值层"指向同一个对象，而不是两套不相干的表。
5. **护栏**：把 `GONGFA.eff` 纳入 `test_text.js` 一致性校验——凡 eff 写了数值承诺，必须有对应结算出口，否则测试失败。

# 问题 3 · 战斗时状态太少、联动不明显

## 现状（证据）

先纠正一个印象：**状态其实有 20 多个，联动也写了不少**（观察→无视卸力×1.6、术神通→foeWeaken 敌伤×0.7 两回合、目神通→foeMark 我方×1.25 两回合、锁灵阵→敌人逃不掉、火云符→首次火招×1.6、灵兽护主/反噬、本命器灵挡刀）。问题不在"少"，在三条断层：

**断层一：联动存在但看不见。** `renderCombat`（实测 `7701-7834`）显示的回合内动态状态只有 3 条：敌方气势、我方守势、我方看破。而 `foeMark`、`foeWeaken`、`talBuff`、`talShield`、`bmVeil`、`preBuff`、气势的增伤倍率**全部没有可见 UI**。玩家挨刀减伤 50% 不知道是守势、金刚符还是本命器灵；打出 ×1.25 看不到"破绽"标记。

**断层二：招式承诺不兑现。** 招式 desc 在 `openSkills`（`7586` 附近）原文展示给玩家，但 `do_cbt`（`7917+`）不实现：

| 招式 | desc 承诺 | 战斗实现 |
|---|---|---|
| 焚山掌 `liehuo` | 可灼烧 | 无灼烧状态 |
| 缠木根 `mumin` | 敌方一回合伤害减半 | 无束缚（唯有神通系 foeWeaken） |
| 毒火丝 `dugu` | 真伤持续三回合 | **全项目无 DoT/中毒字段** |
| 镇压八方 `zhentian` | 压制下一回合不能攻击 | 未实现；control 在 6845 被直接返回 `mul:1,txt:''` |
| 白骨飞剑 `baigu` | 命中低 | 无任何命中惩罚 |
| 流转剑罡 `liuJian` | 攻守两便 | 无防御效果 |
| 血炼神光 `xueLian` | 以气血十成换伤害 | 代码只扣一成（`S.hpMax*0.1`） |

**断层三：时间语义断裂。** `talBuff` 文案"下三回合伤害 +30%"（`data.js:321`），实现是 `8051` 写入、`7951` 读取，`talBuff--` **全局搜不到**——实为本场永久且可叠加。气势每 3 回合 +1、上限 3、无衰减。多数状态只有"读一次乘一下"，没有"产生→持续→消耗→反馈"的生命周期。

另外几处闲置定义：`S.injury` 只在 `6409` 写 `null`、从不读取；`COMBAT_TEXT.down`（`data.js:3204-3208`）三条倒地文案零调用；`FAXIANG`（928-941）12 法相明写"斗法最强"却只在创角展示；双属神通标注被 `shenTongSpec`（5875）用 `charAt(0)` 当单属处理。

敌人侧是纯静态：`trait` 4 种只是固定乘数，唯一行为分支是滑头低血逃跑。玩家叠什么状态，敌人下一步不会变。

## 诊断

每回合实际只有 2 步：玩家一步、敌人一步。敌人不根据玩家上一步决策。玩家能抓住的抓手只剩血条和灵力条——不是因为状态少，而是因为**联动不可见、承诺不兑现、状态不随时间演化**。

## 优化方向（只给方向）

1. **先做可见性，零改公式**：把 `foeMark`/`foeWeaken`（带剩余回合）、`talBuff`、`talShield`、`bmVeil`、`preBuff`、气势增伤倍率渲染成 chip，接进 `renderCombat` 现有的 tags 区（`7780-7784`）。这是投入最小、体感最大的一步。
2. **统一回合数模型**：`foeMark`/`foeWeaken` 已有 2 回合递减范式，把 `talBuff` 接入同一机制兑现"下三回合"；把 `talShield`/`observed`/`bmVeil`/`beastGuard` 明确定义为"1 次触发"并显示剩余次数。
3. **兑现或删除招式 desc**：`mumin` 复用 foeWeaken 式减伤；`dugu`/`liehuo` 加 `c.dot={turns,dmg}` 在 `foeTurn` 结算（现有递减框架可直接扩展）；`zhentian` 跳过一次 `foeTurn`；无意实现的承诺（如"命中低"）直接删文案，避免菜单欺骗。
4. **给敌人一条行为分支闭环**：按玩家 `observed`/低血/`defending`/`foeMark` 让 `trait` 切换应答（老练试探、莽夫追击），让"我用这招改变了敌人下一步"成为可观察事实。
5. **伤害来源拆解**：仿照 tips 区，在战斗日志给出"同源 +20%、你克他 ×1.3、命格 ×0.9"的来源链，让每次伤害有可读因果。

# 问题 5 · 游戏整体有没有逻辑错误？

有，以下每条都用代码坐实，按严重度排列。**注意：我核验时发现部分早期记录已过时，下述为本次实测最新版。**

## 阻断级

**1. 百世书页数耗尽 → 结局界面唯一入口变死按钮（软死档）**
- `pages:3`（`game.js:179`），每次轮回 `S.pages = Math.max(0, pages-1)`（`6042`），全局检索确认**只有初始 3 和递减，无任何补充机制**。
- `pageCount()===0` 时 `do_burn` 只弹"没有页可烧"（`6020` 附近），而结局界面唯一继续按钮就是"百世书·烧一页重来"。
- 更矛盾：`data.js:2855` 有个成就条件是 `s.pages===0` ——成就鼓励你把页数烧到 0，而烧到 0 就锁死唯一入口。
- 后果：第 4 次死亡后卡在结局界面，只能走系统菜单 `do_reset` 彻底清空，丢掉全部跨世积累。

## 严重级

**2. 两个结局永不触发：`ascend`（登仙）、`reinc`（百世书）**
- `ENDINGS` 定义了 12 个结局（`data.js:1911-1955`），我实测 `pickEnd(...)` 的全部调用（`game.js:8491-8503`）共 13 次，覆盖 sit/xiaoyao/fall/daohua/daotai/shizun/zhenjun/guowei/xianzun/modaо **10 个**；`ascend`/`reinc` 零调用，`S.endingId` 唯一赋值在 `6135`（只给 shizun/zhenjun）。
- 注：早期审查说"6 个结局不可达"是旧快照——现版本 `resolveEnding`（8484-8503）已补上死因多分支和 shizun/zhenjun，实际只剩这 2 个。
- `ascend` 的 cond 还写着"补回断掉的四境"（`data.js:1939`），代码里没有这个机制。文案、cond、美术（`end_ascend.png`/`end_reinc.png` 都在）全做完，就是走不到。

**3. 成就 `oldGrudge` 被归档白名单永久屏蔽**
- `tools/check_ach.js:69` 归档理由："需要旧仇寻仇与击杀流程（S.enemy 只置位，无击杀路径）"。
- 但击杀链早已实现：`game.js:532` 置 `pendingVengeance`、`10351-10352` 寻仇胜利清 `S.enemy`。
- 全局 grep 确认 `game.js` 从不 `bump('oldGrudge')`——玩法在、计数器没接，却被白名单伪装成"设计如此"，检查器永远报绿。

## 中等级

**4. 欠费惩罚：一个函数零调用，同一规则三份真相**
- `arrearsMul()`（`1707-1710`）全局零调用；相同逻辑复制两份内联在 `monthXiuwei`（270-271）、`monthXianghuo`（296-297）。改一处不改另一处就会出现仙道/神道惩罚分歧。

**5. 固定开销欠费后果不对等**
- `applyFixedCosts`（1645-1704）：宗门月课欠 3 月会真降级（1667-1670）；但 stones 类开销付不起只 `unpaid++` + 日志（1681-1684），不停用设施。于是"修缮欠费"不导致"庙宇破损"（templeBroken 只在夺祀事件触发），语义自相矛盾。

**6. 三处断链**：`SHIXIU`/`RENCAI`（`data.js:1207/1217`）零引用；`COMBAT_TEXT.down` 零调用；`S.injury` 只写不读。

**7. 愿物售卖文案与周期打架**：`do_vots` 提示"今日香客已散，明日再来"（`3349`），但 `votSold` 在 `advanceMonth`（464）按月清零——玩家以为明天能再卖，实际要等下月。

## 轻微（代码卫生）
`stoneAcc` 两次定义（110/180）后者覆盖前者；`5451-5452` 完全重复两行；`resolveEnding` 上方注释 8483 说的判定顺序与实现顺序不符。

## 系统性根因

# 问题 7 · 瓶颈的体现（与灵根、功法及其他系统的联动）

## 现状（证据）

**当前没有任何条件型瓶颈。** `breakReady()`（实测 `1304-1308`）唯一的突破门槛是"修为数值满"（仙道）或"香火数值满"（神道）。满之后进入四个成功率骰子：

| 突破 | 行号 | 因子 |
|---|---|---|
| xianBreakRate | 2588-2609 | 境界底数 0.72→0.22、heart×0.012、insight×0.006、karma>30 −0.06、merit>20 +0.04、灵气、四印、准备、hp |
| jindanRate | 2966-2974 | 果位档 rate、四印 ±0.15、merit≥50 +0.04、karma≥50 −0.06 |

| pillarRate | 3079-3094 | 三法底数、heart/merit/karma/灵气/香火/hp 加减 |

全是"数值满→掷骰→成/败"，没有"修为满但条件不足则不许突破"。悟性权重极低：悟性从 8 练到 20，破境率只 +7.2%。
