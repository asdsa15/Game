## 一、为什么要做：一期之后剩下的白话洼地

一期把「叙事主干」（诗、场景、奇遇、道书）写雅了，但玩家每隔几秒就会撞见白话，体验被这些缝隙反复打断：

| 出处 | 原文 | 问题 |
|---|---|---|
| 配方 `RECIPES` | `打不过就跑，跑得掉才活得久` | 俗谚口语 |
| 配方 `RECIPES` | `会做的人一辈子不愁药钱` | 现代白话叙述 |
| 四艺 `CRAFT_ARTS` | `自用省药钱，外卖需求刚性` | 「外卖」「刚性」现代词 |
| 功法境界 `DAOGONG_CAP` | `散修烂大街的引气法` | 市井口语 |
| 符箓 `TALISMANS` | `一次性火伤，相当于一记免费大招` | 游戏黑话，最出戏 |
| 提示 `toast` | `这不是 bug，是设定。` | 直接出现英文 bug |
| 提示 `toast` | `那颗丹药已经不在了` | 「了」字白话 + 现代量词 |
| 提示 `toast` | `撑过来了` / `废了` / `跳槽` | 口语、现代词 |
| NPC 对白 `ask.reply` | `我就喜欢跟痛快人做买卖` | 一期完全没碰的对白区 |
| NPC 初见 `meet` | `她就把糖递到你嘴边，你没接，她笑弯腰` | 连「了」「就」，白话叙述 |

**关键判断**：一期定的「了/的 < 2.5%」护栏只覆盖数据层文本，而大批白话藏在 `desc`/`eff`/`note`/`toast`/`meet`/`ask` 这些字段里。这些字段不进 `test_text.js` 的密度校验，所以一期全绿也照留白话。

## 二、优化口径：分三类，不一刀切

沿用一期基准（不用「了」「着」，少用「的」，破折号不进诗），但**必须先分类**——一期记录第 225 行明确「面板提示保持简洁是对的」。把所有提示都改成文言是另一种灾难。

### A 类 · 功能硬提示 —— 保持简洁，只统一措辞
`灵石不足（需 30）`、`无此物`、`已至顶`、`药材不足（需 N 株）`、存档槽位提示等。
- **原则**：不动或仅统一同义异写（`已至顶`/`已到顶` → 一写）。玩家要的是一眼看懂，不是读古文。
- **处理**：本次仅做措辞统一表，不做文言改写。

### B 类 · 叙事性提示与仪式节点 —— 本次重点，全面文言化
破境、证金丹、道胎、破柱、天劫、临终、结局、传承、奇遇结果等 `toast` / 面板 hint / `logLine`。
- **原则**：短章白描、留白多、说破少；去「了/着/就/么」，破折号改句读。
- **目标**：与已优化的 `VERSES`/`SCENES` 同一气息。

### C 类 · 道具/描述词 —— 本次重点，逐字段改写
`RECIPES.note`、`PILL_EXT.desc`、`ARTIFACT_EXT.eff`、`GONGFA_EXT.eff`、`SKILLS.desc`、`TALISMANS.eff`、`FAXIANG.opening`、`CRAFT_ARTS.desc`、`DAOGONG_CAP.why` 等。
- **原则**：**保留全部数值与关键词**（+N%、X 回合、需好感 60 等一个不能丢——它们是玩法契约），只把叙述外壳换成文言。
- **硬约束**：数值/字段名原样保留，`test_text.js` 的文账一致不能破。

### D 类 · 对白与战斗叙述
NPC `meet`/`ask`（一期只重写了 `stages`/`ctx`）、`INTENTS` 残留、`COMBAT_TEXT` 收尾类、战斗硬编码日志。
- **原则**：人物说话要「像他自己」；旁白短句化；不解释性格，只让他说一句自己的话（一期 NPC 写法）。

## 三、风格基准（从一期反推，权威）

| 维度 | 口径 | 出处 |
|---|---|---|
| 虚词 | 不用「了」「着」，少用「的」 | 落地记录 184 行 |
| 破折号 | 不进诗；叙述句改用句读断开 | 落地记录 184 行 + 护栏 205 行 |
| 密度 | 「了」「的」各 < 2.5% | 落地记录 203-204 行 |
| 句法 | 白描、短章、留白多、说破少 | 素材 04 卷首 |
| 人物 | 不解释性格，只让其自道一语 | 落地记录 128 行 |
| 制度 | 写成人话，但用古意，不用现代财经/游戏词 | 素材 04 + 本方案 |

改写范式（一期已验证）：

> 旧：气从鼻端进去，凉。过了三寸就分不清了——是自己的血在走，还是山里的气在走。
> 新：气自鼻端入，凉。过三寸便分不清，是血在行，抑或山气在行。

## 五、映射口径（落地时必须遵守，否则会接错）

1. **一动源表，派生表自更新**：`GONGFA = GONGFA_EXT.map(...)`、`SHOP_GONGFA` 由功法表 filter、`SHOP` 由丹药/法宝/材料拼成。**只改源表**，别改派生表，否则下次构建被覆盖。
2. **数值原样搬运**：`eff`/`desc` 里 `+N%`、`X 回合`、`需好感 60`、`寿元 −5` 等一律保留，只换叙述文字。素材里用 `〔数值〕` 标注的地方尤其注意。
3. **toast 的拼接变量不动**：如 `破境 · ${realmName()}`、`灵石不足（需 ${n}）`，只改固定文案部分，变量插值原样留。
4. **NPC 对白三字段**：`ask.q`（问）、`ask.opts[].t`（玩家选项）、`ask.opts[].reply`（对方答），`fav` 数值不动；`reply` 改写保留原来的情绪走向与好感因果。
5. **不新增字段、不新增表**：本次是纯替换，素材骨架与现表一一对应。

## 六、护栏与验收（建议加进工具链）

1. **扩展密度校验覆盖面**：`tools/test_text.js` 第 7 节现只扫数据层部分表；建议把 `RECIPES.note`、`PILL_EXT.desc`、`GONGFA_EXT.eff`、`SKILLS.desc`、`NPC.meet`、`ask.reply` 纳入「了/的 < 2.5%」校验。**分字段保留原文数值，只测叙述文字的虚词密度**。
2. **现代词黑名单**：新增静态检查，文本中不得出现 `bug / 外卖 / 刚性 / 词条 / 跳槽 / 点一下 / 烂大街 / 免费大招 / 资产 / 属性加成` 等现代词与游戏黑话（A 类功能提示白名单除外）。
3. **数值不丢失断言**：改写前后逐条比对 `eff`/`desc`/`note` 中的数字与 `+N%` 串，必须完全一致——防止「改文风把数值改没了」。
4. **文账一致**：沿用现有 `test_text.js`，凡文本承诺的机制（如「下三回合」）仍须与代码一致——本方案只改文字，**不解决机制缺失**（那是 v10.1 问题 3 的事）。
5. **人工通读**：素材落地后，创角页、配方册、藏经阁、破境/临终/结局各走一遍，确认气息统一、无「文白夹杂到出戏」的接缝。
