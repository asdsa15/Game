> 日期：2026-11-26 ｜ 性质：**方案稿，未实施**（**例外：P4a 的数据库与账号层已提前落地，见 §13**）
> 现状实测：20 个 JS + 1 个 HTML，**26,486 行**；`wxcs3-game.js` 15,364 行 / 530 函数 / 195 ACT；
> `wxcs3-data.js` 4,968 行 / 117 张表；2034 项断言；无服务端、无账号、无数据库、无 CI。
>
> **本方案取代 `架构演进总纲_20261126.md` 的 §1.1 与 §1.2。**
> 那两条的前提是"沿用现有形态、只做增量优化"，结论是「不做全盘后端重写」「不物理拆分老文件」。
> 现在的目标是"做成一个真实项目"——前端、后端、数据库、部署、运营后台齐全。
> 前提变了，结论就必须跟着变，不能让两套结论并存。§1.3 的分层判据、§3 的扩展四模式仍然有效，继续沿用。

## 一、目标形态

一句话：**把"一个能跑的 HTML"改造成"一个能上线的产品"**——玩家端、服务端、内容后台、发布流水线四件套齐全。

```text
                    ┌──────────────┐
   浏览器 / PWA ───→ │  apps/web    │  Vue 3 + TS（玩家端，离线可玩）
   Electron / APK ─→ │              │
                    └──────┬───────┘
                           │ HTTPS / JSON（OpenAPI 契约）
                    ┌──────▼───────┐        ┌──────────────┐
                    │  apps/api    │───────→│ PostgreSQL   │ 账号 / 云存档 / 结局榜
                    │  Fastify+TS  │        ├──────────────┤
                    │              │───────→│ Redis        │ 榜单 / 限流 / 会话
                    └──────┬───────┘        └──────────────┘
                           │
                    ┌──────▼───────┐
                    │  apps/admin  │  内容运营后台（改表 → 发布内容版本）
                    └──────────────┘
                           │
        ┌──────────────────┴───────────────────┐
        │            packages/*                │
        │  core（纯规则） content（数据表）      │
        │  contracts（双端类型） sim（黄金对照） │
        └──────────────────────────────────────┘
```

四条硬边界（写进 CI，违反即挂）：

| 包 | 可以有 | 绝对不许有 |
|---|---|---|
| `core` | 纯 TS、immer、自身 RNG | DOM、`fetch`、`localStorage`、`Date.now()` 直读、`Math.random()` |
| `content` | JSON/TS 常量、zod schema | 任何逻辑分支 |
| `contracts` | zod schema、类型、OpenAPI 定义 | 业务实现 |
| `api` | Fastify、Prisma、Redis | 游戏规则（必须调 `core`） |
| `web` | Vue、Pinia、样式 | 规则判定（必须调 `core`） |

> 这条边界是"像不像真实项目"的分水岭：现在 `applyState` 里同时有规则、文案、结算、渲染四种东西，这在任何团队里都无法评审。

## 三、核心引擎：命令 → 新状态 + 事件流

### 3.1 为什么不是纯 reducer

现有 195 个 ACT 是"直接改全局 `S` + 写日志 + 顺手渲染"。硬改成 `(state, action) => state` 要动 2,786 处引用，等于重写两遍。

采用**可变草稿 + 不可变边界**：命令内部照旧改字段，但改的是 immer draft；对外永远是"进一个快照、出一个快照"。

```ts
// packages/core/src/engine/ctx.ts
export interface CmdCtx {
  s: Draft<GameState>;            // 只在这里可写
  c: Content;                     // 只读内容表
  rng: Rng;                       // 唯一随机源（mulberry32，seed 存在 state 里）
  emit(e: GameEvent): void;       // 事件流：日志/收益/音效/统计共用一条
  now: () => number;              // 时间注入，测试可冻结
}

export type Command = (ctx: CmdCtx, args?: unknown) => void;

export function apply(state: GameState, cmd: Command, args?: unknown) {
  return produce(state, draft => {
    const events: GameEvent[] = [];
    cmd({ s: draft, c: CONTENT, rng: makeRng(draft.meta.rngState), emit: e => events.push(e), now }, args);
    draft.meta.rngState = /* rng 回写 */;
    return events;                              // 由调用方拿去做 UI / 落库
  });
}
```

收益：

1. **可测**：`expect(apply(s0, cultivate)).toMatchSnapshot()`，不用 DOM 桩。
2. **可后端复用**：服务端做校验/重放/反作弊时跑同一份命令，前端不可信也不怕。
3. **可回放**：`{seed, commands[]}` 就是一场完整对局，能复现任何 bug（现在只能靠玩家描述）。
4. **事件流替代 `logLine`**：`emit({type:'log', cat:'combat', text})`，UI 订阅、后端可选落库做年谱云备份与统计。现在 294 处 `logLine` 调用不需要全改签名——`logLine` 作为 core 内的语法糖保留，内部转 `emit`。

### 3.2 随机源

现状 `rng()` 在无 seed 时回落 `Math.random()`（`wxcs3-game.js:60`），这是存档不可复现的根。新核心里 **`Rng` 必须由 state 携带**，`Math.random` 在 `core` 内被 ESLint 规则禁用。

### 3.3 战斗：`do_cbt` 629 行拆五个 resolver

| 现位置 | 拆出 | 性质 |
|---|---|---|
| `ACT.do_cbt` 内联 | `calcGap()` 位格压制 | 纯函数 → `core/rules` |
| 同上 | `resolveCombo()` 杀招链 | 纯函数 |
| 同上 | `resolveShi()` 势 | 纯函数 |
| 同上 | `resolveTalisman()` 符箓乘区 | 纯函数 |
| 同上 | `resolveDamage()` 伤害汇总 | 纯函数 |
| 保留 | `doCbt()` 只做调度 | 命令 |

验收判据不是"拆了"，而是**每个 resolver 有独立单测，且 `doCbt` 从 629 行降到 120 行以内**。

`do_enc` 579 行同理：`resolveEncBranch()` + `renderEnc()` 分离。

## 四、数据与存档

### 4.1 内容表

- `tools/extract-content.mjs` 从旧 `wxcs3-data.js` 一次性抽取 117 张表为 JSON（AST 解析，不手抄）。
- `packages/content/schema/` 每表一个 zod schema。CI 跑 `validateAll()`：
  - id 唯一、引用的 id 必须存在（NPC → EVENTS → ENCOUNTERS 交叉引用）
  - 数值域检查（概率 0~1、价格非负、境界枚举合法）
  - 文案长度下限（延续 `test_text` 的 30 字/12 字门槛）
- `contentVersion` 语义化版本，随包发布；后端可下发版本号做灰度。

### 4.2 存档

```ts
// packages/core/src/state/schema.ts
export const SaveV2 = z.object({
  format: z.literal('wendao-save'),
  version: z.literal(2),
  contentVersion: z.string(),
  savedAt: z.number(),
  seed: z.string(),
  state: GameState,          // zod 全量校验，杜绝"字段兜底"式静默容错
});
```

- **迁移链**：`migrations/001_from_v1.ts`（旧 `{format:'wxcs3-save',version:'10.2'}` → V2），`002_...` 依次叠加，`migrate(save)` 跑完链。
- 旧档当前靠"字段已兜底"容忍版本不符（`wxcs3-rules.js:117`），新方案改为**显式迁移 + 校验失败明确报错**，不再静默吞掉。
- 本地用 IndexedDB（离线可玩），登录后与服务端 `PUT /saves/:slot` 同步；冲突用 `version` 乐观锁，冲突时保留两份让玩家选。

## 五、后端

### 5.1 技术栈

**Fastify 5 + TypeScript + Prisma + PostgreSQL 16 + Redis 7**。
单进程足够：这是单机文字游戏的服务端，压力在存档读写与榜单，不在实时战斗。

### 5.2 表结构（Prisma）

```prisma
model User {
  id        String   @id @default(uuid())
  email     String   @unique
  passHash  String                  // argon2id
  nickname  String
  role      Role     @default(PLAYER)
  createdAt DateTime @default(now())
  saves     Save[]
  runs      Run[]
}

model Save {                        // 云存档：一用户多槽位
  id        String   @id @default(uuid())
  userId    String
  slot      Int                       // 0=自动，1~3=手动
  version   Int      @default(1)      // 乐观锁
  state     Json                      // SaveV2.state
  meta      Json                      // 境界/年龄/道号快照，列表页免解包
  updatedAt DateTime @updatedAt
  @@unique([userId, slot])
  @@index([userId, updatedAt])
}

model Run {                         // 一次完整人生（结局上报）
  id       String   @id @default(uuid())
  userId   String?
  seed     String
  ending   String                     // sit / ascend / guowei ...
  realm    Int
  age      Int
  score    Int
  endedAt  DateTime @default(now())
  @@index([ending, score])
}

model ContentRelease {              // 内容版本（运营后台发布）
  id        String   @id @default(uuid())
  version   String   @unique
  payload   Json
  publishedAt DateTime @default(now())
}
```

### 5.3 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/auth/register` `/auth/login` `/auth/logout` `/auth/refresh` | 邮箱 + 密码，argon2id；access 15 分钟（内存），refresh 30 天（httpOnly + SameSite=Lax） |
| GET | `/me` | 当前用户 |
| GET | `/saves` | 槽位列表（读 `meta`，不解包 state） |
| GET | `/saves/:slot` | 取档 |
| PUT | `/saves/:slot` | 存档（`If-Match: version`，冲突 409） |
| POST | `/saves/:slot/import` | 导入旧 localStorage 档（服务端跑迁移链） |
| POST | `/runs` | 提交结局（服务端重放校验，防改分） |
| GET | `/leaderboard?board=realm\|ending\|age&page=` | Redis zset 榜单 |
| GET | `/content/version` `/content/:table` | 内容版本与按表下发（热更预留） |

- 全部入参 zod 校验，OpenAPI 由路由自动生成 → `packages/contracts` 生成 TS 类型给前端。
- 游客模式：不登录也能玩（纯本地）；登录后才启用云存档与榜单。**不做强制登录**——单机文字游戏强制注册只会掉玩家。
- 反作弊：`POST /runs` 不信任客户端上报的分数，服务端用 `{seed, commands[]}` 重放一次，取重放结果。

### 5.4 工程基线（真实项目必备，缺一样就不算"像项目"）

| 项 | 做法 |
|---|---|
| 配置 | `@fastify/env` + zod，启动即校验，缺变量直接退出 |
| 日志 | pino，结构化 JSON，带 `reqId` |
| 错误 | 全局 error handler + Sentry（P6 接） |
| 限流 | `@fastify/rate-limit` + Redis（登录 5 次/分/IP） |
| 安全 | helmet、CORS 白名单、CSP 明确允许项 |
| 迁移 | Prisma migrate，生产只跑 `migrate deploy` |
| 种子 | `db/seed.ts` 造测试账号与样例存档 |
| 健康检查 | `/healthz`（检查 pg + redis） |
| 备份 | 每日 `pg_dump` 到对象存储，保留 14 天 |
| 版本 | semver + CHANGELOG，镜像打 `git sha` |

## 六、前端

### 6.1 技术栈

**Vue 3 + TypeScript + Vite + Pinia**。

选它的三条理由（不是"生态大"这种废话）：

1. 现有 UI 是模板字符串 + `data-act` 委托，Vue 模板与事件绑定的迁移损耗最小；
2. 单文件组件把"文案 / 样式 / 交互"放一处，契合本作"文本即玩法"的组织方式，比 JSX 更贴近现有写法；
3. 无 SSR 需求，产物是纯静态，PWA / Electron / APK 三条打包线照旧。

**不引 Tailwind**：现有 CSS 是手写水墨风（变量 + 渐变 + 书法字距），换原子类等于重画 1,000 行，收益为零。做法是把现有 CSS 抽成 `styles/tokens.css`（颜色/间距/字号）+ 组件 scoped style。

### 6.2 结构

```text
App.vue
├─ TopBar.vue                （道号 / 时间 / 系统）
├─ CreateScreen.vue          创角（原 renderCreate 8 步）
├─ MainScreen.vue
│  ├─ NavCol.vue             左：天时 + 六组导航
│  ├─ CenterTabs.vue         中：行事 / 纪事 / 账目 / 道基（v10.8 已定）
│  │  ├─ ActionPage.vue      主行动 + 自由输入
│  │  ├─ ChronPage.vue       纪事八类筛选
│  │  ├─ LedgerPage.vue

└─ modals/                   43 类面板，按域拆目录
```

- 状态：`useGameStore` 持 `GameState`（`core` 的 zod 类型），所有变更走 `store.dispatch(cmd, args)`，内部 `core.apply()` 后一次性替换快照 → 组件自动响应。
- **不做** `v-html` 拼字符串。现有 `optRow()` 这类返回 HTML 的函数全部改为组件 `<OptRow>`，XSS 面同时收掉。
- 键盘：`useHotkeys()` 统一注册，战斗与主界面同一套"动作数组真源"（v10.8 P0 已立的规矩继续用）。

## 七、内容运营后台（`apps/admin`）

真实项目的标配，也是这个项目最缺的一环——现在改一句台词要找开发者改 JS。

- 表浏览/编辑：按 domain 分页，字段级校验（复用 `content` 的 zod schema）
- 文案对比：改前/改后 diff，支持回滚
- 发布：生成 `contentVersion` + `ContentRelease` 记录，可灰度（按用户百分比下发版本号）
- 看数：日活、开局数、结局分布、卡点分布（哪一步流失最多）
- 权限：`ADMIN` / `EDITOR` 两级，操作留审计日志

## 八、迁移策略：黄金样本 + 断言清单

完全重构最大的风险不是写不出来，是**写出来之后行为变了而没人发现**。三道保险：

### 8.1 黄金样本（Golden Master）

```text
tools/golden/gen.mjs
  旧引擎 + 固定 seed + 脚本化命令序列
  → 每步输出 { step, cmd, stateHash, logTail }
  → packages/core/test/golden/{xian-early, xian-late, shen, both, combat-heavy, ...}.json
```

- 8 条剧本：仙道前/中/后期、神道、双修、战斗密集、经济密集、奇遇密集、结局分支。
- `stateHash` = 全字段稳定序列化后 sha256；不一致时输出**字段级 diff**。
- 新核心逐帧对齐。差异必须归入三类之一：①等价重构（更新基线）②已知修正（登记白名单并写明理由）③bug（修）。

### 8.2 断言清单

2034 项断言现在靠 `vm` 桩读内部变量，不能直接复用。做法：

- 逐条抄成 **vitest 用例清单**（`docs/05_架构方案/断言迁移清单.md`，按域分组打勾）；
- 纯规则类 → 直接改写成 `core` 单测；
- 界面临界类（"点这个按钮后出现那段字"）→ 改写成 Playwright E2E；
- 迁移完成的标准：**清单 100% 勾选**，不是为了凑数，而是防止"新项目测试很少"这种最常见的重构事故。

### 8.3 并行期

P0~P5 期间旧版一直可玩、可发布。`legacy/` 只读，新版本独立域名/端口。P6 才切流并下线旧版。

## 九、批次计划

七个阶段、十一个批次。每批独立可回滚，批与批之间不交叉改同一功能面。

| 批次 | 范围 | 主要产出 | 验收 | 旧版状态 |
|---|---|---|---|---|
| **P0** 基建 | monorepo、TS、ESLint/Prettier、Turbo、CI、docker-compose、`.env.example`、契约骨架 | 空跑通的四包骨架；`pnpm test` 能跑；CI 绿 | 四个包各自 `build`/`typecheck` 通过；docker 起得来 | 不变 |
| **P1a** 内容 | 117 表抽取脚本 → JSON；每表 zod schema；交叉引用校验 | `packages/content` 完整；`validateAll()` 全绿 | 117 表 0 校验错；文本总量与旧版一致（差 <1%） | 不变 |
| **P1b** 内核骨架 | `GameState` 类型、`Rng`、`CmdCtx`、`apply()`、事件流、迁移链骨架 | `core` 能创建一局空状态并跑 3 个命令 | 单测：同 seed 两次 `apply` 结果 hash 相同 | 不变 |
| **P2a** 修炼域 | 打坐/闭关/破境/境界/寿元/淬体（约 40 命令） | `core/commands/cultivate/*` | 黄金样本 `xian-early` 前 200 帧对齐 | 不变 |
| **P2b** 战斗域 | `do_cbt` 拆 5 resolver + 195 命令里的 23 个战斗动作 | `core/commands/combat/*` | `doCbt` ≤120 行；`combat-heavy` 剧本对齐；战斗单测 ≥80 项 | 不变 |
| **P2c** 其余域 | 经济/四艺/宗门/家族/奇遇/事件/NPC/神道/人生/元系统 | 剩余命令按 12 域落位 | 8 条黄金样本**全部**对齐；断言清单 ≥90% 勾选 | 不变 |
| **P3a** 前端骨架 | Vite + Vue + Pinia + tokens.css；主界面三栏四页 | 能用新前端玩「创角 → 打坐 → 破境」 | Playwright 12 条黄金路径过 8 条 | 不变 |
| **P3b** 前端全量 | 战斗页、43 类弹窗、四艺/坊市/宗门、移动端适配、PWA | 与旧版功能等价 | 12 条全过；三尺寸截图验收；离线可玩 | 不变 |

| **P4b** 榜单与上报 | `runs` 上报 + 服务端重放校验、Redis 榜单、限流 | 榜单页可用 | 篡改分数的请求 100% 被拒 | 不变 |
| **P5** 运营后台 | admin 表编辑、diff、发布、灰度、看数 | 非开发者能改一句台词并发布 | 改文案 → 发布 → 前端生效，全程不碰代码 | 不变 |
| **P6** 切流下线 | 部署、灰度、备份演练、旧版归档、文档收口 | 正式域名上线 | 灰度 7 天无 P0；回滚演练成功 | 下线 |

**为什么这么切**：先立骨架（P0）→ 再搬"不会变的东西"（P1a 数据）→ 再搬"最容易被测的东西"（P1b/P2a 修炼）→ 再啃最硬的（P2b 战斗）→ 前端只做一次（P3）→ 后端最后接（P4，因为前端已经能单机跑）→ 运营与上线（P5/P6）。

**关键顺序理由**：后端放在 P4 而不是 P1，因为云存档依赖 `SaveV2` 定稿，而 `SaveV2` 依赖 `GameState` 定稿；`GameState` 在 P2 结束前一直在动。先做后端等于返工。

> **实施后修正（2026-11-26 夜）**：上面这条前提是错的。存档把 `state` 存成 `jsonb`，服务端只校验**信封**
> （format / version / seed / savedAt）与体积，根本不解析那 210 个字段——所以数据库与账号层
> 不依赖 `GameState` 定稿，可以独立做完。**P4a 已提前落地**（见 §13），顺序反而更合理：
> 先有真接口，前端联调不必再造一套假数据。真正依赖 `core` 的是 P4b 的"结局重放校验"，那条仍必须等 P2。

## 十一、风险与对策

| 风险 | 现实后果 | 对策 |
|---|---|---|
| 行为漂移 | 玩家发现"伤害不对了"但说不清哪不对 | 黄金样本逐帧对齐 + 字段级 diff；P2 期间不开新功能 |

## 十二、需要你拍板的四件事

1. **前端选 Vue 还是 React**。我推 Vue（迁移损耗最小、单文件组件贴合文案型 UI）。如果你更熟 React，现在换成本最低，P3 之后换就是重写。
2. **账号体系要不要**。我建议"游客可玩 + 登录才有云存档与榜单"，不强制注册。若你只想做纯单机、不要账号，那 P4/P5 可以砍掉，但方案就不是"前后端都有"了。
3. **内容后台要不要**（P5）。要，才是"真实项目"；不要，改文案仍然要找开发者。我建议要。
4. **旧版何时冻结**。我的建议是 P2 开始冻结新功能——这是整个计划能不能收口的唯一硬约束。

## 十三、已落地：P4a 数据库与账号层（2026-11-26）

代码在 `apps/api/`，**53 项测试全绿，类型检查通过，服务端真实启动验证过**。
这一批只做"数据与身份"，不含任何游戏规则——所以它不受 P2 影响，可以独立上线。

### 13.1 做了什么

| 项 | 落地 |
|---|---|
| 表 | `users` / `refresh_tokens` / `saves` / `runs` / `content_releases`，DDL 在 `db/001_init.sql` |
| 接口 | 14 个（见 `apps/api/README.md` §二）：注册/登录/刷新/登出/me + 存档 CRUD/导入 + 结局上报/我的历史 + 三榜 |
| 账号 | 邮箱 + scrypt 散列；access JWT 15 分钟（前端内存），refresh 32 字节随机串 30 天（httpOnly cookie，库存 sha256，可轮换可撤销） |
| 云存档 | 乐观锁（`If-Match` → 409 带当前版本）；`state` 存 jsonb，服务端不解析字段 |
| 旧档迁移 | `POST /saves/:slot/import` 收 `wxcs3-save` 信封或裸 state，规整成 v2 并回报 `migratedFrom`；认不出就 400，**不静默兜底** |
| 结局与榜单 | `POST /runs` 服务端计分（客户端传分无效）；榜单每人只取最好一条，同分先到先得 |
| 部署 | Dockerfile + docker-compose（PG 自动建表 + healthcheck）；`.env.example` 声明全部变量 |
| 种子 | `npm run db:seed` 造演示账号 `demo@wendao.local / demo12345` + 存档 + 三条结局 |

### 13.2 实施中改掉的三处原设计

1. **测试库用 PGlite，不是 pg-mem**。pg-mem 对 `jsonb`、表达式唯一索引、`for update`、`interval` 只支持一部分，
   用它测出来的"通过"没有意义。PGlite 是把真 Postgres 编译成 WASM，进程内跑，语义一致且不需要 Docker。
2. **不引 ORM，也不引 Redis**。查询不到 20 条，schema 就是一张 SQL，评审一眼看完；
   榜单走 PG 复合索引，读 QPS 极低，多一个 Redis 只是多一份运维。切换点写在代码注释里，不是忘了。
3. **`saves.state` 不做字段级校验**。原方案写"zod 全量校验 GameState"，实施时判断这是过度耦合：
   服务端一旦校验 210 个字段，每加一个玩法就要改服务端。改为只校验信封，等 `core` 定稿后再加可选严格模式。

### 13.3 测试抓到的真 bug

`verifyPassword` 遇到损坏的散列串（例如库里被改坏的记录）会抛 `RangeError: Invalid scrypt params`，
在登录接口上表现为 500。修法是**先验参数范围再交给 scrypt**（N 必须是 2 的幂且在 1024~2^20，r∈[1,32]，p∈[1,16]，
keylen∈[16,128]），并包 try/catch 返回 false。
这类"只在脏数据下出现"的路径，靠手点永远测不出来。

### 13.4 还没做（仍按原批次）

- **结局重放校验**：现在只做到"改分无用"，没做到"过程可信"。等 `packages/core` 落地后用 `{seed, commands}` 重放，`verified` 才置 true。（P4b）
- 内容版本下发 `/content/version`、运营后台、Sentry、备份演练、多实例限流上 Redis。（P5/P6）
- 前端还没接云存档：`apps/web` 属 P3，目前仍是单机 localStorage。

### 13.5 怎么验

```bash
cd apps/api
npm test          # 53 项，含跨账号隔离、版本冲突、旧档导入、同分排序
npm run typecheck
docker compose up -d --build && curl -s localhost:8787/healthz
```

无库直连时的降级也验过：`/healthz` 返回 503 `db_unreachable`，其余路由 404/401 正常，进程不崩。
