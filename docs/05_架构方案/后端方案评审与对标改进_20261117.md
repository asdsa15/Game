> 日期：2026-11-17

> 方法：先核对代码事实，再评审架构，最后对照四个开源项目给出"加什么、改什么、不做什么"。

## 一、结论先说

**原方案的形态判断是对的，路线顺序也是对的。但它的第一条论据不成立，且漏掉了一次前置重构。**

| 维度 | 评价 |
|---|---|
| 形态选择（B 混合架构） | ✅ 正确。理由充分，与"单批回退"的工程习惯一致 |
| 六步顺序（S1 存档 → S2 论道 → S3 世界层） | ✅ 正确。先做不碰逻辑的两步，风险最低 |
| "前端权威、后端只存不算" | ✅ 正确。但也因此**云存档不能是整包覆盖**（见 3.3 硬伤二） |
| "静默降级、断网可玩"铁律 | ✅ 正确。这是 B 形态能活下去的唯一保障 |
| **"`require('./wxcs3-game.js')` 直接复用逻辑"** | ❌ **不成立。见 3.1，这是最大的低估** |
| "209 条断言" | ⚠️ 过时。实测 **263 条**，dist 也是 **764KB** 不是 649KB |
| 世界按"月"推进 | ⚠️ 与代码不符。v8.0 已月拆三旬，世界 tick 应对齐到**旬** |
| 存档冲突处理 | ❌ **缺整章**。整包覆盖 = 静默丢档 |

一句话：**方向不用改，开工前要先补一次"逻辑与 DOM 解耦"的重构，否则后端只能靠沙箱硬跑。**

## 二、先核对事实：六处与代码不符

评审前我把三文件、八个测试、data.js 的关键表都跑了一遍。以下是可以直接对账的差异：

| # | 原方案说法 | 实测 | 影响 |
|---|---|---|---|
| 1 | `require('./wxcs3-game.js')` 直接复用 | 文件结尾是 `})(window)`，IIFE 挂到 `window.WXCS3`，**不是 CommonJS 模块**，`require` 会抛 `window is not defined` | S1/S3 的复用方式全错，见 3.1 |
| 2 | 209 条断言 | 八个测试文件实际 **263 条**全绿 | 回归基线比方案以为的更宽，是好事 |
| 3 | 649KB dist | `mobile/dist/index.html` = **781,951 字节（764KB）** | APK 体积口径要更新 |
| 4 | 世界层按月推进 | v8.0 已"月拆三旬"，`S.xun` ∈ {0,1,2}，有独立 `advanceXun` | 世界 tick 粒度应同步到旬，否则玩家过一句、世界过一月 |
| 5 | `game.js` 是"纯 JS，天然可在后端复用" | 规则里混着 **60 处** DOM/存储调用（`document.` 40 + `localStorage` 17 + `window.` 3） | 不是"天然"，是需要拆 |
| 6 | 世界层用 `NPC_POOL` 演化 | `NPC_POOL` 只有 **12 人**、`EVENTS` **38 条** | 12 人撑不起"世界简报"，两三个月就会重复撞车 |

另有两项对世界层很关键、方案没提的事实：

- **59 处 `Math.random`**（实际 60 处，分布在 59 行），无种子、无注入点。世界层一旦跑起来，**不可复现、不可对账、不可回放**。
- **7 处当前时间读取**（`Date.now` 4 处 + `new Date(` 3 处），且存档 `envelope` 只带 `format / version / savedAt / state`，没有 `revision`。多端同步时无法排序。

## 三、架构评审

### 3.1 最大低估：不是"搬个地方跑"，是先解耦

原方案说"逻辑迁移只是把 game.js 搬个地方跑"。测试文件的做法可以说明真实成本：

```js
// tools/test_v80.js 第 8~53 行
function makeEl(id) { /* 30 行 DOM 桩 */ }
const document = { readyState:'complete', getElementById(){...}, ... };
const localStorage = { getItem(){...}, setItem(){...} };
const window = { document, localStorage, matchMedia(){...}, ... };
const ctx = { window, document, localStorage, console, Math, ... };
vm.createContext(ctx);
vm.runInContext(fs.readFileSync('wxcs3-data.js','utf8'), ctx);
vm.runInContext(fs.readFileSync('wxcs3-game.js','utf8'), ctx);
```

也就是说：**现在能在 Node 里跑，靠的是 30 行桩 + `vm` 沙箱，不是模块化。** 这两件事差别很大：

| 做法 | 能跑 | 代价 | 问题 |
|---|---|---|---|
| 后端每请求 `vm.runInContext` 两个文件 | ✅ | 每次约 40 万字符重新解析 | 玩家状态 `S` 是模块内私有变量，**每个请求都要重放一次读档**才能续上；并发两人即互相污染 |
| 抽一层 `wxcs3-core.js`（纯规则、无 DOM） | ✅ | 1~2 天重构 | 一次投入，之后前后端同一份规则、同一套断言 |

**建议：把"解耦"提为 S0，排在云存档之前。** 具体三件事：

1. **DOM 收敛**：`document.*` / `localStorage.*` 全部改走一个 `platform` 适配层（浏览器实现 / Node 实现）。60 处不是 60 个地方改，是 60 个调用点换成一个对象的方法。
2. **状态外置**：`let S = null` 改为 `createEngine(state)` 返回实例，`S` 挂在实例上。这样后端能"一个玩家一个实例"，不需要重放读档。
3. **随机注入**：60 处 `Math.random` 收敛成 `engine.rng()`。传 `Math.random` 就是现在的行为，传种子化 PRNG 就变得可复现。

**这一步不做，S3 世界层写完也没法验**——世界跑出来的结果无法复现，出问题只能猜。

### 3.2 成立的部分（不用改）

- **分层原则**"玩家手里的账在前端算，玩家之外的世界归后端管"——这句话是整个方案最值钱的一句，比任何技术选型都重要。
- **降级铁律**：`api.js` 全部静默降级、任何断言不得依赖后端。这条让 B 形态可以随时退回 A。
- **回退点设计**：S3 整目录可删、`api.js` 未接通时与 v8.0 逐字节等价。工程上干净。
- **技术选型**：Node（同语言）、SQLite（单文件）、REST（够用）、OpenAI 兼容接口（可换本地模型）。四项都合理。

### 3.3 三个硬伤

**硬伤一：NPC 会分裂成两套。**

前端遇见 NPC 靠 `NPC_POOL` 抽（`npcMeet`），后端演化 NPC 靠自己的表。两边各存一份，同一个"顾清玄"会有两个境界、两段关系。这不是同步问题，是**数据主权问题**。

而且冲突比看上去更直接——NPC 的**存活状态**就存在玩家存档里：

```js
// L3719  /  L3892
const rec = S.npcs[n.id] || (S.npcs[n.id] = { fav: 0, met: false });
if (r.alive === undefined) r.alive = true;   // ← 生死在存档里
```

也就是说：后端世界层判定「顾清玄已经坐化」，玩家老存档里 `alive` 仍是 `true`，读档后他照样出现、照样对话。**两个世界各跑各的，玩家会觉得世界在骗他。**

对策：把 NPC 分成两类字段，边界划死：

| 归谁 | 字段 | 规则 |
|---|---|---|
| **世界层（后端）** | 境界、年龄、生死、所属势力、与势力关系 | 单一事实源，玩家只读 |
| **玩家存档（前端）** | `fav`（好感）、`met`（是否见过）、`pendingMeet`、与玩家的恩怨 | 只增不改，后端不碰 |

实现上：`S.npcs[id]` 只保留玩家侧四五个字段，境界/生死改为"读档时向世界层取一次当前快照"。这样同一个 NPC 只有一套客观状态，`alive` 不再有两份。NPC **静态定义**仍保持 `wxcs3-data.js` 的 `NPC_POOL` 为唯一来源（同语言，后端直接读同一个文件，这是 B 形态真正的红利）。

**硬伤二：云存档整包覆盖 = 静默丢档。**

现在槽位存的是 `JSON.stringify(envelope(S))`——整包。手机存一次、电脑存一次，后写的把先写的整包盖掉，中间那局白玩，且**没有任何提示**。

对策：字段主权划分见 A4；执行细则见 5.A4 与 8 节最后一条。

**硬伤三：世界简报会撞车。**

`EVENTS` 只有 38 条，且是静态表（`eventSlot` 按长度均分抽取）。如果后端每月从这 38 条里挑几条当"山下发生了……"，玩家玩到第 5 年就会开始读重复段落，且**同一件事会在不同年份重复发生**——世界的"历史感"立刻崩。

对策：简报不能复用 `EVENTS`，要**独立事件池 + 去重 + 冷却**（见 5 节 B1）。

## 四、对标四个项目：能加什么、要改什么

我按"能不能直接抄"排序，四个项目各取一个最有用的点。

### 4.1 斯坦福 Generative Agents —— 抄它的"记忆流 + 反思"

**它做了什么**：每个智能体有一个"记忆流"，记忆以自然语言逐条存储，带四个字段：创建时间、最后访问时间、重要度（1~10）、向量。检索时按 **recency（指数衰减）× importance（静态分）× relevance（余弦相似度）** 三路加权打分，归一化后相加取 top-k。当累计重要度超过阈值，触发一次"反思"，把零散记忆合成高层认知（"我最近似乎在回避社交"），反思结果本身也写回记忆流。LangChain 的实现里这个阈值默认是 150，重要度权重给 0.15 [ref_web_a04cebc9962b8b5c65e459a8][ref_web_c59e3a90853a5dd275271491]。

**对本项目意味着什么**：现在的论道（`ACT.do_free` + `INTENTS` 30 类意图匹配）是**无状态**的——NPC 不记得上次跟你说过什么，玩家问第二遍会得到同样的回答。这是当前"文字系统"最像机器的一处。

**建议增（对应原方案 S2 的升级）**：

| 现状 | 建议 |
|---|---|
| `INTENTS` 意图匹配，无记忆 | 每个 NPC 一个 `memory[]`，对话后写一条摘要（主体+动作+对象+地点，不要代词） |
| 无重要度 | 写入时给 1~10 分。可先用规则打分（谈及恩怨/境界/生死给高分），LLM 可选 |
| 无检索 | 论道时取 top-3 相关记忆拼进 prompt；**纯规则也能用**——按"关键词重叠 + 重要度 + 新近度"打分即可 |
| 无反思 | 每累计 N 条记忆提炼一句"他对你的看法"，写回记忆流 |

**关键取舍：先做规则版，不接向量。** 12 个 NPC、每人数百条记忆，关键词 + 重要度 + 新近度三路打分足够，不需要 embedding。等 NPC 上百、记忆上万再考虑向量库——原文作者的实测结论是"记忆超过一万条就必须换检索方案"，本项目远未到 [ref_web_a04cebc9962b8b5c65e459a8]。

另外一条必须抄的：**记忆要能压缩**。同一主题的低分记忆定期合并成一条摘要，否则记忆条数线性膨胀、检索质量下降。原文给的阈值是"重要度低于 4 且超过游戏内两天" [ref_web_a04cebc9962b8b5c65e459a8]。

### 4.2 AI Town —— 抄它的"人类与 AI 同一输入通道"

**它做了什么**：a16z 与 Convex 合作的开源小镇，四层架构——游戏规则层（世界/玩家/对话的数据模型与输入处理）、游戏引擎层（按 tick 推进，每秒 60 tick、每秒落库一次）、智能体层（调 LLM 生成台词、总结记忆、检索记忆）、渲染层（PixiJS）[ref_web_08717b580105c07d7e40a020]。整个引擎跑在后端，世界推进由调度器驱动，所有观看者看到同一个实时世界 [ref_web_63202b6f475353687a0752e7]。记忆以 embedding 存库、向量检索 [ref_web_899caed7f97ad34e7c6c3d53]。

**最值得抄的一点，不是它的技术栈，是这条设计**：

> 人类玩家和 AI 角色走的是同一条"输入"通道，所以你往里加玩法时，两边都能用。[ref_web_08717b580105c07d7e40a020]

**对本项目意味着什么**：原方案的设计是"前端算玩家的、后端算世界的"，两套逻辑、两条通道。这会带来一个长期成本：**每加一个新玩法（比如"宗门征讨"），都要在前端和后端各实现一遍**。

**建议改（这是我对原方案唯一的结构性修改意见）**：

不要让"玩家动作"和"世界动作"走两套代码，而是让世界层**复用同一个 reducer**：

```
玩家动作（前端算）──┐
                    ├─→ 同一份规则函数（wxcs3-core.js）→ 同一份事件流
世界动作（后端算）──┘
```

具体落地很轻：世界层的 `orgs.js` / `npc.js` 不自己实现"突破""结仇""扩张"，而是**调用 core 里已有的函数**，只是把主语从玩家换成 NPC。这样做的好处是：

- 世界演化和玩家体验的数值口径天然一致（不会出现"NPC 突破比我容易"的割裂感）；
- 加新玩法只写一次；
- 世界层的事件可以直接进 `EVENTS` 的三段式结构（`text` / `after` / `log`），前端零改动就能渲染。

顺带抄两个小设计：
- **冻结按钮**：UI 上一个按钮把整个世界暂停 [ref_web_08717b580105c07d7e40a020]。本项目对应的是"世界跟玩家节奏走"，等价但要显式做（见 5 节 B5）。
- **闲置自动暂停**：页面闲置 5 分钟模拟自动暂停 [ref_web_08717b580105c07d7e40a020]。这正好回答原方案第 2 个决策点——**世界不该在玩家离线时狂跑**。

### 4.3 炎黄群侠传 yhmud —— 抄它的"AI 服务独立进程"

**它做了什么**：FluffOS 驱动的中文武侠 MUD，MIT 协议，目录按 `cmds` / `inherit` / `kungfu` / `world` / `adm` 分离，AI 是一个**独立的 Python 服务**，有自己的 `.env`、自己的启动脚本（`ai/run.sh start|status|logs|stop`）、自己的日志目录 [ref_web_e6969d448e5f7c0baecc4303]。

**它明确写的一句，正好是原方案 A8 承诺的更强版本**：

> 智能 NPC 与场景描写：可选 AI 服务支持 NPC 对话与答疑……**未启用场景创作时仍可正常探索**。

**对本项目意味着什么**：原方案的 LLM 降级是"同一进程内的开关"（`llm.js` 里 try/catch 回退 `INTENTS`）。这不够干净，因为：

- LLM 调用有超时（几秒到几十秒），会拖住整个 Node 事件循环之外的东西；
- key 配错、额度用尽、模型改版，都会让主服务反复踩同一个坑；
- 无法单独重启 AI 而不重启游戏服务。

**建议改**：LLM 做成**独立进程 + 独立配置**，主服务只做 HTTP 代理转发。

```
server/          主服务（存档/世界/简报），永不因 LLM 挂掉
llm-service/     独立进程，独立 .env，独立日志，可单独启停
```

主服务调不通 `llm-service` 时，直接返回"规则层结果"，连超时都不用等。这比原方案的"同进程 try/catch"稳一个档位，且和 yhmud 的成熟做法一致。

**顺带抄它的 AI 治理**：`ai/config/npc_roles.json` 把"NPC 身份与对话风格"从代码里抽成配置 [ref_web_e6969d448e5f7c0baecc4303]。本项目 `NPC_POOL` 里已经有 `inner`（内心）、`approach`（相处之法）、`taboo`（忌讳）三个字段，可以直接生成这份配置——**别在 prompt 里硬编码人格**。

### 4.4 PocketBase —— 把 S1 的人力省下来

**它做了什么**：Go 写的单二进制后端，内含嵌入式 SQLite、实时订阅（**用 SSE，不是 WebSocket**）、内置认证（邮箱密码 / OAuth2 / MFA / 免密）、文件存储、Admin 后台 UI、自动生成 REST API [ref_web_960f9900bada0efd6ee4f63b][ref_web_6942744ba54f196f34c1c683]。

它解决 SQLITE_BUSY 的做法值得知道：**双库（data.db + auxiliary.db）+ 写操作走单连接池串行、读操作走多连接池并发**，事务内两个池指向同一个 TX 保证原子性 [ref_web_a09b9a767779d0dbad69d19f]。

选 SSE 而不是 WebSocket 的理由也很实在：能穿过所有代理和防火墙、浏览器 `EventSource` 自带重连、服务端就是一个长 GET [ref_web_a09b9a767779d0dbad69d19f]。这和原方案"REST 为主、SSE 可选"的判断一致，但 PocketBase 是**白送**。

**对本项目的意义**：原方案 S1 是"后端骨架 + 云存档（账号/多槽/多端同步），1~2 天"。这一两天里，真正花时间的不是写 `save.js`，是**账号体系 + 迁移脚本 + 后台排查工具**——而这三样 PocketBase 全都有。

| 原方案 S1 的活 | 用 PocketBase |
|---|---|
| 写 `server/index.js` 骨架 | 不需要，`./pocketbase serve` |
| 写 `db.js` SQLite 封装 | 不需要，集合直接在 Admin UI 建 |
| 账号体系（若部署到 NAS/云） | 内置，含 JWT / 刷新 / 密码重置 |
| 多槽存档表 + REST | 建个 collection，API 自动生成 |
| 出问题怎么查 | 内置 Admin UI + 实时日志查看器 |
| 换机迁移 | `data.db` 一个文件拷走 |

**建议**：S1 用 PocketBase 做底座，`server/` 里只留真正的业务逻辑（世界层、简报生成、LLM 代理），用它的 JS hook（`pb_hooks/*.pb.js`）或 Go 扩展挂上去。**把省下的一天半挪给 S0 的解耦重构。**

需要说清楚的代价：PocketBase 是**单节点**架构，不适合高并发写、不能水平扩展、跨集合没有 JOIN [ref_web_a09b9a767779d0dbad69d19f]。本项目是单机/家用 NAS 规模，这个代价可以接受；如果哪天真要多人，那时也该换 PostgreSQL 了，不是 PocketBase 的问题。

### 4.5 附带一条：LLM 调用必须有硬闸门

参考一个多智能体小镇的实践，它把失控防控做成四道**代码层**闸门（不依赖模型自觉）[ref_web_70d440e8d6ae257809b6faed]：

| 闸门 | 作用 | 本项目的值（建议） |
|---|---|---|
| `MAX_TICKS` | 单次世界推进上限 | 一次请求最多推进 3 旬（=1 月） |
| `MAX_ACTIONS` | 单实体单 tick 行动上限 | 单个 NPC 每月最多 2 次决策 |
| `MAX_DIALOG_TURNS` | 单次对话轮次上限 | 论道一次最多 6 轮 |
| `TOKEN_BUDGET` | 全局 token 硬顶，超则熔断落盘 | 每日 N 次 / 单次 ≤ 2k token |

原文给的一个反面清单正好对应本项目风险：**无限对话循环、记忆爆炸、死循环计划、token 烧穿、谣言滚雪球（一个 NPC 的幻觉被他人采信放大）**[ref_web_70d440e8d6ae257809b6faed]。最后一条对"NPC 互相传播世界事件"的设计尤其致命——**必须有一个事实校验层：LLM 生成的内容只能进"描述"，不能进"数值与状态"**。

## 六、路线重排

原方案 S1~S6 的顺序我保留，只插一个 S0、调三处粒度：

| 步 | 内容 | 原方案 | 修订 | 量级 | 验收 |
|---|---|---|---|---|---|
| **S0** | 逻辑与 DOM 解耦（platform / createEngine / rng） | — | **新增** | 1~2 天 | 263 断言全绿；`game.js` 里 0 处直接 `document`；同一 state + 同一 rng 种子 → 逐字段相同结果 |
| **S1** | 云存档（PocketBase 底座 + rev 冲突检测） | 1~2 天 | 改底座、加冲突 | 1 天 | 两端交替存 20 次，无一次静默丢档；后端不可达时游戏行为与 v8.0 逐字节等价 |
| **S2** | LLM 论道（独立进程 + 四闸门 + 规则回退） | 1 天 | 改进程模型 | 1.5 天 | 杀掉 llm-service，论道仍可用（走 INTENTS）；单次超 2k token 熔断 |
| **S3** | 世界层规则 AI（tick 按**旬** + 复用 core reducer） | 3~5 天 | 改粒度、改复用 | 4~6 天 | 推 120 旬，NPC 无"境界倒退/年龄不增/关系自相矛盾"；同种子可复现 |
| **S3.5** | NPC 记忆流 + 反思（规则版） | — | **新增**（原属 S2 的增强） | 2 天 | 问同一 NPC 同一问题两次（中间隔 10 旬），第二次能引用第一次 |
| **S4** | 世界简报（独立事件池 + 去重 + 冷却） | 1~2 天 | 加池与冷却 | 2 天 | 连推 10 年（120 月），简报无重复事件；每条简报能追到世界层的事件 id |
| **S5** | 排行 / 多角色 / 仙谱 | 2 天 | 不变 | 2 天 | — |
| **S6** | （远期）逻辑迁移评估 | 视野心 | 不变（S0 已做了大半） | — | — |

**总量重估**：原方案 1~2 周，修订后 **2~3 周**。多出来的一周里，S0 是纯投资（换来后面三步都能验），S3.5 是可选加项（不做也不阻塞）。

## 七、三个决策点（修订原方案）

原方案让我拍三个板。我的建议：

**决策 1 · 选哪个形态？**
→ **B，但前面加 S0。** 不加 S0 的 B 会在 S3 卡住（世界不可复现、不能一人一实例）。

**决策 2 · 世界时钟怎么走？**
→ **跟玩家，且粒度到旬，且要能暂停。** 原方案"跟随玩家"的判断对，但要说清三件原方案没说的：
- 粒度对齐 `S.xun`（0/1/2），不是月；
- 玩家离线超过 N 小时 → 世界挂起（B5），回来时补一份"这段时间山下发生了……"的**摘要**而非逐旬明细；
- 世界事件的**数值影响必须有上限**：物价 ±15%、历练风险 ±1 档，不能出现"闭关三年回来宗门没了"。原方案 `tickMarket` 的 `clamp(0.7, 1.5)` 是个好先例，照抄这个思路。

**决策 3 · 部署目标？**
→ **先 localhost，架构上留好 NAS 的口子。** 具体：PocketBase 监听 `127.0.0.1` 起步，配置里留 `--http=0.0.0.0:8090` 的开关；鉴权用 PocketBase 内置（不要自己写），这样从"本机玩"到"挂 NAS 给家人玩"是改一个启动参数，不是改一套代码。

## 八、风险清单（在原方案 4.2 之上补五条）

| 风险 | 说明 | 对策 |
|---|---|---|
| **S0 重构把 263 断言改坏** | 解耦要动 `S` 的持有方式，最容易伤到"读档后 `G.S` 引用失效"这类隐蔽点（测试文件第 55 行就有一句专门注释提醒这事） | S0 单独一批、单独回退；每改一个模块跑一次全量 263 |

| **NPC 生死与老存档冲突** | 玩家几个月前存的档里 `alive === true`，世界层已判其坐化 | 读档时以世界层为准并给一次提示（"你听说顾清玄已于去年坐化"）；这是叙事机会，不是 bug |

## 九、一句话总结

原方案 **"B 形态 + 渐进六步"的判断成立**，但它把"复用 JS 逻辑"当成了免费红利——实际上要付一次 `S0 解耦` 的入场费。
补上 S0、修好存档冲突、把世界 tick 对齐到旬，再抄四样东西：**GA 的记忆流**（让 NPC 记得你）、**AI Town 的同一输入通道**（让世界复用玩家规则）、**yhmud 的独立 AI 进程**（让 LLM 挂了不拖累游戏）、**PocketBase 的单二进制底座**（把 S1 的一天半省下来）。这样 B 形态不只是"便宜的路"，还是一条**能一直走到 C 的路**。
