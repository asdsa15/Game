# 源码拆分评估：三个文件会不会太臃肿

> 日期：2026-11-18
> 性质：**评估与方案，本轮不动结构。**
> 触发：v9.0 M0 提交后（`90c0487`），`wxcs3-game.js` 已达 **10523 行 / 437KB**。

---

## 一、结论先说

**会臃肿，但不该按"文件数"去拆，该按"改动半径"去拆。**

三句话：

1. **单文件大小本身不是问题。** 10523 行对 JS 引擎没压力，对启动没影响（一次解析 437KB 是毫秒级）。真正的问题是**你改一处要读多少上下文**。
2. **现在就拆整个文件，是高风险的错事。** 实测 **69% 的函数直接读写全局 `S`**，403 个内部函数互相调用、共享 210 个 `S` 字段。硬拆要动 2786 处引用，而 `test_v80` 里有一句注释专门提醒过这类坑：`读档会把模块内的 S 换成新对象，所以这里不能一次性捕获引用`。
3. **有一条便宜且当下就该走的路**：不拆文件，先拆**数据**。你已经做了——`wxcs3-data.js` 独立出来是对的，继续往这个方向走，收益最大、风险最低。

**推荐：现在只做"新代码分文件"，不动老代码。** 具体见第四节。

---

## 二、先把事实摆出来

### 2.1 实际体量

| 文件 | 行数 | 体量 | 性质 |
|---|---|---|---|
| `wxcs3-game.js` | **10,523** | 437 KB | 全部规则 + 全部 UI 渲染 |
| `wxcs3-data.js` | 3,316 | 163 KB | 纯数据表（81+ 张） |
| `wxcs3-art.js` | 35 | 1.2 KB | 插画兜底 |
| `问道长生v6.html` | 687 | 34 KB | CSS 与骨架 |

`game.js` 一个文件里装着 **76 个分节**，最大的几段：

| 行数 | 分节 |
|---|---|
| 768 | 战斗 |
| 699 | 行动 |
| 698 | 情缘 |
| 482 | 历练 |
| 448 | 奇遇结算 |
| 443 | 坊市卖出 |
| 404 | 全局绑定（dispatch / render） |
| 402 | 环形指令盘 |

### 2.2 耦合度（这才是关键数字）

| 指标 | 实测 |
|---|---|
| 内部函数 | 403 个 |
| `ACT` 入口 | 169 个 |
| `S.xxx` 字段访问 | **2,786 处** |
| 被引用的 `S` 字段种类 | **210 个** |
| 直接读写 `S` 的函数块占比 | **69%** |

**这组数字说明什么**：`S` 是全局单例，几乎每个函数都直接读写它。这是典型的"共享可变状态"架构，不是"模块化"架构。

---

## 三、为什么"现在就拆"是错的

### 3.1 拆文件不会降低耦合，只会把耦合藏起来

如果把战斗拆到 `combat.js`，它仍然要读 `S.hp`、`S.mp`、`S.preBuff`、`S.combat`、`S.stats`……拆完你得到的是**四个都依赖全局 `S` 的文件**，而不是"低耦合的模块"。

代价却实打实：

- `wxcs3-game.js` 是一个 IIFE，内部函数靠闭包共享。拆成多文件后，要么挂到全局（污染），要么改成模块（要动构建链）。
- **最危险的一处**：`S` 是模块内 `let` 变量，读档时 `S = out` 换对象。`test_v80.js` 第 55 行那句注释就是为此写的。拆文件后若有人缓存了 `S` 的引用，**读档后所有写操作会写到旧对象上，且不报错**。这类 bug 极难查。
- 你现在的构建链是「HTML + 两个 JS 内联成单文件」。拆成 N 个文件，`mobile/build.py` 要改，`desktop/sync-app.js` 要改，**dist 和 APK 两条产物会同时受影响**。

### 3.2 而"够用"的门槛还没到

客观说，**一万行的单文件在单人项目里是可维护的**。判断标准不是行数，是：

| 你的实际痛点 | 是否成立 |
|---|---|
| 改一处要读整份文件？ | ❌ 不成立。你有 `项目地图.md` 索引，能定位到函数 |
| 找不到东西？ | ❌ 不成立。76 个分节注释 + 403 个函数索引 |
| Git 冲突？ | ❌ 不成立。单人开发 |
| 改 A 弄坏 B？ | ⚠️ **这才是真痛点**，但拆文件治不了它——治它的是测试（已有 430 项） |
| 改一处要翻 3 个文件？ | ❌ 现在**恰好相反**：都在一个文件里，反而好翻 |

**真正在痛的不是"文件太大"，是"一个文件里同时有规则和 UI"。** 这两件事混在一起，才导致你改一个数值要去读渲染代码。

## 四、推荐路径：分层，而不是分文件

按"改动半径"排序，四步，**每一步都独立可回退**。

### 第 1 步（现在就该做）· 新代码分文件，老代码不动

**规则：从现在起，新功能一律写进独立文件，通过 `window.WXCS3_EXT` 注册。**

```
wxcs3-data.js     纯数据（已有，继续）
wxcs3-game.js     老代码，冻结增长（只修 bug）
wxcs3-ext-beast.js    御兽
wxcs3-ext-trib.js     天劫五道
wxcs3-ext-disciple.js 师徒/道统
wxcs3-ext-relic.js    遗迹
```

好处：**零风险**（不动老代码）、**立刻止血**（新代码不再堆进 10k 行的文件）、**构建链只加一行**（`build.py` 的 `scripts` 数组多 push 几个）。

成本：约半小时改 `build.py`，之后每个新功能自动分文件。

### 第 2 步 · 把"纯计算"从 UI 里摘出来

这是**唯一真正解决"规则和 UI 混在一起"的动作**，而且不需要拆成很多文件。

识别标准：**不碰 `document`、不碰 `render()`、只吃参数返回数值**的函数，抽到一个 `wxcs3-rules.js`。

比如现在已经很干净的那些：

```js
computePower()      // 只读 S，返回数字
keMul()             // 纯函数
beastAtkBonus()     // 纯计算
beastBondTier()     // 查表
discipleStageOf()   // 查表
costLine()          // 纯格式化
```

这类函数有个特征：**好测**。它们本来就不需要 DOM 桩。抽出来之后，测试可以脱离 `vm` 沙箱直接跑，快得多。

预计第一步能摘出 **30~50 个函数、约 800 行**，风险极低（纯函数搬家，行为不变）。

### 第 3 步 · 按"改动频率"分，不按"功能类别"分

这是个反直觉但很实用的原则。观察你的提交历史：

| 频繁改动 | 几乎不动 |
|---|---|
| 数值平衡（`data.js`） | `applyState` 存档迁移 |
| 文案（`data.js`） | `dispatch` 路由 |
| 单个玩法 | `boot` / 渲染骨架 |

所以更该关注的是：**把"会频繁改的"和"很少改的"分开**，让你每次改数值时只需要碰 `data.js`。这一点你已经做到了，`data.js` 独立是整套设计里最正确的决定。

### 第 4 步（等真痛了再做）· 真正拆 `game.js`

触发条件（满足任一再动手）：

- 单文件超过 **2 万行**；
- 出现**第二个人**一起改（会用 Git 冲突来告诉你）；
- 你要做**S0 解耦**（上一轮后端方案里那个前置重构）——那时反正要动 `S` 的持有方式，顺手拆是免费的。

拆法建议（按依赖方向，不是按功能）：

```
wxcs3-core.js     纯规则、无 DOM、不碰 render   ← 可后端复用
wxcs3-state.js    newGame / applyState / 迁移
wxcs3-render.js   全部 render* / panel / modal
wxcs3-actions.js  ACT.* （169 个入口）
wxcs3-boot.js     dispatch / boot / 事件绑定
```

关键：**`core` 不依赖其他任何层**，`render`/`actions` 依赖 `core`。这样 `core` 将来能直接在 Node 里跑（对应后端方案的 S0）。

## 五、如果现在就拆，会付出什么

供你权衡。假设把 `game.js` 一次拆成 5 个文件：

| 项 | 影响 |
|---|---|
| 要动的代码 | `S` 引用 2786 处（多数不用改，但要确认作用域） |
| 最易出的 bug | 读档后 `S` 换对象，某文件缓存了旧引用 → **静默写错对象** |
| 构建链 | `build.py`、`sync-app.js`、`desktop/main.js` 三处要同步改 |
| 产物 | dist 单文件、APK、Electron 三条线要重新验收 |
| 回归面 | 430 项断言要全跑一遍，还要人工验 390px 手机端 |
| 预计耗时 | **2~3 天**（含排错），且这段时间不能开发新玩法 |

**对比第 1 步的耗时：半小时，且不影响任何开发。**

所以我的建议很明确：**先做第 1 步止血，第 2 步慢慢摘纯函数，第 4 步等真痛了再说。**

## 六、一个反例：什么时候"单文件"反而是对的

如果你打算**继续做单机、单人维护、走单文件分发**（双击即玩 / APK），那单文件其实是最优解：

- 玩家拿到的是一个 `.html`，不需要 node_modules、不需要构建；
- 你能在任何机器上双击就跑，包括没装 Node 的电脑；
- 分发、备份、发朋友，一个文件搞定。

**这恰恰是这个项目现在的形态**（`dist/index.html` 单文件、APK 内嵌、Electron 也吃单文件）。

所以更准确的表述是：

> **不是"三文件太臃肿"，而是"源码组织"与"分发形态"被绑在了一起。**
> 源码可以拆，只要构建时还能内联回单文件——而你的 `build.py` 天然支持这件事（它本来就是拼接器）。

这句话是整件事的关键：**拆分源码不会破坏单文件分发**，因为内联发生在构建期，不在运行期。

### 一个必须记下的判据

评估时我用「不碰 DOM + 不写 `S`」筛出 94 个候选，但逐个核对后发现**大部分会通过闭包间接读 `S`**：

| 函数 | 看起来纯 | 实际 |
|---|---|---|
| `currentGoal` | 只调 `goalsForLine` | `goalDone` 内部读 `S.goals` |
| `dArtUpkeep` | 只是求和 | `dArtRaw` 读 `S.dArt` |

> 判断一个函数能不能搬，不看它自己写了什么，看它**调用链上还有谁在读 `S`**。

所以 `currentGoal`、`deflectOf`、`fixedCostList` 这类看起来干净的函数，**继续留在 `game.js`**。等将来真正做 S0 解耦（把 `S` 改成参数传入）时，它们才会自然变成可搬的。

## 九、一句话总结

**结论不是"要不要拆"，而是"拆什么"。**

- 拆**数据**（已做）→ 收益最大；
- 拆**纯规则**（可做，低风险）→ 顺带让代码能上后端；
- 拆**文件数量**（现在别做）→ 只把耦合藏起来，却要付 2~3 天回归。

**现在该做的是第 1 步：让新代码不再往 10k 行的文件里堆。** 半小时的改动，换来之后每个新玩法都自动分文件——这比"等攒到两万行再大拆一次"便宜得多。
