## 一、结论先行

这个项目的界面问题**不在"不好看"，而在"该看见的看不见、不该出现的挡着路"**。

具体说，有五个真问题按严重度排列：

**第一个是硬 Bug：ESC 键对任何弹窗都无效。** `wxcs3-game.js:10116` 的守卫条件 `document.getElementById('modals').innerHTML` 会在弹窗打开时提前 `return`，而 ESC 分支在 `:10121`——永远执行不到。玩家关弹窗只能点遮罩或滚到底找"关闭"按钮。修这一行就好。

**第二个是右栏有一段状态被渲染了两次。** `wxcs3-game.js:1131-1134` 与 `:1140-1143` 两段代码调用同一个 `G.WXCS3_EXT.stateExtras()`，中间只隔一条 `divider()`。玩家会以为是两套状态或数据错乱。

**第三个是全局最常见的文字形态达不到无障碍标准。** 面板标题是 13.5px 白字压在 `--jade #5E9689` 上，对比度 3.39:1；主按钮白字压 `--gold #B8912F` 只有 2.95:1。每个面板都有这个标题，也就是说**整个界面的标题栏在低亮度屏上都是糊的**。

**第四个是桌面版发布产物是旧的。** `desktop/app/index.html` 比 `mobile/dist/index.html` 少 158,939 字节，`opt--ico`（图标层样式）在桌面产物里是 `False`、`stateExtras` 是 0 处——桌面与 APK 玩家根本看不到刚做完的条目图标层。

**第五个是"看不见的变化"。** 进度条写了 `transition:width .25s`，但 `bar()` 每次都新建 `<i class="fill">` 节点（`wxcs3-game.js:745-747`），而整个界面是 `stage.innerHTML =` 整块替换（`:990`）。CSS 过渡需要同一元素的旧值→新值才触发，新插入的节点没有旧值。**气血、灵力、修为、寿元、香火五根条全部瞬间跳变**——玩家永远看不出"刚才那一打掉了多少血"。

对照真实项目可以确认这五点都不是设计选择，而是实现遗漏。开源项目 [Cult-Game](https://github.com/Katrina55553/Cult-Game)（同题材文字修仙，独立开发者完整实现）的做法是：数值变化用 `stat-flash-gain/loss` 双向色闪（绿涨朱跌）、进度条用 `bar-shimmer` 流光、境界突破用 `breakthrough-burst` 金光自中心扩散而非整块闪白、日志用 `ink-bleed` 逐行渗出、选项 hover 时一道墨迹自中心洇开。**这些都不需要额外美术资产，纯 CSS 就能做。**

## 二、对照基准：真实项目怎么做

调研了三个层次的参照对象，结论是它们在"文字修仙"这个品类上收敛出了相同的做法。

### 2.1 商业标杆：了不起的修仙模拟器（GSQ Games）

[Steam 页面](https://store.steampowered.com/app/955900/) · [wiki 图鉴](http://www.miandie.com/azyx/20838.html)

Steam 463 篇繁体中文评论，87% 好评。这个游戏的价值在于它证明了**修仙题材的界面重心不在画面而在信息组织**：

- **"看清规则"是它明确列出的卖点**：界面里能直接看到五行风水的克制关系，而不是让玩家猜为什么炼丹失败
- **角色有名有姓有隐秘**：NPC 不是功能按钮，是有故事的人
- **"大道三千"**：功法各自有闪光点，不是一份数值表
- **成就系统 408 项**，把长线目标显性化

对本项目的直接启示：**规则可见性**比视觉装饰更值钱。当前的"异常：垂死"排在右栏第 20 位以后（勘察确认），这就是典型的规则不可见。

### 2.2 开源完整实现：Cult-Game（修仙模拟器）

[GitHub](https://github.com/Katrina55553/Cult-Game) · [在线试玩](https://katrina55553.github.io/Cult-Game/)

这个项目对本项目的参考价值最高——同题材、同为纯前端、且把视觉规范写进了代码。读它的 [index.css](https://raw.githubusercontent.com/Katrina55553/Cult-Game/main/src/styles/index.css) 与 [StatusPanel.tsx](https://raw.githubusercontent.com/Katrina55553/Cult-Game/main/src/components/StatusPanel.tsx)，有几处做法值得直接借鉴：

**一是动效分层，且全部有降级。** 它定义了一整套命名动效（`fade-up` / `pulse-glow` / `stat-flash-gain` / `stat-flash-loss` / `float-up` / `bar-glow` / `milestone-enter` / `breakthrough-burst` / `ink-bleed` / `spirit-rise` / `demon-creep` / `modal-in`），并在 `@media (prefers-reduced-motion: reduce)` 里**逐个关掉**。当前项目全局只有 3 个 `@keyframes`（`问道长生v6.html:180` spin、`:406` sceneart-in、`:649` achIn），且没有 reduced-motion 兜底。

**二是关键状态有专属告警形态。** 它的寿元剩余 ≤10 年时，整个寿元框进入 `animate-pulse-cinnabar` 朱砂脉动；心魔 ≥50 时该数值卡进入 `animate-demon-creep`（边框缓慢渗出墨色）。**不是换个颜色，是换一种动态语言。**

**三是数值变化双向可辨。** `AnimatedStat` 用 `useRef` 记住旧值，涨用绿闪、跌用朱跌、都在 600ms 内回落。当前项目所有数字都是静态刷新。

**四是色彩有明确的对比度预算。** 它的 token 里直接写了注释：`--color-mist` 原 `#6a7a72` 在墨底上只有 3.4:1，提亮后约 6.2:1；`--color-gold-dim` 已提亮到过 WCAG AA，用于小字也看得清。**它把对比度当成 token 的一部分来管，而不是事后补丁。**

**五是装饰有节制。** 它的 `scroll-panel`（四角描金）明确注释"只留给主叙事面板与起始页，其余面板不再叠装饰"。当前项目右栏 30 个信息块全部平铺，没有分组也没有层级。

**六是日志做了高亮分层。** 它有独立的 `logHighlight.tsx` 按语义切段着色，最新一条用描金左边线，旧的用青玉，且底部有渐隐遮罩暗示"还有更多"。当前项目的日志是纯文本流。

**七是纸张质感用 SVG 滤镜做，不是图片。** 它用 `feTurbulence` 生成颗粒与纤维两层噪声，`opacity:0.045` + `mix-blend-mode:overlay` 叠加。**零额外请求、零字节。** 当前项目是纯平色 `#FAF6EE`。

**八是留了主题切换口子。** `[data-theme="dunhuang"]` 覆盖 token 即可换整套配色，因为所有工具类都引用 `var(--color-*)`。当前项目的 22 个 CSS 变量没有这个结构。

**九是零资源依赖。** 它连图标都是内联 SVG/emoji，音效全部 Web Audio 程序化合成，字体自托管 woff2 子集。这对本项目最有价值的启示是：**很多"要花钱做"的效果可以用代码做出来。**

## 三、诊断：当前界面到底哪里不行

以下每条都有代码证据。勘察为纯只读，未改动任何文件。

### 3.1 布局与信息密度

**三栏列宽写死，880px 断点把主操作区压到最窄。**
`问道长生v6.html:46` 三栏 `272px minmax(0,1fr) 312px`；`:53` ≤1100px 变 `232px/1fr/272px`；`:56` ≤880px 单列。
900px 视口下中间栏只剩约 344px——而中间栏是**唯一放选项的地方**；1440px 视口下中间栏有约 710px，宽屏上 3 倍富余宽度被浪费在固定栏位上。

**右栏是"全部状态"的无折叠清单，约 30 个信息块。**
`wxcs3-game.js:1028-1176`：道号/年岁/境界/战力/主修、寿元条、道统、仙基/神通/箓/道途印/果位、修为/灵气/气血/灵力、神庙/信众/香火、锚定+四锚+崩解期、称号、六维、灵根、灵石行、人情、征兆、异常、好感列表。
312px 宽的列里没有任何分组折叠或分页，**玩家要滚过 30 行才能找到一项**；而"异常：垂死"这种最该被看见的信息排在第 20 位以后。

**右栏有一段状态被渲染了两次。**
`wxcs3-game.js:1131-1134` 与 `:1140-1143` 调用同一个 `stateExtras()`，中间只隔 `:1136` 的 `divider()`。已核实。

**指令坞「常用」行被拉伸到每个按钮 250~315px 宽。**
`问道长生v6.html:324-328` 的 `repeat(auto-fit,minmax(0,1fr))` + `:318` 的 `.dockrow{grid-column:1/-1}` + `:48` 的 `max-width:1340px` → dockrow 净宽 1288px；而按钮内部只有 29px 图标圆 + 12.5px 标题 + 11px 副标题。
**4 个常用按钮各占 314px，内容却只占约 70px，每个按钮有 3/4 是空白。** 真正需要信息密度的弹窗列表却挤成一条。

**坊市分类页把 13~19 个条目摊成一条无分页的滚动列表。**
材料页 19 项、法器页 13 项、丹药页 18 项全部挤在一个弹窗（`wxcs3-game.js:3973-3990` 渲染为单个 `<ul class="opts">`），无搜索/排序/价格过滤。

**弹窗一屏装不下，且标题会随内容滚走。**
`问道长生v6.html:210-212` 的 `.modal .box{max-height:86vh;overflow:auto}`；`.opt` 约 49px/行 → 19 项约 930px，全项目只有 `.topbar` 一个 `position:sticky`（`:36`），弹窗标题 `<h3>`（`:213`）随内容滚走。
**玩家看到约 13 项就到底，剩下 6 项要滚，且滚走后不知道自己在哪个分类。**

### 3.2 交互反馈

**进度条的过渡动画是死的，永远不会动。** 详见开头"第五个"。证据：`问道长生v6.html:111` 的 `transition:width .25s` + `:481` 同理；`wxcs3-game.js:745-747` 每次新建 `<i class="fill">`；`:990` 整块替换 DOM。**气血/灵力/修为/寿元/香火五根条全部瞬间跳变。**

**没有任何数值变化的动效。** 全项目只有 3 个 `@keyframes`；`transition` 全部集中在 hover/入场。**所有反馈都是静态刷新**，没有一条能告诉玩家数字往哪个方向变了、变了多少。

**toast 是单元素无队列，1800ms 内的第二条会直接顶掉第一条。**
`wxcs3-game.js:701-707`：`el.textContent = m` 直接覆盖，无队列；调用点 231 处。
一次操作里连续产生两条提示时，前一条**不是排队而是消失**；且 1800ms 对"灵石 +12000"这类关键数值偏短。

**toast 没有任何无障碍播报。** `问道长生v6.html:699` 的 `<div class="toast" id="toast">` 无 `role`、无 `aria-live`；`:700` 的 `#achstack` 同样无。**屏幕阅读器用户完全收不到这条唯一的全局反馈。**

**功过格/道途目标的浮层会盖住整个右栏，且关不掉。**
`问道长生v6.html:640-645`：`position:fixed;right:18px;top:72px;z-index:9300;pointer-events:none`；`wxcs3-game.js:1307` 一轮最多弹 12 个（`for (let i = 0; i < 12; i++)`）。
12 个叠起来约 900px 高，正好压住 312px 宽的右栏；`z-index:9300` 高于弹窗的 `60`（`问道长生v6.html:208`），**弹窗打开期间也会浮在弹窗之上**；`pointer-events:none` 意味着玩家点不掉也关不掉，只能干等 3 秒。

**ESC 关闭弹窗是坏的。** 详见开头"第一个"。证据：`wxcs3-game.js:10116` 在 `:10121` 之前提前 return。

**弹窗没有任何焦点管理。** 全项目无 `.focus()` 调用、无 `tabindex`、无 `aria-`。弹窗打开后焦点仍留在背景输入框，键盘用户不知道自己在弹窗里。

### 3.3 信息可读性

**正文与次要信息的字号梯度太陡。**
`问道长生v6.html:28` body 15px/1.65、`:76` 面板正文 13px、`:102-103` muted/small 12.5px、`:646` 功过格标题 10px、`:648` 功过格说明 10.5px、`:491` 状态卡数值 10.5px。
长叙事 15px/1.65 偏挤，但**大量关键说明文字落在 10~12.5px**，笔记本上要凑近看。

**关键资源是裸数字，无单位无参照。**
`wxcs3-game.js:1145`：`灵石 <b>...</b>　声望 ...　功德 ...　业力 ...` 一行 12.5px 文字；而气血/灵力/修为/寿元/香火都配了进度条（`bar()`，`wxcs3-game.js:745`）。
**唯一硬通货灵石没有进度条也没有购买力参照**，玩家无法一眼判断"12000 石的凝婴丹我现在买不买得起"——而这不是低频决策。

**桌面端寿元不在视野中央。**
寿元条只在右栏（`wxcs3-game.js:1034-1040`）；移动端有专门补的 `.vitals` 快照（`wxcs3-game.js:1227-1242` + `问道长生v6.html:487-496`，`display:none` 仅 ≤880px 显示）。
**寿元是本作的硬死亡条件，桌面玩家视线在中栏时完全看不到它。**

**两组语义不同的颜色用了完全相同的色值。**
`问道长生v6.html:13-14` 与 `:10`：`--hp:#B04A40` 与 `--cinnabar:#B04A40` 完全相同（气血 vs 危险）；`--cul:#9A6F1E` 与 `--stone:#9A6F1E` 完全相同（修为 vs 灵石）。
另有语义冲突：`:79` 的 `.panel.warn .ph` 用 `--purple`，`:138` 的 `.tag.warn` 用 `#A0681F`——**同一个 "warn" 键在两处是紫和棕两种颜色**。
**颜色只承担了"好看"，没有承担区分。**

**多组前景/背景组合达不到 WCAG AA**（按声明 hex 计算的对比度）：

| 组合 | 比值 | 命中位置 |
|---|---|---|
| 白字 + `--gold #B8912F` | **2.95** | `.panel.gold .ph`（`:82`）、`.btn.gold`（`:230`） |
| 白字 + `--jade #5E9689` | **3.39** | **所有面板标题**（`:72`）、主按钮（`:225-226`）、选项字母圆点（`:126-129`）、指令坞图标（`:339-342`） |
| `#8C8578` | **3.63** | 7 处 10.5~12px 小字（`:543,550,555,556,560,563,572`） |
| `--merit #4E8A76` | **3.99** | `.good`（`:104`）、`:146`、`:606` |
| `--stone #9A6F1E` | **4.46** | 灵石/修为 |
| `#C05F55` | **4.16** | — |

对照：`--ink #2F2B25` = 13.94、`--muted #756D60` = 5.06 达标。
**"状态 · 修为"这类 13.5px 白字压青绿在低亮度屏上几乎糊成一片——而这是全局最常见的文字形态（每个面板标题都是）。**

**没有深色模式，也没有 `prefers-reduced-motion`。**
grep `prefers-color-scheme` / `prefers-reduced-motion` 全项目命中数为 0。开了系统"减少动态效果"后，`.opt:hover` 的 `translateX(2px)`（`问道长生v6.html:124`）、`.dockbtn:hover` 的 `translateY(-2px)`（`:337`）、`.sceneart` 的 300ms 淡入（`:405`）、`.achtoast` 的滑入（`:645`）全部照常。

### 3.4 移动端

**`mobile/mobile.css` 做得相当扎实，是本次勘察质量最高的部分。**
185 行覆盖了：`text-size-adjust`/`overscroll-behavior`/`touch-action`（`:12-16`）、安全区（`:18`）、触控目标（`:24-38`）、输入框 ≥16px 防 iOS 缩放（`:46-48,145-155`）、`100dvh`（`:53-56`）、顶栏压缩（`:61-71`）、单列重排序（`:76-86`）、对战保持左右并排（`:91-117`）、弹窗底部弹起（`:122-127`）。

**390px 下三栏塌陷后，状态栏被排到第 4 位。**
`mobile/mobile.css:78-84`：`> .col:nth-of-type(2){order:1}` → `.dockrow{order:2}` → `.col:nth-of-type(1){order:3}` → `.col:nth-of-type(3){order:4}`。
玩家要滚过整个中栏和整个指令坞才到右栏；靠 `.vitals` 补了 4 个数，但道心、锚定、异常状态、好感列表仍要滚到底。

**触控目标自己破了 44px 原则。**
`mobile/mobile.css:22` 注释写"触控目标 ≥44px"，但 `:31` `.chip{min-height:38px}`、`:32` `.btn{min-height:40px}`、`:153` `.shop-tab{min-height:38px}`、`:154` `.chip{min-height:36px}`。
**创角页的主修/性别/出身选择器就是 `.chip`**，38px 在手机上偏小。

**底部弹起的弹窗没有处理底部安全区。**
`mobile/mobile.css:122-127` 的 `.modal{padding:10px;align-items:flex-end}` 规则里没有 `env(safe-area-inset-*)`，而 body 底部（`:18`）和 toast（`:148`）都处理了。
**iPhone 上弹窗最下方的按钮会被 home indicator 压住。**

**指令坞副标题在 390px 五列下基本读不出来。**
`mobile/mobile.css:136`（≤560 五列）、`:140-141`（`.ds{font-size:9px;overflow:hidden;text-overflow:ellipsis}`）、`:163`（≤360 直接 `display:none`）。
每列约 68px，9px 字号 + 省略号，**副标题只剩一两个字，信息等于不存在却仍占了一行高度**。

**横向滚动风险整体可控。** 三栏都用 `minmax(0,1fr)`、战斗备注在窄屏改换行（`mobile/mobile.css:104-105`），未发现明确溢出点。

### 3.5 性能与体积

**dist 单文件 8.26MB，且同一份内容在磁盘上存了两遍。**
`mobile/dist/index.html` 与 `mobile/dist/问道长生.html` 均为 8,666,292 字节，完全相同。

**每次动作整块重绘 DOM。**
`wxcs3-game.js:990` 的 `stage.innerHTML = 三栏 + dockrow` 一次性全量替换；全文件 `innerHTML =` 仅 13 处，但 `render()` 是唯一全量入口。
后果：① 每次点击都销毁重建 190px 插画横幅、30 行右栏、全部选项；② `#in-free` 输入框每次动作后失焦重建；③ hover 态全丢；④ **弹窗内滚动位置归零**；⑤ 插画的 `onerror` 兜底与 `loading="lazy"`（`:777`）每轮重跑。

**每次渲染都触发全量存档序列化。**
`:993` → `:997-1001` 的 600ms 防抖 → `:5588-5592` 的 `localStorage.setItem(SAVE_KEY, JSON.stringify(S))`；S 内含 `S.log`（200 条）与 `S.chronicle`（**4000 条**）。
**每 600ms 把含 4000 条纪事的整个状态序列化并写盘一次。**

**无虚拟列表 / 无增量渲染。**
唯一的"增量"是截断：`:1010` 左栏只显示 24 条、`:8877` 年谱弹窗只显示最近 120 条、`:660` 的 `.achlist{max-height:56vh}`。
**`chronicle` 存了 4000 条，但 UI 最多只能看到 120 条。**

**Service Worker 策略本身没问题**（`mobile/dist/sw.js:39-56` 页面网络优先、`:58-70` 静态缓存优先），问题在 8.26MB 的 `index.html` 每次版本更新都要完整重下。

### 3.6 Electron 专属能力

**现有安全基线做得不错**：`contextIsolation:true` / `nodeIntegration:false` / `sandbox:true`（`desktop/main.js:38-44`）、外链交系统浏览器（`:54-60`）、单实例锁（`:131-140`）、`ready-to-show` 白屏优化（`:48-51`）、自检钩子（`:85-125`）。

**但原生菜单被整条删除。** `desktop/main.js:144`：`Menu.setApplicationMenu(null);   // 菜单栏整条去掉`。
**没有文件/编辑/视图/帮助菜单**，导出存档、缩放、开发者工具都没有原生入口；游戏内的"系统"弹窗（`wxcs3-game.js:5789-5800`）是唯一替代。

**没有原生文件读写能力。** `desktop/preload.js:5-9` 只暴露 `{ shell:'electron', version, platform }` 三个只读字段；导出走浏览器 Blob + `a.download`（`wxcs3-game.js:5657-5672`、`:8871-8878`）。
**桌面版导出存档没有原生"保存为…"对话框、不能指定路径。**

**导出提示早于实际落盘。** `wxcs3-game.js:5657-5672` 的 `a.click()` 后立刻 `return true`，`:5714` 就 `toast('已导出：' + nm)`。
**在 Electron 里下载是异步的（用户还要在系统保存对话框里点确认），游戏已经弹了"已导出"；用户取消保存对话框也会看到成功提示。**

**托盘、系统通知、自动更新、深色模式、窗口状态记忆全都没有。** `desktop/package.json:15-18` 的 devDependencies 只有 `@electron/packager` 和 `electron`。
游戏是完全离线的单机，托盘/通知/自动更新当前价值有限；**但原生菜单和原生文件对话框是明确缺口。**

**壳版本号与页面版本号互相矛盾。**
`desktop/package.json:4` 是 `8.1.0`；`问道长生v6.html:6` 的 title 是 `v8.0`；`:692` 的作者署名是 `v8.0`。
**玩家报 bug 时无法判断自己跑的是哪一版。**

**已发布的桌面安装包跑的是旧页面。** 已核实：

|---|---|---|---|
| `mobile/dist/index.html` | 8,666,292 | **有** | 5 处 |
| `desktop/app/index.html` | 8,507,353 | **无** | 0 处 |

差 158,939 字节。`desktop/release_clean/问道长生-win32-x64/resources/app.asar` 内含的 `/app/index.html` 正是 8,507,353 字节。

### 3.7 无障碍与输入

**全项目只有 1 个键盘监听器，弹窗内完全不可键盘操作。**
grep 全 `*.js` 只有 `wxcs3-game.js:10107` 一处 `keydown`，支持 Enter（`:10111-10115`）与 A/B/C/D/E、1/2/3/4/5（`:10117-10120`），生效条件 `:10116` 要求无弹窗。
**坊市、功法、破境抉择、传法、创角的每一个选项都只能用鼠标点**；系统面板（存档/读档/功过格/年谱/帮助/重置）完全不可键盘到达。

**键盘快捷键映射与实际渲染的选项不是同一份数据。**
主栏渲染在 `wxcs3-game.js:1367-1455`，B 键可能是"受箓"（`:1400`）、破境（`:1402`）、闭关（`:1406`）三选一；`mainKeyAction`（`:6498-6509`）把 b 固定成 `full ? openBreak : openMeditate`。
**神道"未受箓且可破柱"时，屏幕上的 B 是"受箓"，按 B 键却打开破境——键盘和鼠标走的是两套不同的意图。**

**零 aria / 零 role / 零 tabindex。**
`.bar` 是纯 `div`+`span`（`问道长生v6.html:110-112`、`wxcs3-game.js:744-746`），无 `role="progressbar"`、无 `aria-valuenow`；可点元素全是 `<div data-act>`（`:1615-1618`）、`<li class="opt" data-act>`（`:789-791`）、`<span class="shop-tab" data-act>`（`:3970`）。
**屏幕阅读器读不出"气血 30/100"这类进度，也听不到任何 toast。**

**文本选中在所有宽度下都被禁掉。**
`mobile/mobile.css:41` 的 `.opt,.btn,.chip,.dockbtn,.sysbtn-top{-webkit-user-select:none;user-select:none}` 位于 `@media (hover:none),(pointer:coarse)` 块**之外**（该块在 `:38` 已闭合），所以桌面端同样生效。
**桌面玩家无法复制丹药名、价格、错误提示、选项文字**，无法比对数值或检索攻略。注释写的是"避免误拖出蓝底"（`:40`）——这是手机需求，却让桌面一起被禁。

**脚本错误只提示 3 次，且一闪而过。** `wxcs3-game.js:10126-10137` 的 `if (errShown > 3) return;`；`:10138-10140` 的 `unhandledrejection` 只 `console.error`，**玩家完全无感**。

## 五、关于"前端做不到就放 exe"的判断

不是所有东西都适合往桌面端搬。按三个标准筛：

**适合放 Electron 的**（浏览器确实做不到或做得很差）：

- 原生文件对话框与任意路径读写——浏览器的下载目录由用户系统决定，无法指定路径
- 系统通知、托盘、窗口状态记忆、任务栏徽标
- 全局快捷键与全局菜单
- 离线资源目录（音效包、字体子集）——当前 8.26MB 单文件每次都要重下，桌面端可以走本地文件直读

**不该放 Electron 的**（放进去反而是负担）：

- 任何游戏逻辑、数值、存档格式——放进去就要维护两套
- 界面布局与视觉——那必须浏览器和手机端共享，否则两端会分叉
- 关键交互（选项、菜单、滚动）——桌面端反而应该更接近网页，避免两套心智

**中间地带**（可以两边都做，但要明确单一事实源）：

- 导出/导入：逻辑在页面，**IO 在壳**。页面调 `WENDAO_DESKTOP.saveFile(...)`，无壳时回退到 Blob 下载。这样一套逻辑两个平台都能用。

## 六、推进建议

**第一批先做。** 六个改动加起来不到 50 行，能一次修掉一个真 Bug（ESC）、一处重复渲染、一项被误伤的能力、一处快捷键错位、一处产物滞后、一处版本号矛盾。全部当场可验证，且不触碰任何视觉决策。

**第五批可以并行做**（`desktop/` 目录与前端基本独立），但要先定一件事：**导出/导入的 IPC 契约**。契约定错会导致后面网页端和桌面端各改一遍。

**第二批的进度条修复需要小心。** 真正的修法（节点复用）会碰到 `render()` 的全量重绘策略，而全量重绘本身是第三、四批要动的部分。**建议先做 7/9/10/11/13（纯加法，不改渲染架构），把第 8 项和"渲染策略"一起做。**

**第三批的第 14 项（右栏分组）会牵动数据结构。** 需要先定义分组边界再动渲染——`renderStateCol()` 现在是顺序 append，改成分组意味着要重构这个函数的组织方式。这是本批里最重的一项。

## 七、不建议做的事

为免返工，明确列出几条看着诱人但不该做的：

**不要为了"好看"加暗色水墨主题。** Cult-Game 的暗色水墨很出彩，但它的前提是墨底 + 描金 + 朱砂的完整色板，而本项目已经锁死了"重墨重彩的**青绿山水**"（实测 33 张插画），现有 22 个变量和 33 张插画都是宣纸米白底。**换底色等于重做全部视觉资产。** 本方案的所有改动都在这个基调内做。

**不要给纵向轴（等级/品阶）配图标。** 已在《图形体系规格》§2.1 写成铁律：等级是纵向轴，玩家已习惯看色块，再画图标就是两套视觉语言打架。

**不要给列表加花哨的 hover 效果。** 参照项目里最有价值的那条 hover 是"一道墨迹自中心洇开"，不是因为它炫，是因为它**用同一套视觉语言**（墨）表达了可点击。当前项目已有 `.opt:hover` 的位移，够用。

**不要引入 React 重写。** Cult-Game 用 React + Tailwind + Vite 是因为它从零起步且有 27 个组件。本项目已有 535KB 的成熟渲染层 + 452 条通过的断言 + 33 张已落地插画。**重写的收益远小于把渲染层推倒重来的风险**，本方案全部改动都不需要框架迁移。

**不要在图标未出图前大规模改列表布局。** 83 张图标一旦落地，列表行的行高、图文比例都会变。**先让图标进来，再调行高**——否则要调两遍。
