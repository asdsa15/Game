## 一、结论速览

### 1.1 总体结论

| 项目 | 评价 |
|---|---|

### 2.2 v6.2 运行架构

```

  ├─ <style> 三栏布局 / 面板 / 弹窗 / 境界条 / 战斗双栏

       ├─ ACT.*         所有玩家动作
       └─ 存档          自动存档 + 5 槽位 + 导入导出 + 版本校验
```

**状态机：**

```
create ──finishCreate()──> play ──startCombat()──> combat
   ↑                         │                      │
   │                         ├──die(reason)──> over ─┘
   └──do_reset / do_legacy───┘
```

**关键设计：**

- **双轨境界**：仙道 `xRealm/xStage`（六境）与神道 `pillar/pos`（八柱四阶）并存，`cultivation` 决定走哪条。
- **功法分家**：`daogong` 道基功法决定修炼速度与境界上限；`skillsKnown/skillsEquip` 是杀伐神通，决定战斗招式。
- **锚系统**：道胎 / 八柱后期没有寿元，靠 `anchors`（物/人/事/仪）维持；`anchors` 总和决定「稳/虚/将散/失锚」。
- **位格压制**：`positionRank()` 把境界折算为数字，战斗时按差值修正伤害。
- **渐进解锁**：`unlockStage` 控制状态栏与常驻入口的显隐。

### 2.5 游戏循环与关键公式

```
每次行动 / 推进一月：
  advanceMonth(1)
    ├─ 仙道：xiuwei += monthXiuwei()
    ├─ 神道：xianghuo += min(monthXianghuo().capped, maxXianghuo()-当前)
    │        followers *= (1-流失率)，受 followLimit 上限
    ├─ 寿元：普通修士 age++；神道/道胎按 lifeStop 处理
    ├─ 锚：tickAnchors() → resolveAnchors()（仅 needsAnchor 时）
    ├─ 气血/灵力自然回复
    ├─ 神位人功、家族供奉、宗门年俸、神道灵石进项
    └─ 香火反噬判定
```

核心公式：

- `monthXiuwei = 境界base × 灵气系数 × 资质/10 × 灵根mul × 功法定阶mul × 伤势系数 × 体质/箓/闭关修正`
- `monthXianghuo = 信众/4 × 虔诚 × 庙格系数 × 灵气 × 神道系数 × 伤势系数`，并受 `need/12` 月上限
- `computePower`：仙道按境界/仙基/果位分档，神道按柱位/位阶/神通数
- 战斗伤害：`hpMax × 基准比例 × 战力比 × 位格倍率 × 五行克制 × 法宝加成`

## 三、缺陷清单

> 级别定义：**P0** = 主线不可达或确定性崩溃；**P1** = 功能断链 / 状态错误 / 核心数值失效；**P2** = 设定与实现不符 / 死分支；**P3** = 工程与体验清理。

### 3.1 P0 · 主线级问题

#### P0-1　紫府之后无法进入金丹（主线断点，已实测）

**现象：** 玩家修到「紫府三关」后，无论怎样点击破境，都只能在「幻想关」反复循环；`xStage` 一路从 3 涨到 8，`xRealm` 始终停在 3，金丹永远不可达。

**证据链：**

1. `openBreak()` 在 `xRealm === 4` 时才调用 `openJindan()`（1132 行）；紫府阶段不会走这里。
2. 紫府阶段只要 `xStage >= 2`，就固定进入 `openZifuGate()`：
   ```js
   // 1147
   if (S.xRealm === 3 && S.xStage >= 2) { openZifuGate(); return; }
   ```
3. `do_zifu()` 成功只执行 `S.xStage++`（2853 行），**从不增加 `xRealm`**；而 `zifuGateName()` 把阶梯钳在 0~2（2844 行），所以第 4 次、第 5 次仍显示「幻想关」。
4. 另一条独立死锁：紫府 → 金丹需要 **天阶道基功法**（`DAOGONG_CAP.tian.cap = 4`），否则在 1139 行的功法上限检查就会被 `openCapBlocked()` 拦住；但天阶传法 `tx_tian` 要求 `needRealm: 4`（金丹），藏经阁只遍历 `SHOP_GONGFA`（只有黄/玄），坊市也不卖天阶。**「需要天阶才能进金丹，天阶又只能金丹后拿」** 形成闭环。唯一例外是奇遇「残页天书」无品阶筛选（3563 行），概率极低。

**实测记录（Node 模拟 DOM）：**

```
第1次: 走紫府=true → xStage=3 xRealm=3
第2次: 走紫府=true → xStage=4 xRealm=3
第3次: 走紫府=true → xStage=5 xRealm=3
...
第6次: 走紫府=true → xStage=8 xRealm=3
```

**影响：** 金丹、果位、道胎、锚系统、12 个结局中的大部分内容全部不可达；游戏实际终点是紫府。

**建议（不修改）：**
- 紫府关只应在 `xStage < 3` 时触发；第三次通关后应走 `openXianBreak()` 跨入金丹，或直接在 `do_zifu()` 第三次成功时推进 `xRealm`。
- 放开天阶功法的正常获取路径：藏经阁真传层应能换天阶；或把 `tx_tian.needRealm` 下调到 3；或让 `openCapBlocked` 的「藏经阁」入口真的能解决当前卡点。

#### P0-2　满柱（八柱·正位）再点破柱直接崩溃（v6.2 与 v5.1 均复现）

**现象：** 神道修到八柱正位后，主栏仍显示「破柱」，点击即抛 `TypeError: Cannot read properties of undefined (reading 'name')`，界面冻结。

**证据：**

```js
// wxcs3-game.js 1369
b += `...下一柱：${D.PILLARS[S.pillar+1].name}...`
// D.PILLARS 只有 0~7，S.pillar === 7 时 [8] 为 undefined
```

`do_pilbreak()` 成功分支也没有上限保护：

```js
// 1383
S.pillar++; S.pos = 0; S.xianghuo = 0;
S.miao = D.PILLARS[S.pillar].miao;
```

v5.1 同样位置：`wxcs2-game.js:676`（`D.PILLARS[S.pillar+1].image`）与 `714-715`。

**实测：**

- v6.2：`FAIL 满柱破柱不崩溃 :: Cannot read properties of undefined (reading 'name')`
- v5.1：`Cannot read properties of undefined (reading 'name')`

**影响：** 神道终局崩溃；且八柱满级没有胜利/结算出口（`resolveEnding` 只在死亡时触发），玩家只能继续点。

**建议：** 在 `openPillarBreak()` 开头与 `do_pilbreak()` 成功分支都加 `S.pillar >= D.PILLARS.length - 1` 的封顶判断；满级改为「证真君 / 结算」而不是继续破柱。

### 3.2 P1 · 功能断链与状态错误

#### P1-1　藏经阁「用贡献换功法」完全点不动（do;libbuy 与 do_libb 不匹配）

- 动作字符串：`'do;libbuy:' + g.id`（1910 行）
- 实际处理器：`ACT.do_libb = (id) => {...}`（1927 行）
- `dispatch` 拼接的是 `ACT['do_' + 'libbuy']` → `ACT.do_libbuy`，不存在 → 兜底 toast「无此指令：do;libbuy:xxx」。

**实测：** `after do;libbuy: owned has liehuo = false, toast = 无此指令：do;libbuy:liehuo`。

**影响：** 藏经阁功法货架整体不可用，而它正是 P0-1 中「换地阶/天阶」的唯一引导入口。

**建议：** 把动作改成 `do;libb:`，或把处理器改名为 `do_libbuy`；同时把 `check_actions.py` 的扫描范围扩到 `optRow(..., 'do;...')`。

#### P1-2　首次破柱会吞掉「本命权柄」

**证据：**

```js
// 1400
if (!S.lu) { logLine('破柱已成，当受天箓……'); openLuPick(); return; }
// 1401-1402 只有在已有箓时才会执行
if (S.phase === 'play') maybeTransmitNow();
openQuanbingPick();
```

首次破柱必然没有 `S.lu`，于是 `openLuPick()` 后直接 `return`；`do_lu()`（2590-2604）只处理受箓、推进一月、渲染，**不会补开 `openQuanbingPick()`**。

**实测：** 首次破柱 → 受箓 → `本命权柄数: 0`（应为 1）。

**影响：** 每个神道角色第一次破柱都少一个权柄；后续破柱才正常。虽然 `currentQuanbing()` 仍按柱位取庙，但「得权柄」的提示与收集感缺失。

**建议：** 把破柱后的后续动作做成队列（受箓 → 权柄 → 传法），或让 `do_lu()` 在受箓完成后继续执行剩余的破柱回调。

#### P1-3　`pendingTx` 残留会永久堵死传法系统

**证据：**

- `openTransmission()` 设置 `S.pendingTx = t.id`（3163 行）
- 只有玩家在弹窗里选择后，`ACT.do_tx()` 才清空（3190 行）
- `applyState()` 已经清理了 `pendingEnc`（2279 行），但**没有清理 `pendingTx`**
- `maybeEvent()` 的触发条件是 `if (S.phase === 'play' && !S.pendingTx) { tryTransmission(); }`（3937 行）

**复现：** 传法弹窗出现时自动存档 / 关闭页面 / 刷新 → 读档后 `pendingTx` 仍是旧 id，弹窗已消失，玩家无法选择；此后 `maybeEvent` 永远跳过传法，所有未触发的传法（地/天/仙阶功法）再也拿不到。

**实测：** 载入带 `pendingTx:'tx_di'` 的存档后，`S.pendingTx` 仍为 `tx_di`。

**建议：** `applyState()` 中 `out.pendingTx = null;`，与 `pendingEnc` 同样兜底；或在 `boot()` 时清空。

#### P1-4　自由输入「打坐」会把 `meditate` 永久置为 true

**证据：**

```js
// 2173-2176
if (/打坐|采气|闭关|修炼/.test(txt)) {
  S.meditate = true;
  const g = Math.round(monthXiuwei()); S.xiuwei += g;
  ...
}
```

`do_free()` 结束后没有 `S.meditate = false`。`monthXiuwei()` 对 `S.meditate` 有 ×2（136 行），`monthXianghuo()` ×1.5（153 行），`monthlyHeal()` ×1.8（2965 行）。

**实测：** `after free-cultivate: meditate = true`。

**影响：** 玩家在自由输入里写一次「打坐」，之后所有行动（游历、宗门任务、事件推进）都按闭关加成结算，直到再次点击正式「打坐采气」（`ACT.cultivate` 才会重置为 false）。这是一个隐性永久增益，严重破坏数值平衡。

**建议：** 自由输入只对本次 `advanceMonth` 临时生效，结算后立刻复位；最好把「闭关」做成显式状态而不是复用 `S.meditate`。

#### P1-5　迁移地图会重置灵脉升级

**证据：**

```js
// 2921-2922
S.lingqi = clamp(p.lingqi, 0, D.LINGQI.length - 1);
S.lingqiBase = S.lingqiBase === undefined ? p.lingqi : S.lingqiBase;
```

- `do_upqi()` 花灵石提升的是 `S.lingqi`；
- 一迁移，`S.lingqi` 被目的地基础灵气覆盖；
- `S.lingqiBase` 被赋值但**全文件没有任何读取**。

**实测：** 灵脉 3 → 迁往青岳 → `lingqi = 1`。

**影响：** 洞府升级投入的灵石被一次旅行清零；玩家可以通过「迁到高灵气地点」免费获得高灵气，也可以被低灵气地点永久降级。

**建议：** 把「地点基础灵气」与「洞府升级档」分开存储，最终 `S.lingqi = clamp(placeBase + upgrade, 0, max)`；或迁移时保留两者较高值。

#### P1-6　破障丹加成不消耗；筑基丹自动扣掉却不生效

**证据：**

- `applyPill()` 的 `break` 分支：`S.breakBonus = (S.breakBonus||0) + v`（3025 行）
- `xianBreakRate()` 读取 `S.breakBonus`（1179 行）
- `consumeBreakBonus()` 已定义（3034 行）但**从未调用**
- `openXianBreak()` 提示「持有筑基丹：成功率 +10」（1190 行，写死 +10，数据实际是 +15）
- `ACT.do_xbreak()` 只执行 `if (S.bag.zhuji > 0) S.bag.zhuji--;`（1200 行），**没有把 +15% 加进本次判定**

**实测：** 破境失败后 `breakBonus` 仍为 `0.12`；`bag.zhuji=1` 时破境后 `zhuji=0, breakBonus=0`。

**影响：**
- 吃一颗小破障丹，之后**每一次**破境都永久 +12%；吃大破障丹永久 +28%；
- 买了筑基丹不手动「使用」，破境时被自动扣掉但没有任何加成；
- 提示中的 +10 与数据 +15 不一致。

**建议：** 在 `do_xbreak()` 掷骰前读取并清零 `breakBonus`；筑基丹的加成显式加入本次 `rate`；统一提示数值。

#### P1-7　崩解期计数恢复后不归零，会跨多次失锚累计致死

**证据：**

```js
// resolveAnchors() 284-322
if (v >= 3.0) { S.anchorState = '稳'; return; }   // 不重置 collapse
if (v >= 2.0) { ... return; }                      // 不重置 collapse
if (v >= 1.0) { ... return; }                      // 不重置 collapse
S.collapse = (S.collapse || 0) + 1;
```

只有「崩解第 3 月且补回至少两根固锚」时才 `S.collapse = 0`（320 行）。

**实测：**

```
第一次崩解后 collapse=1
补回四锚后 collapse=1（应为 0）
再次失锚一月后 collapse=2（新一段应重新从 1 计）
```

**影响：**
- 玩家只要历史上崩解过一次，之后即使完全恢复，状态栏仍显示「崩解期第 N 月」；
- `do_med()` 的 `if (S.collapse > 0) break;` 会让闭关永久提前中断；
- 下一次失锚从旧计数继续累加，更容易直接死亡。

**建议：** 在所有「恢复稳定」分支（`v >= 1`）中把 `S.collapse = 0` 并清理崩解提示。

#### P1-8　灵脉契被当成法宝；「玉华」ID 重名导致材料买成丹药

**证据：**

- 数据：`SHOP` 里 `灵脉契` 是 `{ id:'fudi', cat:'art', type:'land' }`（data 980 行）
- `do_buy()` 先判断 `if (it.cat === 'art')`（1724 行），于是 `type:'land'` 分支永远到不了；`S.arts` 里多了一个 `fudi`，`S.lingqi` 不变；
- `openArts()` 只显示 `D.ARTIFACT_EXT` 中的法宝（1707 行），`fudi` 不在其中，买完完全看不见；
- 数据中 `PILL_EXT` 的 `yuhuaShui`（玉华灵水，760 石，data 303）与 `MATERIAL_EXT` 的 `yuhuaShui`（玉华宝鱼汁，220 石，data 336）**ID 相同**；`SHOP.find` 第一次命中丹药，材料页购买会按 760 扣款并放进丹药。

**实测：**

```
灵脉契: lingqi=1 arts=["fudi"] stones=2600   // 花 2400 石，灵气未升
买 yuhuaShui: 剩 4240（按丹药 760 扣款）
```

**影响：** 2400 灵石买一个不可见、不可用的道具；材料货架的玉华宝鱼汁永远买不到。

**建议：** `do_buy()` 先处理 `it.type === 'land'`，再处理 `cat`；材料 ID 改为 `yuhuaYu` 等唯一值；法宝购买增加已拥有判断。

#### P1-10　藏经阁没有地阶/天阶功法，与「藏经阁分级」设计不符

## 四、v1 / v5.1 抽查结论

### 4.1 共同问题：存档没有迁移层

- **v1**：读档直接 `S = JSON.parse(raw)`（`wxcs-game.js:1265-1267`）
- **v5.1**：读档直接 `S = JSON.parse(raw)`（`wxcs2-game.js:1105-1107`）

两版都没有 `applyState()` 式的字段兜底。只要后续给 `newGame()` 增加字段，旧存档读入后该字段就是 `undefined`，一旦走到 `.push()` / `.length` / 下标访问就可能抛错。v6.2 已经为这个问题写了较完整的 `applyState()`，旧版没有回填。

**建议：** 旧版若还要维护，至少补一个最小迁移函数；若冻结，建议在 README 明确「旧版存档不保证兼容新代码」。

### 4.2 v5.1 的额外问题

| 问题 | 证据 |
|---|---|
| **满柱破柱崩溃** | `wxcs2-game.js:676`、`714-715`；实测 `Cannot read properties of undefined (reading 'name')`。 |
| **道途四印空实现** | `727-729` 只有 `if (S.pillar >= 4 && S.daoYin.length < 4) { /* 到四柱后每破一柱得印 */ }`，注释在、代码没写；`S.daoYin` 永远为空。 |
| **部分状态字段未初始化** | `S.skills`、`S.destinyTong` 等只在个别分支赋值；读旧档后可能缺失。 |

### 4.3 v1 的抽查结论

- 语法通过，`ACT` 动作链无断链，`D.*` 引用无缺失。
- `S.gongfa.push` 有 `includes` 保护（1069/1472），未发现同类崩溃。
- 最高境界前进有 `D.REALMS[S.realm + 1] ? ... : '登仙之上'` 保护（637 行），没有 v5.1 的满级越界。
- 主要风险仍是「无迁移读档」与「无测试」。

### 4.4 三版共同的结构性问题

1. **三套引擎各自复制**：v1 1,748 行、v5.1 1,530 行、v6.2 4,343 行，修复一个共性 bug 要改三处；实际上 v6.2 已经从旧版分叉，旧版不会再同步。
2. **数据与代码的「有表无算」反复出现**：v5.1 的四印、v6.2 的释修/人材/仙基表都是如此。
3. **文档滞后于实现**：每次大改后 README 与审查报告没有回写，导致维护者按旧结论判断。
